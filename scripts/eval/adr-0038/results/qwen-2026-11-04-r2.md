## What changed since the first run

The review found 10 issues. Three of them can change results:

- **Fix 6** changes `auto`. Before, any command that exited non-zero
  turned thinking on for the next step. Now only a tool failure does: a
  timeout, a sandbox refusal or a spawn error. The exit code goes to the
  model as data. This changes (c), (e) and the loop workers in (d).
- **Fix 1** changes the loop: a pass on changed check files never becomes
  the best candidate. No loop run in either data set changed its check
  files. One single run did: (c) `code-json-pointer`, repeat 2, edited its
  test file. The real check restores the original tests, so that run
  failed.
- **Fix 3** keeps the real end of a long command output. It can change
  what the model sees. It does not change how a run is scored, because the
  real check uses only the exit code. No final check in (a) or (b) cut its
  output. So (a) and (b) are kept from the first run, not scored again or
  run again.

The other fixes do not change a result. Fix 2 (symlinks), 4 (JSON
parser), 5 (errors in the summary), 7 (confirm re-run only for `command`),
8 (Go cache path), 9 (no retry of a timeout) and 10 (README) do not apply
to an honest run.

Variant (f) is new. It is `auto` plus thinking on after a non-zero exit:
the policy of (c) in the first run, measured again on the fixed code.

### Does `auto` keep the quality of (a) at the cost of (b)?

It depends on what counts as a failed check.

- **The strict `auto` (c)** thinks on the first step and after a tool
  failure only. On this model it is the same as thinking off: 77 % in both,
  and 68 % on coding in both. It thinks on about one step per run. Its
  token cost is also close to (b): 94.0k against 82.7k total per run.
  The first-run result for `auto` does not hold for this form.
- **`auto` that also thinks after a non-zero exit (f)** keeps the quality
  of thinking on and does better: 92 % against 83 %, and 93 % against 71 %
  on coding. It costs about half of thinking off (42.5k against 82.7k total
  tokens per run). It uses 1.1k reasoning tokens per run, against 5.1k for
  thinking on. It thinks on 1.8 steps per run. Its wall time (111 s) is
  half of thinking on (219 s) and close to thinking off (91 s).
- So the thinking that helps is thinking **after a failing test or build
  run**. A failing test run is a failed check. ADR-0038 decision 4 says
  "after a failed verification". The runtime should count a command that
  exits non-zero as such a failure. A tool failure alone is not enough.
- The cost of this rule is small. A `grep` with no match also exits
  non-zero, but (f) thought on only 1.8 steps per run.
- Thinking on loses through the output cap, as in the first run. Nine of
  its 52 runs stopped at 12,288 completion tokens in one step.

### Does the loop beat the single run, and at what cost?

Yes. The gap to the best single variant is now smaller, and the cost is
higher.

- Against (f), the best single run: 96 % against 92 % overall, and 100 %
  against 93 % on coding (28 against 26 of 28 runs). The cost is 2.6 times
  the total tokens (111.9k against 42.5k) and 6.1 times the wall time
  (682 s against 111 s).
- Against the strict `auto` (c): 100 % against 68 % on coding.
- The loop workers now use the strict `auto`, so they think less and take
  more steps. In 9 runs a worker hit its 20-step limit. The loop still
  recovered by more rounds: 1.6 rounds per run, against 1.2 before.
  - `code-template-sections` passed in round 3 in both repeats, after two
    cut-off workers. The held-out tests passed too. In the first run the
    loop passed only the public tests here.
  - `code-go-cron` (repeat 2) passed in round 6, after five cut-off
    workers.
- So the round structure did the work this time. The plan alone did not
  carry it. Only 20 of 28 coding runs passed in round 1.
- The control (e) again shows that it does not help to tell a single run
  the check. It passed 77 %, the same as (c).
- Not measured: the loop with (f) workers. With the first-run policy, the
  loop needed 1.2 rounds and 57.1k tokens. It is likely the cheapest form
  of the loop.

### Where did the loop get worse?

- **A schema pass is not a content pass.** Two extraction runs
  (`extract-flight-itinerary` and `extract-incident-timeline`, repeat 2)
  ended "verified" with wrong values. In the first run there was one such
  run. The `schema` verifier is strong only for shape.
- **The reviewer does not converge.** On the doc tasks the loop used 2.8
  rounds, 29k reasoning tokens and 1,294 s per run, against 44 s for (c).
  In `doc-api-reference` (repeat 1) the reviewer rejected all 8 drafts.
  The run ended "unverified" after 87 minutes, and its document passed the
  rubric. Every single variant also passed every doc rubric.
- **Overfitting.** `code-csv-quotes` (repeat 1) ended "verified", and the
  held-out tests failed.
- **The hard rules still never fired.** There were no `done` overrides, no
  regression restores, no flaky confirms and no same-task stops. One run
  stopped at the round limit.

### Recommendations

- **Qwen default: `auto`, where a command that exits non-zero counts as a
  failed check.** That is (f): the best quality of the single variants, at
  about half the tokens of thinking off. Without that rule, `auto` is no
  better than off on this model. Send this to the ADR-0038 decision 4
  implementation.
- **Verified loop: go, as an opt-in mode.** It is the only variant that
  passed every coding run. It costs 2.6 times the tokens and 6 times the
  wall time of (f), so it must not be the default. Give its workers the
  same `auto` rule.
- Label a run that only a `schema` verifier checked as "shape verified" or
  similar, not plain "verified".
- Do not offer the `review` verifier as an agent default. It did not
  converge on a document that met every mechanical requirement. Its reject
  rate on planted wrong results is still unknown.

### Limits

- **Small sample.** 26 tasks and 2 repeats. Between repeats, 20 to 24 of 26
  tasks gave the same result per variant. A difference of two or three
  runs is in the noise. The differences that the conclusions use are 7 to
  9 coding runs ((c) against (f) and (d)) and 2 coding runs ((f) against
  (d)). The second one is in the noise.
- **Two runs of the same code mix.** (a) and (b) come from the first run.
  The other variants come from the second run. The server, model and tasks
  were the same.
- **Ceilings.** All variants passed all doc tasks. Extraction was close to
  the top. Only coding separates the variants well.
- **Load.** Up to 8 runs shared one vLLM server, so wall times include
  waiting in the queue.
- **Output cap.** The 12,288-token cap per call shaped the result of (a).
- **Prompt cost.** The token counts are nominal. vLLM prefix caching makes
  resent prompts cheaper than the counts show. This favours the variants
  with many steps: (b), (c), (e) and the loop workers.
- **One model.** The `gpt`, `claude` and `gemini` entries in
  `providers.json` are templates. Nobody has run them yet.
