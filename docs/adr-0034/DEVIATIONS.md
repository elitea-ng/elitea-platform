
## desktop

Branch `feat/handoff-desktop` (workspace-store crate, local-tools `handoff` feature, Tauri `src/handoff.rs`).

1. **Error envelope.** The real `desktopwire.WriteError` is flat: `{"error": "<code>", "message": "…"}`, not the nested `{"error": {"code","message"}}` of §2. The client reads both. It reads `details` (for `ref_conflict`'s `current`) from `details` at the top level or from `error.details`. The server must put `current` in one of those two places.
2. **Bearer on grant URLs.** The bearer is sent only to a URL on the deployment's own origin (the ADR-0016 streaming facade). A presigned URL on another host never receives it. A URL that is not `https` (or `http` when the deployment itself is `http`) is refused.
3. **Multipart completion.** §2.2 does not define it. The client sends `POST complete_url` with `{"upload_id", "parts": [{"part_number", "etag"}]}` and takes each part's `ETag` from the PUT response header. When `complete_url` is on the deployment's origin it carries the bearer.
4. **Lost publish ack.** The client relies on the identical-replay rule. In addition, a retried publish that meets `409 ref_conflict` with `current` equal to every `new` value of the request counts as success, and `seq` comes from the fetch plan's `head_seq`. A first attempt that meets this conflict is still a conflict.
5. **Repository top only.** Phase 1 refuses a workspace that is a subfolder of a repository (`handoff_unsupported`). A folder with no repository gets the shadow.
6. **Shadow location.** The shadow git directory is `<app data>/handoff/shadow/<key>`. The app data is on the deny list of host git, so for the shadow the deny list is carved: the shadow is opened and every other entry of the app data stays denied.
7. **Caps before begin.** The preview and the send check the ADR default caps before begin, because the limits arrive only in the begin answer. `project_workspace_bytes_left` in `handoff_preview` is therefore `null`. If the server's limits refuse the snapshot after begin, the desktop cannot cancel: no cancel route exists, and DELETE is for `CLOUD_*` and `RECLAIMING`. The thread then stays `HANDING_OFF` until the 15-minute expiry, and the desktop reports `handoff_too_large`. **Ask:** let the server accept `DELETE workspace_handoff` in `HANDING_OFF`, or add a cancel route.
8. **Whole-object packs.** Segments are written without deltas, so they are larger than a `git bundle` of the same refs. The Phase 1 caps bound the size. The reader accepts deltified packs (`git bundle create` output) too.
9. **IPC additions.** These do not change the names of §5:
   - `handoff_undo {checkpoint_id}`: `checkpoint_restore` is keyed on turn ids, so a take-back's checkpoint (`"<workspace_id>:<seq>"`, in the workspace's own checkpoint store) is restored here;
   - optional `project_id` on `handoff_status` and `handoff_erase`, for a thread that has no local record;
   - `modes` on the preflight answer;
   - `branch`, `imported_turns` and `released` on the apply answer;
   - `executor`, `read_only` and `sent_from_here` on the status answer;
   - `details` on every rejection (findings, caps).
10. **Outcomes.** The preflight returns `fast_path` or `conflicts`. `conflicts` covers every change since the send: HEAD moved, local edits, or both, even when no path overlaps (`conflict_paths` lists the overlapping ones). An `error` outcome is an IPC rejection with a code (`integrity_failed`, `handoff_conflict`, …), not a value.
11. **History column.** The column is `turns.turn_origin` (`local` or `cloud`), because `turns.origin` already holds the deployment origin. In JSON the field is `StoredTurn.origin`. The schema goes from v1 to v2 by `ALTER TABLE`.
12. **Worktree mode.** A path the cloud wrote that the send excludes (a `.env` created in the cloud) is not written into the worktree, so `git status` there shows it deleted. For a shadow folder the "worktree" is a plain directory beside the folder, with no git worktree.
13. **Device policy key.** The desktop reads `local_work.cloud_handoff` from the native client policy (the platform key is `local_work_cloud_handoff`), the same pattern as `cloud_sync`. The server unit must send it under that name in the `local_work` group.
14. **Device id.** The begin and reclaim calls send the device id of the stored native session. Only when the session has none does the desktop send a random per-install id (`<app data>/handoff/install-id`).
15. **Cloud turn import.** The desktop reads `GET conversation/prompt_lib/{p}/{uuid}?messages_limit=1000&sort_order=asc`. A cloud turn is an answer group whose `meta.executed_by` is `cloud_executor` and whose `meta.workspace_epoch` is between the epoch after complete and the release epoch. The question is the `reply_to_id` group, else the group before it. Changes come from `meta.workspace_commit`, which must be a commit of the fetched chain; otherwise the turn is imported with no changes. Text comes from `message_items[].item_details.content` of `text_message` items.
16. **Stats.** `stats.excluded` is a list of `./path` strings, as in the §2.1 example. `scan_findings` is always 0, because a finding stops the send before begin.
17. **Release retry.** A release that gets no answer is stored and sent again on the next `handoff_status`. Until the server acknowledges it, the thread stays read-only on the desktop.

## web-ui

Branch `feat/handoff-desktop` (apps/elitea-web: `features/workspace-handoff`, `shared/desktop/handoffIpc*`, `pages/workspace`, `pages/chat`, `widgets/desktop-shell`).

1. **"Leave on my laptop" does not shrink the preview.** `handoff_preview` takes only `{workspace_id, conversation_uuid}`; `leave_on_laptop` exists on `handoff_send` only. The client sends `leave_on_laptop` with the preview too when the list is non-empty (the host ignores an unknown argument today) and re-runs the preview, but until the host honours it the counts and sizes do not drop. The UI hides the findings of a left file locally and passes the list to `handoff_send`; a finding the preview could not see comes back as `secret_found` with `details.findings` and is shown the same way. **Ask (Rust unit):** accept `leave_on_laptop` in `handoff_preview`.
2. **Send button visibility.** `handoff_status` carries no policy, so the client reads `host_state().policy.local_work.{allowed, cloud_handoff}` (the stored `native_client_policy`). It shows Send only for a started thread (it needs the conversation UUID), whose status is `LOCAL`, when both flags are true. A host that stores the policy under another shape hides the button (safe default).
3. **UUID.** The session page holds the numeric conversation id; the UUID comes from `GET conversation/prompt_lib/{p}/{id}` (`uuid`). The sidebar must badge a row without opening the thread, so a thread page remembers `id → uuid` per folder (`desktop.workspace.<id>.threadUuids`, `el.` namespace) and the row asks `handoff_status` (no `project_id`: the host answers from its own records, no request for a thread never sent). A thread never opened since this build has no badge. The row shows the badge for `In cloud` and `Returning` only; `Local` is shown in the thread's header (a `Local` chip on every row would be noise).
4. **Cloud transcript.** While not `LOCAL` the transcript is the conversation's server messages (the existing "earlier messages from the server" read, newest 100), polled every 3 s, in place of the recorded turns. Tool rows of earlier local turns are not shown during that time; they are back after the take back (the host imports cloud turns into the history).
5. **Preflight shows paths, not diffs.** `handoff_preflight` returns paths only (no diff text), so `unifiedDiff` / `ChangedFilesCard` are not reused in the take-back dialog. The result lists changed, conflicting and skipped paths.
6. **Take-back notification.** The notification plumbing exists in the desktop (SSE signal + list). A new shell toast (`ReclaimRequestToast`) reads unseen notifications of event type `workspace_reclaim_requested`. **Assumption to confirm with the server unit:** the notification's `meta.conversation_id` carries the conversation id or its UUID (either is matched). Without it the toast does not show. The toast marks the notification read on Take back or Dismiss. It shows only for threads this computer remembers (id or UUID in the folder's thread list); a request for another computer's thread shows nothing.
7. **Web build.** `workspace_executor` is read from the conversation response and the owner from `author_id`. For `cloud` the composer stays enabled and a notice sits above it (through `extensions.contextIndicator`); for `returning` the notice replaces the composer (a cloud turn would not start); `local` Local work threads keep the read-only notice. Regenerate is dropped (`extensions.noRegenerate`, new) when the newest answer's `meta.executed_by` is `desktop`; edit-and-resend stays. The generated client is not touched: `shared/api/workspaceHandoffApi.ts` is a hand-written stand-in for the three routes, to be deleted when v2.yaml has them. `GET workspace_handoff` is polled every 10 s by the notice (for `reclaim_pending`, and to re-read the conversation when the thread is `LOCAL` again).
8. **Strings.** 14 new shared strings (`pages.chat.cloud.*`) are in `en.json` (the web notice), everything else in `en.desktop.json`. `features/workspace-handoff` is a desktop-only prefix in `scripts/lib/i18n-backfill-core.mjs`.
9. **Visual baselines.** Not regenerated (see memory). Affected only if a spec renders a desktop Workspace session or a chat of a cloud thread: none of the current baselines does.

## server

Branch `feat/handoff-server` (services/elitea-main). Migrations shared/0167 and shared/0168.

1. **Error envelope.** Flat desktopwire shape `{"error": code, "message": ...}` as the coordinator asked. `ref_conflict` and `env_name_denied` put their data in a top-level `details` object (`details.current`, `details.names`).
2. **Epoch on cloud turns.** CLOUD_IDLE → CLOUD_RUNNING → CLOUD_IDLE keeps the epoch (contract §2.6/§4 examples: epoch 2 in CLOUD_RUNNING). A cloud turn is fenced by its execution id (`running_execution_id`) and the epoch. Every ownership change (send, complete, take back, release, erase, expiry, forced reclaim, abandoned reclaim) increments it. ADR decision 7 says "on every state change"; the contract wins.
3. **reclaim_pending closes the fence.** The `local_work_thread` fence opens only for CLOUD_IDLE / CLOUD_RUNNING **with no take back pending** (ADR decision 7: no new cloud turn starts while it is set). Such a start answers 409 `local_work_thread`.
4. **Two extra routes.** `PUT|GET workspace_store_object/prompt_lib/{p}/{conversation_uuid}/{sha256}` is the streaming facade for backends without presign (the artifact routes must 404 workspace grants, so the ADR-0016 facade route cannot carry them), and `POST workspace_store_upload_complete/prompt_lib/{p}/{grant_id}` completes a multipart grant (body `{"upload_id","parts":[{"part_number","etag"}]}`). Multipart is used above 64 MiB on backends with native multipart, 64 MiB parts. 15 client operations in all (13 handoff/store + policy is §6).
5. **Native token only.** Every desktop route (begin, complete, reclaim, release, upload, upload complete, publish, fetch, object PUT/GET) needs a native app access token (`handoff_requires_token` otherwise), not only begin. GET state, DELETE and reclaim_request accept a cookie or any token.
6. **Error codes beyond the contract.** `handoff_not_found` (404), `handoff_not_in_cloud` (409, reclaim_request outside CLOUD_*), `handoff_unavailable` (503), `handoff_failed` (500), and for regenerate in a handed-off thread `cloud_turn_not_newest` (409) beside `local_work_turn`. Body/shape errors are 400 `invalid_handoff`; validation errors (caps, not a Local work thread, refs not published at complete) are 422 `invalid_handoff`.
7. **Begin caps.** A send whose declared `stats` pass `max_files`, `max_segment_mb` or `max_unpacked_mb` answers 422 `invalid_handoff` (the contract lists no 413 for caps at begin; 413 is the quota only).
8. **Erase.** DELETE accepts every non-LOCAL state, HANDING_OFF included (the desktop's cancel, §6.3). It erases the objects (and the env secret) synchronously when it can; the sweeper finishes what it could not. A send while an erasure is unfinished answers 409 `handoff_in_progress`. DELETE on a LOCAL row within its return grace erases the cloud copy now. HANDING_OFF erase appends no event message.
9. **Event messages** are authored by one `system` participant per tenant schema (`entity_meta.kind = workspace_handoff`), not mapped into the conversation, with meta `workspace_event` and `workspace_epoch`. Texts: "Work moved to the cloud executor (N files, M left on the laptop)." + note; "Work returned to <device name>." (device name from `elitea_auth.native_sessions`, "the desktop" when unknown); the erase text of ADR decision 12.
10. **workspace_executor** is on the conversation details response, the conversation list rows and the list's `changes_since` delta rows. Every ownership transition stamps the conversation's `sync_at`, so the delta re-delivers the row. The reclaim notification's meta is `{"project_id", "conversation_id" (the UUID), "conversation_uuid", "epoch"}`, event type `workspace_reclaim_requested`, deduplicated per thread, epoch and hour.
11. **Regenerate rewind not wired.** The ADR's "regenerate moves refs/elitea/cloud back to the turn's parent" is executor-side (it needs the turn's commit); the server gives the newest-turn and desktop-turn refusals and strips `workspace_epoch`/`workspace_commit`. `workspacehandoff.CloudTurnMeta(epoch, commit)` builds the answer meta keys (`executed_by`, `workspace_epoch`, `workspace_commit`) for the executor.
12. **Dedicated bucket.** The chart value is `main.env.STORAGE_WORKSPACE_BUCKET` (not a new `storage.workspace.bucket` key): same backend and credentials, segment rows record `physical_bucket`. Chart sandbox resources: `main.env.ELITEA_CLOUD_EXECUTOR_{TURN_WALL_SECONDS,CPU,MEMORY,DISK}`.
13. **Encryption gate.** S3 reads GetBucketEncryption (AWS S3 and RustFS implement it); Azure Blob and GCS are always confirmed. Three answers: a default rule confirms; no rule (`ServerSideEncryptionConfigurationNotFoundError`) or an error refuses, and no attestation overrides it; a backend that does not implement the call (`NotImplemented`, 501, or a store without the check) is "unreportable". Only then `main.env.ELITEA_CLOUD_EXECUTOR_STORAGE_ENCRYPTION_ATTESTED=true` enables the executor. The default stays refuse; an invalid value stops startup. An attestation is logged at startup (warning), written to the audit trail once per bucket set (advisory lock + insert-if-absent into `centry.audit_events`, entity `cloud_executor`; if that write fails the attestation does not apply), and shown as the admin `cloud_executor` section's `notice` ("attested by operator"; the notice also says "reported by the storage backend" or "not confirmed"). **Consequence for dev stacks:** RustFS answers "no rule" for a bucket without `PutBucketEncryption`, so a local stack must configure bucket encryption on RustFS (the attestation does not apply to it).
14. **Policy permission.** The admin `cloud_executor` section reuses `configuration.native_clients` (no new permission, no migration).
15. **Project setting writes** go through the generic configurations routes; the `cloud_executor` type additionally needs `models.project_settings.edit` on create, update and delete.
16. **Admin usage, idle warning, offboarding** (were "not done").
    - There is no admin "storage view" in this platform, so the per-project usage is on the admin **projects** listing: `GET admin/projects` rows carry `workspace_bytes` (live segments, apart from artifact usage; sortable), and the web admin projects table has a "Cloud copies" column.
    - The idle warning is a notification, event type `workspace_idle_expiring`, sent 3 days before the idle-retention erasure; meta `{project_id, conversation_id (UUID), conversation_uuid, epoch, delete_after, message}`; once per thread, epoch and idle period (deterministic uuid). No banner is pushed; GET still answers `delete_after` for the client's own banner. The CLOUD_IDLE walk is now keyset paged and continues across sweeps (the old oldest-first batch of 50 could starve a due thread behind many not-yet-due threads of a longer-retention project).
    - Offboarding is detected by the sweeper, not by a hook in each route: a thread whose owner is deleted or suspended (`auth_core__user.suspended`, which both the admin suspension and a SCIM deactivation set) is erased with the orphan erasure (cancels a running turn, erases objects and the env secret) within one sweep (30 s). This covers the admin routes, SCIM and direct changes alike. A suspension is treated as offboarding, so un-suspending does not bring a cloud copy back. A database without `public.auth_core__user` (it belongs to the auth migrations) skips the owner check.
17. **Amendment (§6).** `GET workspace_handoff_policy/prompt_lib/{p}` needs `models.chat.messages.create` (cookie or any token). The env secret is ONE **hidden** secret of the **project** vault (not the global vault), named `workspace_env_<32 random hex>`; the name lives only on the handoff row, so no `{{secret.NAME}}` reference can reach it, and the redeem refuses a regular secret of that name. A send without `env` keeps the thread's previous secret; `env: {}` clears it; a new non-empty `env` replaces it. The secret is erased with the objects (cancel, erase, release + grace, idle retention, conversation/project gone), before `deleted_at` is set. `path_denied` carries `details.paths`; `env_name_denied` carries `details.names`. At most 1000 includes per send. A `path_deny` pattern anchored at `~/` or `/` matches nothing inside a workspace. Glob rules: `**` spans directories, a pattern without `/` matches the base name at any depth.
18. **Executor hooks (§6.4).** `workspacehandoff.Service.CloudTurnEnv(ctx, thread, epoch, executionID)` answers the values only for the running turn of that epoch (else `ErrStaleEpoch`); `Handoff.EnvSecret()` is the runtime context's `env_secret`; `Policy` carries the effective `Exclusions`, `PathDeny`, `AllowUserInclude`, `EnvHarvest`, `EnvDeny`, `EnvAllow`. The audit of `handoff.begin` and `handoff.complete` lists include paths and env names, never values.
19. **PullRequestSource dropped.** Main exposes no pull-request diff source; the worker computes the diff itself. `RecordExecutorEvent` keeps `pull_request.opened` (and `scan_blocked`) for the audit row.
20. **Publish hashing.** The upload grant binds the SHA-256: on a backend with `Capabilities.ChecksumSHA256` (S3, RustFS) the presigned PUT signs `x-amz-checksum-sha256` (a required signed header, never hoisted to the query) and the grant's `headers` carry it, so the store refuses other bytes (BadDigest). Publish then does one HEAD (`x-amz-checksum-mode: ENABLED`) and compares size and full-object digest; no bytes stream through Main. A segment above 64 MiB on such a backend gets ONE checksum-bound PUT (up to the 5 GiB single-PUT ceiling) instead of multipart, because a multipart upload has only a composite checksum. Fallback (streaming hash at publish): GCS and Azure (no SHA-256 checksum exists there; their MD5/CRC cannot bind the SHA-256 address), multipart, the facade, and any object whose HEAD reports no full-object digest. **The desktop must send every header in the grant's `headers`** (it was `Content-Type` only).
21. **Workspace bucket by type.** The hidden bucket is found by `bucket_type = 'workspace'`, never by name. If a user bucket `elitea-workspaces` already exists, the hidden one is created as `elitea-workspaces-<8 hex>`; the user bucket keeps working (artifact routes, access lists and the runtime plane gate on `IsWorkspaceBucket`, by type). New user buckets cannot take the reserved name or any `elitea-workspaces*` name.
22. **Env vault.** The first harvested env creates the project vault row (idempotent) instead of answering 503.
23. **Policy exclusions split.** `GET workspace_handoff_policy` also answers `exclusions_platform` and `exclusions_project` (project additions the platform does not already list); `exclusions` is unchanged.
24. **Load gate (decision 15).** `-tags loadgate`, job `ci-handoff-loadgate.yml`. The gated p99 (< 50 ms) is for 1,000 threads publishing within one second (1 ms apart). A burst of 1,000 released at one instant is measured and logged but its latency is not gated: with a bounded pool (32) p99 is the drain time of the pool's queue (local: 136 ms), and the gate also forbids connection growth. Row/transaction lock waits between threads are gated to zero; relation extension waits (`extend`) are logged, not counted. Local (pool 32): sustained p99 1.27 ms; burst p99 136 ms, 0 row lock waits; contention case other threads p99 7.6 ms, the hot thread waits only on its own row.
## executor

Branch `feat/handoff-executor` (worktree `.claude/worktrees/handoff-executor`).

1. **Five RPCs, not four.** `WorkspaceStoreService` has `WorkspaceFetchPlan`, `WorkspaceUpload`, `WorkspacePublish`, `WorkspacePullRequestDiff` and `WorkspaceEnvSecret` (contract 6.4; the "existing ADR-0011 secret path" is internal REST on the content plane, and AGENTS.md forbids new internal REST, so the env rides a claim-bound gRPC stream). Segment bytes ride the fetch stream itself (plan frame, then 32 KiB chunks, then an end frame) instead of a separate download RPC or a presigned URL, so the control listener's 64/80 KiB message bounds are unchanged.
2. **Server-side meta stamping.** The worker returns `executed_by`/`workspace_epoch`/`workspace_commit` from its publish but has no channel to put them on the response without changing `agent.proto`. Main must stamp them from its own publish record (the claim's execution id → epoch, new cloud sha). This is integration work for the server unit (documented on `workspaceruntime.Store`).
3. **Audit events from the worker are log events.** `handoff.scan_blocked` and `pull_request.opened` are emitted as structured `tracing` events (counts, rules, shas; never paths or contents); the worker has no audit API. Main should record the audit rows (the scan failure arrives as turn failure cause `workspace_run.secret_found`).
4. **No workspace-run launcher yet.** The worker cannot reach Docker/Kubernetes (the sandbox supervisor does). There is no supervisor RPC for long-lived workspace runs (start, exec `unpack|serve|pack`, destroy), so `WorkspaceSandboxLauncher` has no production implementation and the worker composes no `WorkspaceRunFactory`: a cloud turn fails with `workspace_run.unavailable` instead of running without files. The pod/container specs (`sandbox::workspace_run`), the runner binary and image, and the turn lifecycle are done and tested; the supervisor bridge is the remaining integration. Consequently **no Docker-backend integration test was run** (nothing to launch), and the runner was tested on the host (macOS) with `container` enforcement, not in the image; the image was not built.
5. **Host allowlist refused.** There is no ADR-0011 egress proxy in the code. A project `network_allowlist` with network on makes `WorkspaceRunSpec::from_context` refuse (`workspace_run.policy_unenforceable`).
6. **Docker egress.** `deploy/docker/workspace-egress.sh` creates the dedicated network (IPv6 off, ICC off) and DOCKER-USER rules (deny RFC 1918, CGNAT, link-local/metadata, loopback, extra ranges; DNS only to `ELITEA_WORKSPACE_EGRESS_DNS`). The compose stack does not run it; the supervisor must set the same resolvers as container DNS (`DockerRunPlan.dns`). Docker's local volume driver cannot cap the named workspace volume's size; the runner's archive limits bound it. Not exercised on a live Docker host.
7. **Kubernetes DNS off.** With the network off, a workspace-run pod has `dnsPolicy: None` and nameserver `127.0.0.1` (and no egress label, so deny-all applies).
8. **HITL from the runner.** The runner's approval channel approves commands the rules ask about only for network or full access (decision 9); anything else (destructive commands) is deferred, which the tool reports as waiting for approval. It is not yet turned into a server HITL interrupt.
9. **`create_branch.from_sha` is not in the model schema.** The SDK conformance gate compares the family's schemas with the SDK's; `from_sha` is accepted by the argument parser and passed in process by `open_pull_request` only.
10. **`open_pull_request` repository match is checked at call time** (the runtime context only says `has_upstream`); a folder whose upstream URL names another `owner/repo` than the toolkit's is refused.
11. **Trailer formats I defined.** `Elitea-Included: <path>` (one trailer per explicit include, on the handoff snapshot commit) and the upstream parse `Elitea-Upstream: <sha> <url> <branch>` (as the desktop writes it). The desktop must write `Elitea-Included` this way.
12. **`WorkspaceStore` (crate) transport trait not implemented.** It is URL/presigned-PUT shaped and does not fit gRPC streaming; the worker has its own `WorkspaceStore` trait over the gRPC client. Only the crate's bundle/objects modules are used (no `rest` feature).
13. **Env redaction scope.** Values are redacted from every tool result (so the transcript and trace). Files a command writes (e.g. `env > out.txt`) are committed and published unredacted; the segment re-scan on publish is not done.
14. **Pipelines refuse workspace turns** (`workspace_run.unavailable`) when they redeem the runtime context; a recovered model checkpoint of a workspace turn is refused too (its sandbox is gone).
15. **Workspace runner image is not in docker-bake/publish/scan.** Adding a bake target requires the four lists `scripts/ci/image-matrix.sh` checks; left for integration.
16. **fmt.** `cargo fmt --check` from the worker also checks `libs/rust/workspace-store/tests/rest.rs`, which the desktop branch's later commit reformats; the cherry-picked c0a5e516f version fails it until that lands.

## desktop-followup

Branch `feat/handoff-desktop`, on top of 3ebcbc607. Supersedes desktop items 7 (caps before begin, no cancel), 8 (whole-object packs) and 12 (worktree mode) and web-ui items 1 (preview ignores leave_on_laptop) and 5 (paths, not diffs).

1. **Delta packs: who writes them.** The desktop packs a send with its hardened, sandboxed git: `pack-objects --revs --delta-base-offset` into a private temporary object directory that borrows the repository's objects as an alternate (git writes its temporary pack into the object directory, which the sandbox keeps read-only). `elitea-workspace-store::bundle::write_compact_with_pack` wraps the pack in the v2 header after checking the refs, the limits and the object count, and the desktop verifies the result with the store's own reader (`verify_into`) before upload. The crate never runs git: reading needs no git binary, and a writer without git (the cloud worker today) keeps `write_compact` (whole objects, about 1.5x larger on text). A delta writer inside the crate is left for when the worker needs smaller segments.
2. **Exclusion sources.** §6.1's `exclusions` is one merged list, so the desktop cannot tell platform from project patterns. It shows a pattern of the ADR's default list as platform and any other as project, unless the server also sends `exclusions_platform` and `exclusions_project` (read when present). **Ask (server unit):** send those two lists.
3. **Pattern syntax.** Platform, project and folder patterns match at any depth (`.env` matches `a/b/.env`); a leading `/` anchors at the folder's top; `x/**` covers a directory. Includes are exact paths or patterns anchored at the top (an include widens what leaves the laptop, so it never matches at any depth). A path with a control character is never included (it could not be named in a trailer).
4. **Trailer form.** One `Elitea-Included: ./<path>` per included file, the same `./` form as `stats.excluded` and `included_excluded`; the executor strips the `./`. A test parses the trailers back the way the executor's hydrate does.
5. **Env harvest source (decided 2026-10-15: the login shell).** The harvest offers the person's login-shell environment, read the way editors read it: `$SHELL -l -i -c` (else `/bin/zsh` on macOS, `/bin/bash` on Linux) printing `/usr/bin/env -0` between two random markers, from the home directory, no stdin, its own process group killed at 10 s, 1 MiB read at most (`local-tools::shell::login_environment`, tokio process like `run_command`). It is merged over the desktop process's environment, then `env_deny`/`env_allow` apply. It runs once per preview, settings read and send; values are never cached or written. A shell that fails, hangs or prints no markers offers nothing and sets `env.notice` / `env_notice` (shown in the dialog), never an error. Local `run_command` is unchanged (it still passes only its fixed passthrough set). The shell runs unsandboxed, as a terminal would: it is the person's own rc, not repository code (the working directory is the home, not the folder).
6. **Defaults without the policy route (404).** `allow_user_include: true` (the ADR's ceiling default), `env_harvest: false`, the ADR's exclusion and env deny lists and caps; `project_workspace_bytes_left` stays `null`; the preview's `policy.source` is `defaults` and the UI says so. Any other failure of the route rejects the preview.
7. **Cancel.** Every failure after begin (begin's caps, upload, publish, complete, storing the record, `handoff_cancel`) sends `DELETE workspace_handoff`; a failed DELETE is logged and the server's 15-minute expiry remains the fallback.
