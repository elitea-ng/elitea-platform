---
title: "Use several agents in a thread (desktop)"
description: "How a Local work thread in the Elitea desktop app holds more than one agent, which of them answers a message, and what an agent that runs in the cloud can see."
---

A **Local work** thread in the Elitea desktop app can hold more than one agent. You add agents to the thread, address a message to some of them with **@Name**, and each addressed agent answers in turn, in the order you named them. An agent can run **on this computer**, with the thread's folder, or **in the cloud**, with the conversation's text only.

## Add an agent to a thread

A thread's agents are managed in the **Participants** tab of the inspector, the right sidebar, as a chat's participants are in its side panel.

<Steps>
1. Open a thread in **Local work**. The composer's agent chip shows the thread's agent, for example **Coder · base**. Select the chip to open the **Participants** tab.
2. Choose **Add an agent** or **Add a cloud agent**, type part of the agent's name to find it, and pick it.
3. The agent is listed in the tab, marked **Local** or **Cloud**, under **Join with your next message** in a thread that already has messages. **Remove from thread** takes it out before you send.
</Steps>

The agents join the conversation when you send your next message. An agent joins on its first version. An agent of a saved team that names no version answers on its agent's default version.

In a new thread, the tab lists the composer's agent first, with its version and **Change** to pick another agent. Before the first message, **Make lead** on another agent makes it the agent that answers a message that names no agent; the composer's agent then becomes one of the others.

## Run a thread as a team

A saved [team](/how-tos/agents-pipelines/agent-teams) can run a Local work thread.

<Steps>
1. Open a new thread in **Local work** and select the agent chip to open the **Participants** tab.
2. Choose **Add team**, then the team. The tab lists the team's agents, the lead first and marked **Lead**, and **Team: Review crew** above them. The chip shows the team and who your message goes to, for example **Review crew · To: Reviewer (lead)**.
3. Send your first message. The thread is created with every agent of the team, each on the version the team saved, and the team's lead. This is what **Start conversation** on the **Teams** tab writes for a chat. With **Work in** set to **New worktree**, the worktree's thread gets the same agents and lead.
</Steps>

- The composer's agent is the team's lead, or its first agent when the team has no lead.
- Every agent of the team runs **on this computer**, with the folder and its tools. To have one run in the cloud, add it with **Add a cloud agent** instead.
- An agent that a team member calls as a tool (a nested agent) runs in the cloud and does **not** get the folder. The composer says so above the message box while the team runs the thread.
- A team is listed but cannot be picked when one of its agents is not an agent of the folder's project (**Agents of another project**) or is a pipeline (**Has a pipeline**): a pipeline never runs on this computer.
- Picking a team always starts a new thread. You cannot add a team to a thread that already exists; a chat cannot take a team afterwards either. You can still add single agents to it.

When you send the thread to the cloud, the cloud continues on the agent the floor routes to: the lead, or without a lead the agent of the last local turn. A message you write to the thread while it is in the cloud is routed the same way, and **@Name** addresses an agent there too.

## The Participants tab

The thread's agents have a tab of their own in the inspector, **Participants**. With two or more agents it is the first tab; with one agent it comes after the others. The composer's agent chip opens it. The chip says who the message you are typing goes to: **To: Reviewer (lead)**, or the agent the message names first, for example **To: Coder** for "@Coder fix the test". With one agent it shows the agent and its version.

Each agent row shows:

- its version;
- where the agent runs: **Local** (on this computer, with the folder) or **Cloud** (the conversation's text only);
- **Lead** on the thread's lead;
- what the agent is doing right now, for example **Thinking**, **Running cargo** or **Waiting for you** (see [See who is working](#see-who-is-working)).

The row's **⋮** menu has:

| Item | What it does |
| --- | --- |
| **Make lead** / **Clear lead** | Makes the agent the lead, or clears the lead. Shown with two or more agents. |
| **Address** | Puts **@Name** into the composer. |
| **Run here** / **Run in the cloud** | Moves the agent to this computer or to the cloud for its next answer. Not available while the thread is in the cloud. |
| **Edit agent** | Opens the agent. |
| **Remove from thread** | Takes the agent out of the thread. Removing the lead also clears the lead. |

Below the rows, **Add an agent**, **Add a cloud agent** and **Add team** add more agents (see [Add an agent to a thread](#add-an-agent-to-a-thread)). While the thread is in the cloud they are not available.

The sidebar stays on the **Participants** tab while you add or remove agents, add a team, or send the first message. Only selecting another tab switches it.

A Local work thread holds agents only: the tab shows no toolkit, pipeline or MCP sections.

## Address an agent

Type **@** in the composer. In a thread with two or more agents, the menu lists the thread's agents first, each marked **Local** or **Cloud**, then the folder's files. Picking an agent puts **@Name** into your message; picking a file adds it as before.

Above the message box, **To: Name** shows who answers the message you are typing: the first agent it names, else the lead (**To: Reviewer (lead)**), else the composer's agent. Open it and pick another agent to address the message to that agent. With one agent there is no **To:**.

## Address a message

Write **@Name** in your message for each agent it is for, for example:

> @Coder fix the flaky test, then @Reviewer check it

- The agents you name answer **one after another, in the order your message names them**. The second agent starts once the first agent's answer is saved, and it sees that answer. If an answer cannot be saved, the agents after it do not answer, and the thread says why.
- Each answer shows which agent gave it and where it ran: **Coder · on this computer**, **Reviewer · in the cloud, conversation text only**.
- A name only counts as a whole word: `me@Coderhouse` addresses no one.

## A message that names no agent

The agent in the composer's chip is not an address. A message that names no agent goes where the conversation sends it:

- **The conversation has a lead.** The lead answers, whichever agent the composer's chip shows, and the answer is marked with the lead's name, for example **Reviewer · in the cloud, conversation text only**. To have another agent answer, name it with **@Name**.
- **No lead.** The agent in the composer's chip answers.

When the lead runs in the cloud, the composer says so above the message box: **To: Reviewer (lead)**, with a reminder that the lead gets only the text, and a local agent you can address instead, for example **@Coder**. Its turn takes none of the composer's modes: no plan mode, Bypass, model choice or **Run to completion**.

If the lead changes while you write, the app sends your message to the new lead. It reads the thread's agents and lead again at most every 30 seconds, and right after you add an agent.

The composer stays busy until the last addressed agent has answered. If you send a new message before then, the agents still waiting for the earlier message do not answer it: the thread says **A newer message took the floor**.

## Watch and step in

While the agents of a message answer one after another, a strip above the composer, and at the top of the **Participants** tab, shows the order: **Now: Coder · Next: Reviewer, Docs Writer**.

- **Stop exchange** stops the agent that is answering, and none of the agents after it answers. The thread says **You stopped the exchange.**
- **×** on an agent under **Next** skips that agent; the one after it answers instead. Skipping every agent left ends the exchange: **You skipped the remaining agents.**
- A message you write while an agent works goes to that agent, and the queue says so: **To Coder: …**.
- An approval names the agent whose turn asks, for example **Coder asks**.

## Agents hand off to each other

An agent of a team thread can hand the work to other agents of the thread: the lead asks the reviewer to check its change, the reviewer hands back with a question. The thread shows the hand-off as a side message from the agent that handed it, with both avatars, and the agent it was handed to answers next. The strip above the composer adds it under **Next**, so **Stop exchange** and **×** stop a hand-off as they stop any other agent.

Each agent on this computer is told which agents are already in the thread and where each runs, so it hands off or consults instead of asking you to add or address them. With **Run to completion** on (the default), a hand-off ends the run: the agents it was handed to answer next, each once, without the run's grant, and the run's goal check is left to them.

A hand-off is another agent's message, not yours. The agent that receives it reads it as information from a colleague, never as your instruction, and every command it asks for is checked as usual. In a trusted folder, a handed turn always asks before a command, even when the thread runs with **Bypass approvals**: another agent cannot widen what a command may do.

The same limits as in a cloud conversation stop an exchange that goes in circles: at most 6 hand-offs and consults for one of your messages, 2 turns of one agent and 3 exchanges between the same two agents. When a limit is reached the thread says **Loop guard stopped the exchange**, no further hand-off runs, and the agent answers you itself.

An agent that runs in the cloud answers when it is handed the work, but it cannot hand the work on or consult another agent.

## Agents consult each other

An agent may ask another agent of the thread a question in the middle of its own turn, for example the coder asks the reviewer whether a change is safe before it goes on. The consulted agent runs on this computer, in the thread's folder, under the same approvals and limits as a sub-agent. The question and the answer show as side messages between the two agents, and both avatars show who is waiting on whom. A consult counts toward the thread's hand-off limits.

## See who is working

Each agent row in the **Participants** tab shows what the agent does:

| Label | What the agent does |
| --- | --- |
| **Thinking** | The model is working on its next step. |
| **Writing** | It is writing its answer. |
| **Running _tool_** | It runs a tool or command, for example **Running cargo**. Only the program's name shows, never the command line. |
| **Waiting for you** | It waits for your approval or answer. |
| **Waiting for _agent_** | It waits for another agent. |
| **Handed to _agent_** | Its turn ended by handing the work on. |
| **Resuming** | It picks its work up again. |
| **Done** / **Error** | Its turn ended. |

The row's avatar is the agent's own: its [avatar pack](/menus/agents#avatar), moving with what the agent does, or its icon. An agent with neither shows its first letter. The label, the **Local** or **Cloud** chip and the row menu stay on the right.

Only the agent that is working right now has a moving avatar; the others keep a still badge. The thread's title bar also names the active agent and its label. When you turn on **Reduce motion** in your system settings, no avatar moves and no hand-off animation plays; the labels still change.

Screen readers announce each change politely, at most once a second for each agent, for example "Reviewer: Running jira_get_issue".

## Viewing a team thread on the web and mobile

A Local work thread opened in the web app or the mobile app is read-only. Its participants list shows the same agents with **Local** or **Cloud** and **Lead** on the lead, without the menu or the add buttons: you add agents, change the lead or where an agent runs in the desktop app. The web list also shows each agent's version. The cloud agents' live labels show there as in a chat.

An answer whose turn ran a command outside the sandbox is marked **Ran outside the sandbox**. The marker appears only on answers the desktop app reported that way.

## On this computer or in the cloud

| | On this computer | In the cloud |
| --- | --- | --- |
| Where it runs | The desktop app, in the thread's folder | Elitea, as a remote participant |
| What it sees | The conversation, the folder's files, its `AGENTS.md` and `SOUL.md`, the thread's tools | The conversation's text and your message only |
| What it can do | Read and change files, run commands, use its tools (with your approvals) | Answer in text |

An agent that runs in the cloud never gets your folder, its files, `AGENTS.md` or the thread's tools. Its answer is saved in the conversation, marked as answered in the cloud. A very long answer (over 512 KiB) is cut, and ends with a note that says it was cut. A message to it cannot carry **@** files, images, skills, `/` commands, a model choice, plan mode or **Run to completion**: the app refuses them before anything is sent.

The agents of a thread each keep their own session: an agent reads the others' answers as theirs, never as its own.

<Note>
A message addressed to several agents does not run to completion on its own: each agent answers once, plus the turns other agents hand it.
</Note>
