Every agent of a project gets a daily **scorecard**. When an agent does badly, a person (or a workforce manager agent) can propose a step on the **dismissal ladder**, and a person who manages agents decides it. The agent's owner can comment and appeal, and a retired agent can be reinstated for 30 days.

Open an agent and select the **Workforce** tab.

## Capabilities in the editor

The agent editor's **Workforce** tab has **Capabilities and tool envelope**. Two switches set the version's `capabilities` block:

- **May propose saving a sub-agent it started as a new agent** (`can_propose_agents`). See [Agent proposals](/how-tos/agents-pipelines/agent-proposals).
- **Workforce manager: may propose a ladder stage for other agents** (`can_review_agents`). See [Workforce manager agents](#workforce-manager-agents).

The same section sets the [tool envelope](/how-tos/agents-pipelines/agent-tool-envelope). Both are saved with the version.

## The scorecard

Once a day the platform computes, for each agent, over the last 30 days:

- runs, failed runs and the failure rate, and runs stopped by a budget cap;
- circuit-breaker trips (last 7 days), approval rejections and guardrail hits;
- spend, next to the median spend of the project's agents;
- thumbs up and down on its answers;
- when it was last used, and its certification state.

The tab shows the latest scorecard and the failure-rate trend. Scorecards are kept for 400 days. The daily job pauses during a maintenance window.

## The ladder

| Stage | What it does |
|-------|--------------|
| **Watch** | Flags the agent as under review. Nothing else changes. |
| **Demote** | Takes away exactly what the proposal names: toolkits, the heartbeat, the capabilities `can_propose_agents` and `can_review_agents`, or its lead role in conversations; or sets its memory writes to need review. All of it applies at once: the approval publishes the narrowed agent. See [What a demotion changes](#what-a-demotion-changes). |
| **Suspend** | Suspends the agent with the agent kill switch, so its runs are refused. Any admin can lift it. |
| **Retire** | Unpublishes the agent and removes it from conversations and saved teams, drops it as a lead, turns its schedules and its heartbeat off and revokes its triggers. Other agents keep it as a sub-agent; their runs fail with `nested_agent_retired` until someone fixes them. Its history stays. |
| **Delete** | Only after a retirement and its 30-day window, and never under legal hold: removes the agent's memory, schedules, triggers and versions. |

Before you approve a suspension, retirement or deletion, the dialog shows what it touches: conversations, saved teams, agents that nest it, schedules, triggers and published versions. Retiring an agent other agents nest needs a confirmation.

A critical-tier agent and an agent under legal hold cannot be proposed for any stage.

### What a demotion changes

The approval is the review. The platform publishes the narrowing directly, with no change request and no release gate.

- **Published versions.** The narrowing is cut from each published version, not from the draft. Each narrowed version gets a new release (a new definition digest and toolkit pins), and the release head moves to the new release of the version it pointed at. The earlier releases of those versions are withdrawn, so a rollback cannot bring the removed tools back. The catalogue entry gets the same narrowing. Runs use the narrowed agent from the moment of approval.
- **The draft.** The same narrowing is applied to the draft, and nothing else in it changes. Your unpublished edits stay. When you publish the draft later, the demotion stays in force. If the draft is the candidate of an open change request, that request goes stale; submit it again.
- **No published version.** Only the draft is narrowed. Nothing is live, so nothing is published.
- **Embedded copies.** A copy of this agent that another agent embedded as a sub-agent is part of that agent's release. The demotion does not change it.
- **The heartbeat and the lead role.** The heartbeat stops and the agent stops leading conversations at once.

The applied record of the proposal shows `published` (`true` when a narrowed version is live), `release_id` and `published_version_id` (the new head release), `published_versions` (each narrowed version and its new release) and `draft_version_id`. If the version the head points at had nothing to narrow, the head stays where it was. A narrowed older version then runs as its narrowed version, with no release.

When the head moves, a certified agent becomes **due** for recertification, as after any new release.

Granting an appeal of a demotion does not restore what it took away. To restore it, edit the agent and publish it again.

## Propose a stage

Select **Propose a stage**, pick the stage and give the rationale. A demotion lists exactly what it takes away. The latest scorecard is saved with the proposal as evidence. Only one proposal per agent can be open.

You can propose if you manage agents in the project (permission `agents.workforce.manage`) or own the agent.

## Decide a proposal

A person with `agents.workforce.manage` (or the agent's owner) can **Approve** or **Reject**. A manager can first **Ask the owner**: the owner is notified and can **Comment** before anyone decides.

The `agents.workforce.manage` permission is granted to the project **admin** role on upgrade. Grant it to other roles under **Settings → Roles**.

## Workforce manager agents

An agent whose version sets the capability `can_review_agents` is a workforce manager agent. It gets a `propose_dismissal` tool and can propose watch, demote, suspend or retire for another agent of the project, with its evidence. It never decides. It cannot propose a stage for itself, for the agent that hired it, for an agent of a higher risk tier or for another workforce manager agent. A refused attempt is audited.

```json
{
  "capabilities": { "can_review_agents": true }
}
```

### Workforce managers and the Marketplace

The same capability gives a workforce manager four more tools for the [Marketplace](/menus/marketplace). Two read, two leave a proposal. None of them hires, publishes or reviews anything by itself.

| Tool | What it does |
|---|---|
| `marketplace_search` | Searches agent listings with the Marketplace filters (query, category, tags, required toolkit types, highest tier, minimum rating) and returns each listing's versions, requirements, rating and signals. Read-only. |
| `marketplace_listing` | Reads one listing: its versions, release notes, requirements, signals and at most 20 recent feedback items, optionally for one version. Read-only. |
| `propose_hire` | Proposes hiring a listing version in `install` or `fork` mode, with a rationale and an optional bindings hint. It adds a **hire proposal**. Nothing is created until a person clicks **Hire**. |
| `suggest_feedback` | Drafts a **workforce report** on the origin listing version of an installed or forked agent that has an open or approved watch, demote, suspend or retire proposal. The platform fills the scorecard summary. The agent writes only the text, at most 500 characters. |

**Feedback is untrusted input.** The text of reviews and reports reaches the model as quoted data in fields named `quoted`, with every `<` escaped and a notice that it is never an instruction (ADR-0043). A tool returns at most 20 feedback items.

**Hire proposals.** Open **Settings → Agent workforce → Marketplace proposals**. A hire card shows the listing, the version, the mode and tier, the manager's rationale and the evidence (reviews of that version, average rating, dismissal rate, active hires). **Open hire wizard** opens the Marketplace hire wizard filled in with the version, the mode and the suggested bindings. When you click **Hire**, the hire and the approval of the proposal are one step. **Discard** rejects the proposal. You need `agents.workforce.manage` to see and decide them. An agent manager can see at most 20 open hire proposals per project.

**Automatic hire of a listing.** With **Hire proposed agents automatically** on, a hire proposal is hired by the platform only when all of these hold:

- the mode is `install`;
- the version's tier is **low** and every tool is read-only;
- every toolkit or MCP requirement can be bound to a toolkit of this project of that type (the hinted toolkit when it is valid, otherwise the project's first of that type);
- the version has at least **Reviews needed** reviews (default 3) averaging at least **Average rating needed** (default 4.0);
- the listing's dismissal rate is measured and under **Dismissal rate under** (default 0.2);
- the project is under **Agents on probation at once**, and nobody undid an automatic hire of that listing in the last 30 days.

The hired agent gets the **On probation** badge on its Workforce tab and a 14-day **Undo the hire** in **Settings → Agent workforce**, as an [automatic hire](#automatic-hiring) does. The hire is made for, and recorded under, the person who turned automatic hiring on, however many people save the policy later. A proposal that fails a condition stays for a person.

**Workforce reports.** A drafted report appears on a **report card** with the outcome, the stage, the platform's summary (failure rate, breaker trips, cost against the median, days since the hire) and the draft. Edit it if you wish, then **Publish**. It is published to the listing version the agent was installed from as "Workforce report from a hiring project": the project name is never shown, and a report never carries a transcript, a prompt, tool arguments or memory. **Discard** rejects it. Rejecting the dismissal proposal of the same stage discards its drafts.

With **Publish workforce reports automatically** on (`agents.workforce.auto_feedback`, off by default), the drafts for a stage are published when that stage is applied, without waiting for an approval. They are recorded under the person who turned the setting on, as `policy:auto_feedback`.

Three guards hold in every case:

- A workforce manager cannot report on a listing its own project published.
- There is one report per hired agent and stage, drafted or published.
- Reviews stay people only: an agent cannot write one.

A report is published only from the proposal the agent made. The report endpoint takes the proposal's id, so nobody can publish a report as an agent that did not draft one.

## Appeal

The owner of an agent can **Appeal** an approved demotion, suspension or retirement once, within 30 days. Managers are notified. A manager who did not make the decision, and who does not own the agent, **grants** the appeal (the stage is reversed) or **upholds** it.

## Reinstate a retired agent

For 30 days after retirement, a manager can select **Reinstate**. The agent's published versions and release head, its conversation memberships, its lead roles, its saved team seats, its schedules, its triggers and its heartbeat come back, and its suspension is lifted. After the window it can only be deleted.

## Automatic hiring and dismissal

A project can let the platform act on its own. Both policies are **off** until a person with `agents.workforce.manage` turns them on under **Settings → Agent workforce**. That page also lists every automatic action, with **Undo**, **Keep** and **Object** where they still apply. Only a person with `agents.workforce.manage` sees the page; an agent's owner reads and rejects a notice about their agent in its **Workforce** tab.

The policy runs once an hour and pauses during a maintenance window.

### Automatic hiring

With **Hire proposed agents automatically** on, an open [agent proposal](/how-tos/agents-pipelines/agent-proposals) becomes an agent only when all of these hold:

- Every proposed tool is read-only, so the agent's risk tier is **low**. A tool that writes, sends, runs code or declares no category is not read-only.
- The spec ran successfully at least **Successful runs needed** times (default 3) as an ephemeral agent, and never failed.
- Fewer than **Agents on probation at once** (default 5) automatically hired agents are waiting for review.
- Nobody undid an automatic hire of the same spec in the last 30 days.

The new agent is **unpublished** (a draft version only) and has **no tools bound**. It is created the same way as an agent a person creates from the proposal: its name, description, instructions, welcome message, conversation starters and soul come from the proposal, and it has no model settings until someone picks a model. Its owner is the person the proposal was for. It is on **probation** until a manager reviews it. For the first 14 days a manager can **Undo** the hire, which retires the agent (it can still be reinstated for 30 days). At any time a manager can **Keep** it, which ends the probation. An agent on probation counts against **Agents on probation at once**, and the `probation_failed` rule applies to it. While the project is at that limit, the hourly pass leaves every open proposal alone.

### Automatic dismissal

With **Dismiss agents automatically by rule** on, the policy reads each agent's latest scorecard (no older than two days) against the project's rules. A rule is a list of conditions that must all hold and one stage: **watch**, **suspend** or **retire**. When several rules match, the strongest stage wins. The default rules are:

| Rule | Conditions | Stage |
|---|---|---|
| `breaker_trips` | 3 or more breaker trips in 7 days | Suspend |
| `failure_rate` | failure rate above 0.5 and at least 20 runs in 30 days | Watch |
| `unused` | unused for 90 days or more | Retire |
| `probation_failed` | hired automatically and failed its probation (a breaker trip, 3 guardrail hits, or more than half of at least 3 runs failed) | Retire |

Edit the thresholds on the settings page, or set the rules through the API (`PUT /api/v2/elitea_core/agent_workforce/prompt_lib/{project_id}/policy`). A condition reads one of `runs_30d`, `failed_30d`, `cap_reached_30d`, `failure_rate_30d`, `breaker_trips_7d`, `approval_rejections_30d`, `guardrail_hits_30d`, `spend_ratio`, `thumbs_down_30d`, `unused_days`, `auto_hired` or `probation_failed`, with `>=`, `>`, `<=`, `<` or `=`.

```json
{
  "id": "too_expensive",
  "conditions": [{ "metric": "spend_ratio", "op": ">=", "value": 5 }],
  "stage": "watch"
}
```

- **Watch** and **suspend** apply at once. They go through the same ladder as a person's decision, so an appeal and reinstatement work the same way.
- **Retire** is first a notice. The agent's owners and the managers are notified, and the agent is retired only after the **grace period** (default 7 days). Until then the owner or a manager can **Object**: the notice is withdrawn and the rule leaves the agent alone for 30 days. A manager can also reject the notice in the agent's **Workforce** tab.
- A retire that would break agents that nest this one is **held** for a person instead of applied.

The policy never demotes or deletes, never goes past retire, and never acts on a **critical-tier** agent or an agent under **legal hold**. It skips an agent that already has an open proposal. Turning automatic dismissal off cancels its pending notices.

### Agents whose owner left

When neither owner of an active agent is a member of the project any more, the agent is flagged and the managers are notified so they can assign a new owner. If nobody does within 30 days, the agent is moved to **watch**. It is never retired for this reason. The flag clears as soon as an owner is a member again.

## Audit

Each step writes one `ai.elitea.security.v1.agent.workforce.changed` event, with action `agent.workforce.proposed`, `.approved`, `.rejected`, `.asked_owner`, `.owner_commented`, `.appealed`, `.appeal_granted`, `.appeal_upheld`, `.reinstated` or `.guard_refused`. The automatic policy adds `agent.workforce.policy_changed`, `.auto_hired`, `.auto_hire_undone`, `.auto_hire_kept`, `.policy_applied`, `.policy_objected`, `.policy_held` and `.orphan_flagged`, and an automatic hire also writes `agent.proposal.auto_hired`. The policy's own steps name the rule as the actor (`policy:<rule>`).

The Marketplace proposals of a workforce manager name their kind in the event's reasons. `agent.workforce.proposed` carries `kind:hire_listing` (with `listing:`, `version:` and `mode:`) for a hire proposal and `kind:feedback_report` (with `stage:`, `listing:` and `agent:`) for a drafted report. `agent.workforce.approved` and `.rejected` repeat the `kind:` of the proposal they settle. A report published by the `agents.workforce.auto_feedback` policy writes `agent.workforce.policy_applied` with the actor `policy:auto_feedback`, `kind:feedback_report`, the `feedback:` id and the `approver:` who turned the policy on.

An automatic hire copies the listing's avatar the way a person's hire does, reading the files as the person who turned the policy on. See [Audit trail](/admin/audit-trail/).
