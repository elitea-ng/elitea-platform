---
title: "Sub-agent profiles, briefs and lanes"
description: "Give a sub-agent a name and a role with spawn_agent's profile, pass it what you can see with a context brief, watch it work in its lane, and find each spawn in the run's record."
---

An agent with the `subagents` internal tool starts a sub-agent with `spawn_agent`. A sub-agent has its own fresh context: it sees only its task. Two optional arguments shape it:

- `profile` names the sub-agent and gives it a role.
- `context` is a **brief**: parts of the conversation, files and notes that the agent passes to it.

```json
{
  "task": "Review the migration plan and list the risks.",
  "profile": {
    "display_name": "Risk reviewer",
    "soul": "You are a careful reviewer. Write short, direct findings.",
    "tools": ["github/get_issue"],
    "model": "inherit",
    "avatar": "default:owl"
  },
  "context": {
    "excerpts": [{"message_id": "m-3f9a0c12be", "quote": "We ship on Friday after the review."}],
    "attachments": ["att-0011aabb"],
    "facts": ["The staging cluster runs Kubernetes 1.33."],
    "memory_entries": ["42·k7f2m6q3xz"]
  }
}
```

## The profile

| Key | What it does |
| --- | --- |
| `display_name` | The name shown for the sub-agent, at most 60 characters. It is the label when `label` is not set. |
| `soul` | A short role and style, at most 2 KiB. It replaces the default role text. The safety sentence stays: a soul never widens what the sub-agent may do. |
| `tools` | Only these of the agent's tools, as `toolkit/tool` or `toolkit/*`. See [Sub-agent tools](/how-tos/agents-pipelines/agent-tool-envelope#sub-agent-tools). A tool that writes still needs the agent's `subagent_tools`. |
| `model` | `inherit` (the default): the sub-agent uses the model of the agent that starts it. Or the name of another model of the project catalogue that the agent may use, at most 256 bytes. See [The model](#the-model). |
| `avatar` | An avatar key, at most 128 bytes. The platform stores it. |

An unknown key or a value out of its bounds refuses the call with `invalid_arguments`.

### The model

When an agent has the `subagents` internal tool, Main freezes the other models of the project catalogue into the run when the run starts: the models of the project and the shared models of the platform, with their limits. A sub-agent that names one of them runs on it with that model's context window, output limit and thinking control. Its calls go through the same budget gate and egress rules as the agent's own calls, and its tokens count against the same run.

A name that is not in the frozen list refuses the call with `SUBAGENT_MODEL_NOT_ALLOWED`. No sub-agent starts. A model added to the catalogue after the run started is not in the list.

The desktop app accepts `inherit` only. It refuses any other name with `SUBAGENT_MODEL_NOT_ALLOWED`.

The profile digest includes the model, so a sub-agent on another model has a different digest. A sub-agent started by a sub-agent uses its parent's model, unless its own profile names one.

## How deep sub-agents go

The platform administrator sets **Sub-Agent Depth** under **Configuration › Agent tools** (see [Agent tools](/admin/enterprise-controls/runtime-safety/#agent-tools)):

- **1** (the default): a sub-agent does not get the four sub-agent tools. A call from a sub-agent is refused with `subagent_depth_exceeded`.
- **2**: a sub-agent gets the four tools too, and can start sub-agents of its own. Those do not get the tools and cannot start more.

At depth 2 these rules apply:

- **One budget.** All sub-agents of a run, at every level, share the run's limits: at most 12 started in a turn. One agent or sub-agent runs at most 4 sub-agents at a time.
- **One delegation depth.** Each level counts one level of the run's delegation depth. When the maximum delegation depth is reached, a spawn is refused with `DELEGATION_DEPTH_EXCEEDED`.
- **Tools only narrow.** A sub-agent's sub-agent gets only tools that its parent got. A `profile.tools` entry that its parent did not get refuses the call with `SUBAGENT_TOOL_NOT_GRANTED`. A tool that writes still needs the agent's `subagent_tools`.
- **Own children only.** A sub-agent manages only the sub-agents it started.

The record keeps each spawn with its own row. A sub-agent's ordinal counts across the run, so each spawn of a run has its own ordinal. The row also keeps the spawn's depth (1 or 2) and, at depth 2, the id of the sub-agent that started it.

## The brief

A brief may contain at most 20 entries of each kind. The agent can pass only what it can see itself. The platform checks each reference before the sub-agent starts:

| Entry | The check | Refusal |
| --- | --- | --- |
| `excerpts` | `quote` is an exact part of the text of the message `message_id`, as the agent reads it. A run of spaces or line breaks counts as one space. | `BRIEF_EXCERPT_NOT_VISIBLE` |
| `attachments` | The id is one of this turn's attachments. | `BRIEF_ATTACHMENT_NOT_READABLE` |
| `memory_entries` | The agent was given this entry in the same turn: at the start of the turn, or from `recall`. It names the entry as `N·TAG` with this turn's tag (see [Memory entry ids](#memory-entry-ids)). | `BRIEF_MEMORY_NOT_RECALLED` |
| `facts` | None: each fact is the agent's own words, at most 500 characters. | |

### Message ids for excerpts

In a cloud run with the sub-agent tools, the agent sees a short id before each message it can quote:

```text
[message m-3f9a0c12be]
We ship on Friday after the review.
```

The agent can quote the person's messages, other participants' messages in its view (see [What an agent sees of a conversation](/how-tos/agents-pipelines/agent-context-view/)), and the current message. Its own earlier answers have no id, and it cannot quote them. The id is `m-` and 10 hex digits. It comes from the message's id only, so it is the same on every turn and prompt caching still works. If a message's own text contains `[message`, the agent sees `&#91;message` there instead, so a message cannot fake the id of another message. This also covers a fullwidth bracket and invisible or non-breaking spaces after the bracket. A quote is checked against the text after the id line, as the agent reads it. The text of a file attached to the current message is not part of that message, so the agent cannot quote it as an excerpt. Pass the file in `attachments` instead.

The sub-agent record keeps the chat message id of each quoted message, not the short id.

A regenerated answer, a continued turn, or an addressed agent answering a message another agent answered first has no id on its current message. Quote the current message on a new turn.

### Memory entry ids

An agent with [agent memory](/how-tos/agents-pipelines/agent-memory/) is given its most relevant notes at the start of a turn. Each note starts with its id:

```text
- [memory 42·k7f2m6q3xz, preference, pinned] The team wants short reports.
```

The id is the note's number, a middle dot (`·`), and a tag of 10 letters and digits that the platform derives for the conversation from a secret key. The agent names a note in `memory_entries` exactly as its line shows it, `42·k7f2m6q3xz`, or by the `memory_ref` that `recall` returned for it in the same turn (`recall` shows the same tag). A bare number such as `42`, or a mark with another tag, is refused with `BRIEF_MEMORY_NOT_RECALLED`. The platform sends the sub-agent the note as it is stored, not the text the agent wrote in the call. The ids of the notes given at the start of the turn, and their tag, travel with the run, so the check does not depend on the prompt text. A note about a person is given only while that person is in the conversation, so the agent can pass it on only then.

The tag is what makes a real mark impossible to type. The agent's instructions, its skills and the project context are sent next to the notes and are never rewritten, so a prompt copied from somewhere else can still contain a line such as `[memory 42, fact] ...`. Nobody can know a conversation's tag in advance, so such a line cannot point a brief at a real note. If a note's text, a person's name, a personal memory or the project context contains `[memory`, the agent also sees `&#91;memory` there instead.

The tag stays the same across a conversation's turns, so the notes block keeps its text and prompt caching keeps working. It changes when the conversation's next turn is served by another instance or after a restart, which costs one cache miss.

A regenerated or continued answer is given no notes at the start of the turn. It can pass on only notes that `recall` returns. An agent that wakes when its sub-agents finish keeps the notes its turn started with, and their tag. A note the agent deletes with `forget` can no longer be passed on in the same turn.

A refusal is a tool result that the model reads. No sub-agent starts. The sub-agent gets the checked brief before its task, marked as information and not instructions. The brief counts against the sub-agent's token budget.

### In the desktop app

A sub-agent of a local turn in the desktop app takes the same `profile`: its display name is the lane's name in the transcript, its soul replaces the role text, and `model` can only be `inherit`. It still only reads, unless it has its own checkout (`isolation: "worktree"`). `profile.tools` can only narrow it to some of its read-only tools, because the desktop app has no `subagent_tools` grant. The desktop app checks a brief against what the agent saw:

| Entry | What the desktop app accepts |
| --- | --- |
| `excerpts` | A quote of a message the agent read in its last model request. These messages carry a `[message m-…]` line: the person's messages, other participants' messages, and the current message. The id is the same as in a cloud run, and the same check applies. A message that compaction took out of the request cannot be quoted. |
| `attachments` | An image attached to the current message. Each image is shown to the agent as `[Attachment att-…: "name"]` after the message. The sub-agent gets the image's name only, because it cannot view images. |
| `memory_entries` | None: the desktop app has no `recall` tool, so it refuses every memory entry with `BRIEF_MEMORY_NOT_RECALLED`. Pass what you need as a fact. |
| `facts` | Accepted. |

The desktop app writes no `ephemeral_agents` row for a local sub-agent. The turn's thread history keeps the lane's start, with the display name, the avatar key and the profile and brief digests and references. Like the cloud record, it never keeps the soul, a quote or a fact. A cloud agent in a desktop thread runs in the cloud, so the cloud checks its briefs.

## Watch a sub-agent work

In a cloud run, each sub-agent shows as a temporary participant under the `spawn_agent` call that started it. The row shows the sub-agent's `display_name` (or **Sub-agent 1**, **Sub-agent 2** and so on), a dashed avatar ring, a **Temporary** badge and its status: running, done, failed, out of budget or stopped. While the sub-agent runs, the row is open and shows its own tool calls, each with a short summary of its arguments and result, and its text. When it ends, the row folds. Open the row to see its final answer, its steps and its tokens.

The row is the same after you reload the conversation. The answer keeps each sub-agent's lane, so the lane does not depend on the live stream.

The lane is a summary, not a transcript:

- The platform masks secret arguments (keys such as `api_key`, `token` and `password`) before it sends a tool call.
- A tool call's arguments are one line of at most 160 characters. Its result is at most 240 characters, a text at most 600 characters and a final answer at most 2,000 characters.
- One sub-agent run shows at most 48 tool calls and texts. A sub-agent that `send_input` continues runs again, and the lane keeps at most 96 in total.
- Every text is the model's or a tool's output. The apps show it as plain text.

If the run ends while a sub-agent still runs, the sub-agent's row shows **Stopped**.

The web app, the desktop app and the mobile app show the lane. At **Sub-Agent Depth** 2, a grandchild's lane shows nested under its parent's own lane on the web and desktop apps. The mobile app has no nested view: each sub-agent's tool calls and its final answer show in the answer's tool card, under the sub-agent's name and **temporary**, a grandchild's steps following its parent's under both names.

A local turn's sub-agents in the desktop app have the same lane, with the profile's display name and, when the profile names an avatar, an avatar. They have no **Temporary** badge or dashed avatar ring: they run on your computer, not as cloud participants. The lane in the chat answer and the lane in the desktop transcript are the same control, so both show the steps and tokens of a sub-agent that has ended.

## The record

Each spawn of a cloud run writes one row to `elitea_runtime.ephemeral_agents`. The row keeps:

- the run, its project, its conversation and the agent that started the sub-agent;
- the sub-agent's id, label, display name and avatar key;
- its depth: 1 for a sub-agent of the run's agent, 2 for a sub-agent that another sub-agent started, with that sub-agent's id;
- a digest of the profile, and a digest of the brief with the ids it named (message ids, attachment ids, memory entry ids and the number of facts);
- the status, steps, tokens and error code, and when it started and ended.

The row never keeps the soul, a quote, a fact or the task. The run's step records keep the `spawn_agent` call itself.

The rows follow the retention of the run's step records: when the step record policy deletes a run, it deletes the run's sub-agent rows too. If `send_input` continues a sub-agent and the run ends before it answers again, its row shows `cancelled`.
