---
title: "Test toolkit tools"
description: "Run a single tool against a configured toolkit to verify credentials and behavior before you attach it to an agent."
---

Before attaching a toolkit to an agent or a chat, you can run one of its tools directly to confirm the credential works and the tool returns what you expect.

## Run a test

<Steps>
1. Open a saved toolkit's configuration page (unsaved changes disable testing — save first).
2. Open its **Test tools** pane.
3. Pick a tool from the list and fill in its arguments.
4. Choose a model if the tool needs one, and run it.
5. Read the result in the transcript alongside the run.
</Steps>

<Screenshot id="test-tools-pane-result" alt="Test tools pane on a toolkit showing a tool argument form and a run result" />

<Warning>
**Index Data can't be tested here.** The Go backend routes it through a separate, asynchronous endpoint owned by the toolkit's [Indexes tab](/how-tos/indexing/using-indexes-tab-interface); running it from Test tools returns that route's own refusal instead of an actual index run.
</Warning>

<Note>
There's no history of individual **Test tools** runs to come back to — a run's result only exists in this session's transcript. The toolkit's own **History** tab (the clock icon on its Configuration tab) is a different, related record: every past *conversation* that attached this toolkit, with its recorded trace of tool calls and thinking steps.
</Note>

## What testing verifies

A successful run confirms the credential authenticates and the tool's arguments are valid for your instance of the external service — useful before wiring the toolkit into an agent where a failure is harder to diagnose. A failing run typically means a credential problem, a permission problem on the external service, or an argument the service rejects.

## Run history

The clock icon on a saved toolkit's Configuration tab opens **History**: every past conversation that attached this toolkit, newest first, with its date, a derived duration, and its message count. Select a run to see its recorded trace — the tool calls the runtime logged for that conversation. A toolkit with no past conversations shows an empty state rather than a blank panel.

## Choosing which tool to test first

If a toolkit exposes many tools, start with the simplest read-only one (a list or search operation) rather than something that writes to the external system. That confirms the credential and connection work before you risk a test run creating or modifying real data in Jira, GitHub, or whichever service the toolkit reaches. Once a read tool succeeds, move on to testing the write tools you actually plan to use.
