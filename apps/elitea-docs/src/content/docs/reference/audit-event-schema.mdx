Every audit event Elitea exports, whatever its source and whichever transport carries it, is one JSON document in the `elitea.audit.v1` envelope. The machine-readable definition is a JSON Schema (draft 2020-12), `libs/jsonschema/audit/v1/event.schema.json` in the platform repository. Field names follow [OCSF](https://schema.ocsf.io) where a class fits.

How to turn the export on is in [Post-install configuration](/deployment/configuration#export-audit-evidence-to-a-siem); what it guarantees is in [Audit trail](/admin/audit-trail#export-to-your-siem).

## Versioning

`schema` is always `elitea.audit.v1`. Adding an optional field is not a version change. Renaming, removing or retyping a field, or making one required, is a new version (`elitea.audit.v2`); a consumer should quarantine a version it does not recognise rather than guess. A field with no value is omitted, never `null`, except `tenant.project_id`.

**A receiver ignores fields it does not know.** The schema stays strict for producers so that a producer typo fails CI; a receiver that encounters a field it does not know ignores it rather than rejecting the event.

## The envelope

| Field | Type | Meaning |
|---|---|---|
| `schema` | string | `elitea.audit.v1`. |
| `event_id` | string | Stable identifier. Delivery is at least once, so **deduplicate on it**. A security audit event keeps its UUID; an audit trail row has a name-based UUID derived from its row id, so a replay carries the same id. |
| `time` | RFC 3339 string | When the audited operation happened (UTC). |
| `source` | enum | `security_audit` (the security audit outbox), `admin_audit` (`centry.audit_events`, the Audit Trail), `run_step` (the [step records](/admin/enterprise-controls/audit-evidence-and-retention#run-step-records) of agent runs), `security_signal` (the security signal ledger, ADR-0058). `approval` and `suspension` are reserved for evidence added later. |
| `event_type` | string | The producer's type: a CloudEvents type such as `ai.elitea.security.v1.decision`, or `api`, `socketio`, `rpc`, `agent`, `tool`, `llm`, `schedule`, `admin_task` for the Audit Trail, or `security_signal.<type>` for the signal stream. `chain.checkpoint` is the event_type of a chain checkpoint. |
| `delivery_seq` | integer, optional | The sink's delivery order: one monotonic, gap-free value per sink across all partitions. Absent on an event that has not been stamped by the relay yet. |
| `ocsf` | object, optional | `class_uid` and `category_uid` when an OCSF class fits: 3003 Authorize Session, 3004 Entity Management, 3005 User Access Management, 6003 API Activity. |
| `tenant.project_id` | integer or null | The tenant project. `0` is the platform partition of the security audit chain. |
| `actor` | object | `type` (`user`, `principal`, `agent`, `system`, `unknown`), `id`, and optionally `email`, `chain` (the RFC 8693 actor chain, outermost first), `fidelity` (`native_act`, `configured_act`, `azp_only`, `attributed`, `none`) and `actor.role` (`subject` or `affected`, only on the signal stream). |
| `action` | string | The governed operation (`credential.use`, `grant.revoke`) or, for the Audit Trail, `METHOD /route`. |
| `target` | object, optional | `type`, `id`, `name` and optionally `target.release_id` (the agent release next to the application id) of what the action acted on. |
| `outcome` | enum | `allow` or `deny` for authorisation decisions; `success` or `failure` for operations; `unknown`. |
| `correlation` | object, optional | `trace_id`, `span_id`, `parent_span_id`, `correlation_id` and optionally `correlation.conversation_id` (the conversation uuid as a string). |
| `chain` | object, optional | `partition`, `sequence`, `prev_hash`, `hash` (hex SHA-256) when the source keeps a tamper-evident chain. Present on every `security_audit` and `run_step` event (partition `run:<run id>`, one chain per run), and on `admin_audit` events written since the trail was chained (partition `0`, one platform-wide chain). |
| `signal` | object, optional | One security signal; present on every `security_signal` event whose `event_type` is not `chain.checkpoint`, never on any other source. See [Security signals](#security-signals). |
| `details` | object | Fields specific to the source, listed below. |

The OCSF mapping, in the schema's own description: `event_id` to `metadata.uid`, `time` to `time`, `source` to `metadata.product.feature.name`, `ocsf.*` to `class_uid` and `category_uid`, `tenant.project_id` to `cloud.project_uid`, `actor.id` to `actor.user.uid`, `actor.email` to `actor.user.email_addr`, `action` to `activity_name`, `target.*` to `resources[]`, `outcome` to `status_id` and the authorization disposition, `correlation.trace_id` to `metadata.correlation_uid`. `chain.*` and `details.*` have no OCSF attribute and travel in `unmapped`.

### `details` for `security_audit`

`reasons` (stable reason codes), `authorization_epoch`, `revocation_epoch`, `outbox_seq`, and, when set: `calling_application_id`, `authentication_ref`, `agent_binding_id`, `authority_id`, `mandate_ref`, `delegation_ref`, `grant_ref`, `workload_id`, `execution_id`, `invocation_id`, `decision_id`, `policy_revision_id`, `arrangement` (`A`, `B`, `C`). Every value is a reference or an identifier; an event never holds a token, a secret or a provider response.

### `admin.access.changed`

A change of who holds what on the administration surface is one `security_audit` event of type `ai.elitea.security.v1.admin.access.changed` (OCSF 3005 User Access Management), appended in the same transaction as the change: a change whose event cannot be written does not happen. `action` is `admin.access.<kind>`, `actor` is the person who made the change (none for `bootstrap`), `target` is what changed, and `details.access` carries the change:

| Field | Meaning |
|---|---|
| `kind` | One of the kinds below. |
| `before`, `after` | The subject's set before and after the change, by name, sorted. Always present; empty for a kind that names fields instead. Two kinds use them as stated in the table below: `role_renamed` (the old and the new name) and `project_permissions_pushed` (the permissions removed and added). |
| `fields` | For a provider or trust change, the fields that changed (`created`, `deleted`, `issuer`, `secret`, `data.api_base`), never their values or a digest of them. |
| `mode` | The role mode of a role change (`administration`, `default`). |
| `source` | For `role_assignment`, how the change was made: `console`, `api`, `bootstrap`, `migration`, `operator`, `review`, `scim` (see [Role changes are recorded](/admin/users-and-roles#role-changes-are-recorded)). On `role_assignment` and `project_membership`, `provisional` is a gift under an elevation that is in effect only while the elevation is active (`after` is the standing set with the gift), and `review` is its confirmation by the elevation's reviewer (see [What an elevated person gives is provisional](/admin/break-glass#what-an-elevated-person-gives-is-provisional)). |
| `elevation_id` | The elevation the change was made under, when there was one. |
| `reason_code` | The reason code the caller gave, when there was one. The event never carries the reason text: that stays in the Audit Trail row. |
| `membership` | For `project_membership`: `actor_is_member`, `member_holds_admin_role`, `bulk`. |

| Kind | Target | Recorded when |
|---|---|---|
| `role_assignment` | `user` | A central role is assigned or removed: the Users page, `/admin/modes`, an account deletion, the first sign-in of an initial administrator. |
| `role_permissions` | `role` (`<mode>:<name>`) or `project_role` (`<project>:<name>`) | A role's permission set is edited on the Roles page. |
| `role_created`, `role_deleted` | `role` or `project_role` | A role is created or deleted. A deleted role's `before` is the permission set it held. |
| `role_renamed` | `role` or `project_role`, by the new name | A role is renamed. `before` is the old name and `after` the new one, so the events of the old name join to the live role. `fields` is `["project_role_copies"]` when a central `default` role was renamed in every project with it. No permission set changes: grants and members follow the role. |
| `project_permissions_pushed` | `project_roles` (`personal:<role>` or `team:<role>`) | An estate-wide push wrote a role's permissions in every project of a set: the personal-project or team-project matrix save, and **Apply to Projects** (`mode` `default`). One summary event per role the push changed, not one per project. `before` is the permissions it removed from the role in at least one project and `after` those it added in at least one. `fields` is `["roles_assigned"]` when the push also gave the role to every member. |
| `token_scopes` | `token` | A personal access token is given administration scopes. Reserved: comes with administration-scoped tokens. |
| `project_membership` | `user`, partition the project | A membership is written through a central route: a bulk invite, or an invite, role change or removal on the central member routes (`/admin/users/administration/{projectID}`). `bulk` is set for a bulk invite and for a request that writes more than one membership. A removal's `after` is empty. |
| `global_provider_route` | `global_provider` | A global provider is created or deleted, or its endpoint, credential or keyless identity changes. |
| `identity_trust` | `identity_provider` or `scim_client` | An identity provider is created, deleted, turned on or off, or has a trust field or its secret changed; a SCIM client is created or its secret rotated. |
| `break_glass_approval` | `configuration_section` (`break_glass`) | The approval switch of break-glass changed. `fields` is `["approval_required"]`; `before` and `after` hold `approval_required` while approval is requested on. `reason_code` is `approval_off_requested` (written at once; the switch-off takes effect after the delay) or `approval_on_restored` (at once; cancels a pending switch-off). See [Break-glass access](/admin/break-glass#switching-approval-off). |

A change that changes nothing (assigning a role already held, a settings-only edit) appends no event.

### `admin.elevation`

Each step of a break-glass elevation is one `security_audit` event of type `ai.elitea.security.v1.admin.elevation` (OCSF 3005 User Access Management, the class of its sibling `admin.access.changed`). The event is appended in the same transaction as the ledger write in `elitea_auth.admin_elevations`. If the event cannot be written, the step does not happen: no elevation starts and none ends. `action` is `admin.elevation.<action>`. `actor` is the person who took the step, or none for the platform and an operator command. `target` is the elevation, or the sealed credential or person for a step about no elevation. `effect` is `deny` for `denied` and `allow` otherwise. `details.elevation` carries the step:

| Field | Meaning |
|---|---|
| `action` | One of the actions below. |
| `source` | How the step was taken: `console`, `api`, `operator` (a process command) or `system` (the platform: an expiry, a session or account event). |
| `elevation_id` | The elevation. Present on every action except `credential_issued`, `credential_revoked` and `local_admin_signin`. `credential_used` carries it when the credential started one. |
| `user_id` | The person elevated, or the person who signed in. |
| `level` | `admin` or `super_admin`. |
| `path` | `approved`, `self` or `sealed`. |
| `reason_code` | `incident`, `identity_outage`, `recovery` or `other`. The event never carries the reason text: that stays in the elevation ledger. |
| `expires_at` | The elevation's expiry, once it has started. |
| `end_reason` | On `ended` and `expired`: why access stopped (`holder`, `approver`, `operator`, `expired`, `logout`, `session_revoked`, `user_suspended`, `user_deleted`, `scim_deactivated`). An end asked for after the expiry is `expired`; the reason that was asked for is the reason code `requested_end_reason:<reason>`, and the actor and source stay those of the person who asked. |
| `note_id`, `note_length` | On `note_added`: the note's id and its length in characters, never its text. |
| `credential_id` | On the credential actions: the sealed credential. |

The actions are `requested`, `approved`, `denied`, `request_expired`, `started`, `ended`, `expired`, `critical_change`, `reviewed`, `unreviewed`, `note_added`, `credential_issued`, `credential_used`, `credential_revoked` and `local_admin_signin`. In this release the ledger writes `started`, `ended` and `expired`, and the operator commands `break-glass issue` and `break-glass revoke` write `credential_issued` and `credential_revoked` with the source `operator` and the credential's `level` (see the [break-glass runbook](/deployment/break-glass-runbook#sealed-credentials)). The other actions are written by the request, review, sealed sign-in and local sign-in features as they arrive.

Reading the sealed credential list (`break-glass list`) is recorded too, as a `decision` event (`ai.elitea.security.v1.decision`) with the action `admin.elevation.credential_list`, the effect `allow`, the target type `sealed_credential` and the reasons `source:<source>` and `credentials:<number listed>`. No event ever carries a credential, its selector or its digest. An end that changes nothing (the elevation had already ended) appends no event.

### `details` for `admin_audit`

`row_id` (`centry.audit_events.id`), `is_error`, and, when recorded: `http_method`, `http_route` (the matched route pattern, never the raw URL), `status_code`, `duration_ms`.

A request that checked administration permissions also says in which capacity it was made. These fields follow `is_error`, each omitted when it was not recorded (rows from before the fields existed, and requests with no administration check):

| Field | Type | Meaning |
|---|---|---|
| `acting_roles` | array of strings | The caller's standing administration roles at request time, by name. An empty array is a credential that acts with no administration role (a `none` token, a run token, a system token): it is a value, not an absence. |
| `elevation_id` | UUID string | The break-glass elevation the request was made under. |
| `credential_kind` | enum | `session`, `form`, `sealed`, `token`, `native`, `run`, `system` or `scim`. Omitted when unknown, never guessed. |
| `central_override` | boolean | The write went through the central override: an administration permission reached a project the caller is not a member of. |
| `reason_code` | string | The reason code the caller gave. The reason **text** is never exported. |
| `reason_missing` | boolean | A reason was required and not given. |
| `elevation_flagged` | boolean | The action was done under an elevation and is marked for the elevation review. |

On a row chained in the trail's canonical form `elitea.audit_events.v2` (every row written since that form was introduced), these fields are covered by the row's `chain.hash`, so a change to one of them breaks the chain's verification. A row chained before it keeps its older form (`elitea.audit_events.v1`): its hash still verifies and does not cover these fields. The chain verification route picks the form by the row's chain position, so a chain that spans the change verifies end to end.

### `details` for `run_step`

`row_id`, `run_id`, `step_id`, `seq`, `generation`, `kind` (`model_call`, `tool_call`, `retrieval`, `approval`, `delegation`, `cap`, `error`, `output`), `started_at`, `ended_at`, `summary` (small fields per kind), `cited_step_ids`, `cited_document_ids`, `inputs` and `outputs` (each `digest`, `size`, `original_size`, `truncated`, `filtered`, `media_type` and `ref`, the object-store reference), and, when known: `application_id`, `release_id`, `definition_digest`, `node_id`, `name`, `toolkit_id`, `retrieval` (`index_name`, `query`, `filters_json`, `top_k`, `documents` with `document_id`, `source`, `score`, `rank`). The event carries digests and references, never the content.

When a run ends, its chain is anchored by a `security_audit` event of type `ai.elitea.security.v1.run.steps.anchored` whose `details` carry `chain_head` (the run's last hash) and `chain_length`.

## Security signals

The security signal stream carries one event per row of the security signal ledger (ADR-0058). `source` is `security_signal`, `event_type` is `security_signal.<type>`, and `signal.type` is the dotted name (`category.subtype`) the registry assigns: for example `security_signal.content.prompt_injection` carries `signal.type: content.prompt_injection`. `signal.type` is validated by a pattern, never by an enumeration, so a new type does not break a strict receiver. The `signal` object is never set on another source, and a `security_signal` event with an `event_type` other than `chain.checkpoint` always carries it. `chain.checkpoint` events use `source: security_signal` and carry neither `signal` nor `chain`. A producer keeps `event_type` equal to `security_signal.` plus the signal type, and the first segment of `signal.type` equal to `signal.category`. The registry of E0.1b owns the types, severities and the OCSF class of a signal type, so a signal event may carry `ocsf` when the class fits; it is optional, never required.

| Field | Type | Meaning |
|---|---|---|
| `signal.type` | string, pattern | The stable dotted name (`access.authn_failed`, `derived.repeated_prompt_attack`). Never enumerated here; the registry of ADR-0058 decision 2 is the published list. |
| `signal.taxonomy_version` | string | The version of the registry the producer used. |
| `signal.category` | string | The first segment of the type. |
| `signal.severity` | enum | `info`, `low`, `medium`, `high`, `critical`: the value after the deployment's overrides. |
| `signal.default_severity` | enum | The registry value, before the deployment's overrides. |
| `signal.confidence` | enum | `low`, `medium`, `high`: the declared confidence of the detector. |
| `signal.disposition` | enum | `blocked`, `masked`, `flagged`, `warned`, `approval_required`, `rejected`, `throttled`, `suspended`, `error_open`, `error_closed`, `observed`: what the control did. |
| `signal.detector` | object | `component` (the governance entry), `name` (the detector) and `type` (the detector type). |
| `signal.provenance` | object | `kind` (`user_turn`, `tool_result`, `retrieval`, `attachment`, `skill`, `participant_message`, `subagent_brief`) and, when known: `toolkit`, `mcp_server`, `document_id`, `url_host`, `author` (the subject surrogate of the uploader, the skill author or the message sender), `self_supplied` (true when the author is the actor), `digest` (the keyed digest of the untrusted part) and `claimed` (true when the client gave the provenance and it is the only one). |
| `signal.locator` | object, optional | Content-free: `step_ref`, `part_index`, `byte_start` and `byte_end`. Numbers and ids only. |
| `signal.attribution` | enum | `resolved` (default), `unresolved`, `stale_lease`, `reconciled`. |
| `signal.labels` | array, at most 16 | Bounded labels: a detector label, a framework tag or a reason code. Never matched text. |
| `signal.count` | integer | The number of signals a summary replaces. |
| `signal.first_seen`, `signal.last_seen` | RFC 3339 string | The window of a summary signal. |
| `signal.folded` | array, at most 20 | The event ids, run ids and conversation ids (uuids) of the signals that a summary replaced. |
| `signal.dedup_key` | string | A keyed hash of the type, the project, the subject surrogate, the agent, the detector, the disposition and, for a signal with no subject, the client key. |
| `signal.origin` | enum | `server`, `client` or `client_attested`. A client-reported signal is never treated as verified. |
| `signal.evidence` | object, optional | `digest` of a whole stored artifact and `ref`, a capability: signed, expiring and bound to this signal. |

A signal about untrusted content carries `actor.role` as `affected` (the actor's run met the thing) or `subject` (the actor did the thing). The actor of a signal is a surrogate or a pseudonym, never a clear user id or email.

`platform.sink_test` is one of the type registry: it is the event of "Send test event". It is sent to the one sink under test with that sink's next `delivery_seq`, is not written to the ledger and carries no `chain` object.

A `chain.checkpoint` event is not a detection. Its `event_type` is `chain.checkpoint` and it carries no `signal` object and no `chain` object (the checkpoint rules apply to `security_signal` events only). Its `details` carry `partition`, `epoch`, `head_hash` (hex SHA-256), `length`, `delivery_seq_high`, `chain_status` (`broken_since=<sequence>` on a partition with a break, or `deleted` on the final checkpoint of a removed partition), `key_id` and `signature`.

## Signed webhook

Elitea POSTs a JSON batch of up to 100 events:

```json
{ "schema": "elitea.audit.v1", "batch_id": "5d1c0f3a9b7e2a64c8f01d3e7b9a2c40", "events": [ { "...": "..." } ] }
```

| Header | Value |
|---|---|
| `X-Elitea-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256>` |
| `X-Elitea-Key-Id` | The `id` of the key that signed. |
| `X-Elitea-Delivery` | The batch id. Stable across retries of one batch. |
| `X-Elitea-Schema` | `elitea.audit.v1`. |

The HMAC is computed over the ASCII timestamp, a dot, and the **exact request body bytes**, with the key named by `X-Elitea-Key-Id`. Verify before you decode the body, compare in constant time, and reject a timestamp more than five minutes from your clock. During a rotation your receiver holds both keys and picks one by the key id.

Answer `2xx` to acknowledge. Any other answer, a timeout, or a connection error makes Elitea send the batch again, with backoff, until it is accepted. Answer `400`, `413` or `422` only for content you can never accept: Elitea then splits the batch in halves and sends each half as its own batch (with its own batch id), down to single events, so one bad or oversized event does not hold back the others. A single event refused on five passes is dead-lettered on its own. Redirects are not followed.

<Tabs>
<Tab title="Python">
```python
import hashlib, hmac, time

KEYS = {"2026-10": b"<secret>", "2026-04": b"<previous secret>"}  # both during a rotation

def verify(headers, body: bytes) -> bool:
    key = KEYS.get(headers["X-Elitea-Key-Id"])
    t, v1 = (p.split("=", 1)[1] for p in headers["X-Elitea-Signature"].split(","))
    if key is None or abs(time.time() - int(t)) > 300:
        return False
    expected = hmac.new(key, t.encode() + b"." + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, v1)
```
</Tab>
<Tab title="Node.js">
```js
import { createHmac, timingSafeEqual } from "node:crypto";

const KEYS = { "2026-10": "<secret>", "2026-04": "<previous secret>" };

export function verify(headers, body /* Buffer */) {
  const key = KEYS[headers["x-elitea-key-id"]];
  const [t, v1] = headers["x-elitea-signature"].split(",").map((p) => p.split("=")[1]);
  if (!key || Math.abs(Date.now() / 1000 - Number(t)) > 300) return false;
  const expected = createHmac("sha256", key).update(`${t}.`).update(body).digest("hex");
  return expected.length === v1.length && timingSafeEqual(Buffer.from(expected), Buffer.from(v1));
}
```
</Tab>

## OTLP logs

Each event is one OTLP log record: the whole envelope as a JSON string in the log body, event name `elitea.audit.event`, severity `WARN` for `deny` and `failure` outcomes and `INFO` otherwise, and the fields a SIEM filters on as flat attributes: `elitea.audit.schema`, `elitea.audit.event_id`, `elitea.audit.source`, `elitea.audit.event_type`, `elitea.audit.action`, `elitea.audit.outcome`, `elitea.audit.actor.type`, `elitea.audit.actor.id`, `elitea.audit.tenant.project_id`, `elitea.audit.ocsf.class_uid`. The resource carries `service.name` `elitea-main`.

A collector that receives them and writes JSON lines to a file your log shipper reads:

```yaml
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
      grpc:
        endpoint: 0.0.0.0:4317

processors:
  filter/elitea-audit:
    logs:
      log_record:
        - 'attributes["elitea.audit.schema"] != "elitea.audit.v1"'
  batch: {}

exporters:
  file:
    path: /var/log/elitea/audit.jsonl

service:
  pipelines:
    logs:
      receivers: [otlp]
      processors: [filter/elitea-audit, batch]
      exporters: [file]
```

Point `ELITEA_AUDIT_EXPORT_OTLP_ENDPOINT` at `http://<collector>:4318` (protocol `http`) or `<collector>:4317` (protocol `grpc`). The collector may be on a private address; this endpoint is set by the operator, not by tenants, so it is not subject to the webhook egress allowlist.

OTLP delivery is at least once too: Elitea does not advance until the collector acknowledges the request, so a collector restart repeats a batch. Deduplicate on `elitea.audit.event_id`.
