The **Cloud Browser** toolkit (`browser`) gives an agent that runs on the platform a real browser. The agent opens pages, reads them, clicks, types and fills in forms. The tools are the same as the desktop app's browser pane, with the same names and arguments. Each run gets its own browser session. The session is never shared and never used again.

An operator must first install the browser on the cluster. See [Cloud browser on Kubernetes](/deployment/cloud-browser-kubernetes). Without it, every browser tool answers `browser_unavailable`.

## Turn it on for a project

1. In the project's settings, open **Cloud browser** and set **Enabled**.
2. Optional: add **Allowed domains**, the hosts the browser may reach when the platform limits browser egress. You can add at most 128.
3. Add the **Cloud Browser** toolkit to an agent, or hand a thread off to the cloud. A handed-off thread gets the browser tools automatically when its project has the browser enabled.

## The engine

The project's **Cloud browser** setting has an **Engine**:

| Engine | What runs | Size | Offered |
|---|---|---|---|
| `full` (the default) | Chrome (chrome-headless-shell) | up to 2 CPUs and 2 GiB | yes |
| `auto` | Moli, a smaller browser engine, first. If the page needs Chrome, the session moves to Chrome once and stays there | up to 2 CPUs and 2 GiB | yes |
| `lite` | Moli alone, for pages that are mostly read | up to 1 CPU and 512 MiB | no |

You can choose `full` or `auto`. `auto` starts each session on Moli, which uses far less memory on most pages (a median of about 180 MiB against about 1.6 GiB for Chrome in the bake-off), and moves to Chrome only when Moli cannot serve the page. It needs the operator to have set up the lite engine on the cluster ([Cloud browser on Kubernetes](/deployment/cloud-browser-kubernetes)); without it, an `auto` session answers `browser_engine_unavailable`.

`lite` alone is not offered. A project setting that names it is refused with `engine_not_admitted`.

Engines are offered only after the engine bake-off (ADR-0049 decision 9, Appendix A). The bake-off runs 40 tasks on real sites, from Atlassian, Microsoft 365, Salesforce, ServiceNow, GitHub, documentation sites, government forms and single-page apps. An engine is admitted only if:

- it succeeds on at least 80% of the read and extract tasks,
- it is no more than 10 points behind `full` overall, and
- it never crashes or hangs.

`auto` passed every rule: 40 of 40 tasks, none crashed. `lite` succeeded on 37 of 40, but Moli crashed on 3 heavy pages (two Atlassian support pages and a large Rust documentation page). `auto` moved to Chrome on those 3 and finished them. `lite` will be tested again on a later Moli release.

When an `auto` session moves to Chrome, the page opens again in Chrome, and anything typed into a form that was not sent is lost. The agent's tool result says `engine_switched`, with the reason. A click, typing or a wait that caused the switch is not done a second time on Chrome, so the agent looks at the page again before it carries on. If a person had taken over, they keep control. A person who is watching sees *The page needed the full browser, so it was reopened there.* A switch happens when Moli fails where Chrome would not:

- Moli does not support a command the page needs.
- Moli stops, or stops answering, or a page does not finish opening in time.
- Moli reports an internal error.
- A snapshot misses the page's links and fields, or comes back empty on a page that has text.

A wait that runs out because the page never shows what it waits for is the page's, not Moli's, and does not cause a switch.

## Available tools

The category of a tool decides when a run needs human approval to call it. See [Runtime safety](/admin/enterprise-controls/runtime-safety#tool-categories-and-approval-policy).

| Tool | Category |
|---|---|
| Browser open | `read` |
| Browser snapshot | `read` |
| Browser screenshot | `read` |
| Browser back | `read` |
| Browser forward | `read` |
| Browser reload | `read` |
| Browser wait | `read` |
| Browser click | `write` |
| Browser type | `write` |
| Browser select | `write` |
| Browser scroll | `write` |
| Browser press | `write` |
| Browser request user | `read` |

`browser_request_user` asks the person to do a step, for example a sign-in. A screenshot goes to the model as an image.

## When the browser asks

The category in the table is the lowest one. The category of an act is decided again for each call, from the call and the latest snapshot of the page:

| The control is | Category | Asks a person |
|---|---|---|
| A plain control | `write` | Only if the approval policy names `write` |
| A submit or an upload (Submit, Save, Apply, Continue, Choose file, Enter in a form) | `external_send` | Yes, unless an unattended grant names the host |
| A consequential control (Send, Post, Delete, Sign, Confirm and similar) | `external_send` | Yes, always |
| A payment control (Buy, Pay, Checkout, Order and similar) | `payment` | Yes, always |
| A control the agent has not seen in a snapshot since the page last changed | `external_send` | Yes, always |

After any click, type, select or navigation, the platform forgets the page's labels. An act on an element then asks until the agent takes a new snapshot, even when the browser still knows the element. This way a click on "Place order" never runs without a question because the label was not known.

When the agent asks, the run pauses for approval as it does for any sensitive tool. The browser session stays alive while the run waits. If the run fails after an approved call that may have started, the call is not run again.

## Watch and take over

A person can watch a run's browser live, and take it over, for example to sign in. The view is a stream of screenshots from the session, sent only while somebody watches it.

### Open the browser

1. Open the conversation in the web app.
2. When an answer in the conversation used a browser tool, the side panel gets a **Browser** tab. Select it.
3. The tab shows the page the agent is on, its address, and the control pill:

   | Pill | Meaning |
   |---|---|
   | **Agent** | The agent drives the browser |
   | **You** | You took over: the agent waits |
   | **Idle** | Connected, waiting for the first page |
   | **Ended** | The session has ended |

The tab shows the browser of the newest answer that used it. Each run has its own browser, so a new run shows a new one. If the run has not opened a page yet, the tab says so and tries again by itself.

### Take over and hand back

1. Select **Take over**. You can also just click, type or scroll in the page: any input while the agent drives takes over too.
2. Use the page as you would in a browser, for example to sign in or answer a CAPTCHA.
3. Select **Hand back**. Optional: write a note for the agent, for example "signed in, continue from the inbox". Then select **Hand back** again.

While you have control, the agent may still take snapshots and screenshots, and every other browser tool answers `user_in_control`. The agent continues after you hand back, and reads your note.

### Watching only

If you may watch but not take over, the tab says **Watching only** and has no **Take over** button. Your clicks and keys do nothing. After the run ends, the session stays up to 10 minutes so the last page can still be watched. In that time nobody can take over.

### In the desktop app

The desktop app shows the same view, with the same toolbar, pill, **Take over** and **Hand back**:

- in a chat, in the inspector's **Browser** tab, as on the web;
- in a **Local work** thread that runs in the cloud, in the thread's own **Browser** tab, where the local browser shows while the thread runs on your computer. See [Browse the web in a thread](/how-tos/chat-conversations/desktop-browser-pane#when-the-thread-runs-in-the-cloud).

The app opens the stream itself, signed in as you, so it needs no browser sign-in. If the app is older than the deployment allows, the tab asks you to update it.

A native client or an integration can open the same stream with `viewBrowserSession` (client contract 1.40).

### Who may watch and take over

| Who | Watch | Take over |
|---|---|---|
| The person who started the run | Yes | Yes |
| A participant of the run's conversation who may send messages in the project | Yes | Yes |
| Anyone else who may read the conversation | Yes | No. Their input is refused |
| Anyone else | No. The session reads as not found | No |

Several people can watch the same session at once, from any replica of the platform. The tab finds the browser from the answer's run while the answer streams; after you reload the page, a finished answer no longer offers the tab.

Treat the view like the conversation itself: whoever may read the conversation sees what the agent's browser shows, including what a person types into it.

## Egress

The browser reaches the internet only through the platform's egress proxy, with a token signed for the run. An administrator sets the policy in **Admin › Configuration › Cloud Browser**:

| `browser_egress` | The browser may reach |
|---|---|
| `allowlist` (default) | The run's egress allowlist, plus the project's **Allowed domains** |
| `open` | Any public host. An administrator must choose it. |

A run under the governed credential profile always uses the allowlist. When the proxy refuses a host, the tool answers `egress_refused`. The refused host is in the run's egress summary.

One run token carries at most 128 allowed hosts: the platform worker egress allowlist, the project's worker egress entries and the project's **Allowed domains** together. If the list is longer, the run still starts, but every browser tool answers `browser_allowlist_too_large`. Shorten the lists to fix it. If the platform cannot read the browser settings or the month's usage when the run starts, the browser tools answer `browser_unavailable` for that run, and the run goes on without them.

## Time limits and metering

Browser time is metered per engine second, through the gateway (provider `browser`, operation `engine_seconds`, unit `second`). The price starts at $0 per second. Set your own in **Admin › LLM proxy › Tools**. If an administrator removes the price, a browser call answers `browser_unpriced`.

| Limit | Where | Default | At the limit |
|---|---|---|---|
| Seconds per run | `max_run_seconds` in the Browser section | 1800 (0 is no cap) | The run stops with `max_browser_seconds` |
| Seconds per project per month (UTC) | `monthly_quota_seconds` in the Browser section | 0 (no quota) | The run stops with `browser_monthly_quota` |

Each stop is visible on the run. A run stopped at a browser limit offers no **Allow the next run past this cap** action: no override raises these two limits. Budgets and rate limits of the gateway also apply, and a refused call says so.

Only time with a running browser counts. A call that never reached the browser (no route out, a refused grant, the platform's browser capacity, an ended session) bills 0 seconds and does not count against either limit. The month's usage is read from the usage ledger, so a retried call counts once.

## Unattended runs

A run that a schedule or a webhook starts, or one that a person starts with an unattended grant, has nobody to answer:

- The agent may read, navigate and act on plain controls without asking.
- An ask follows the run's `on_approval_required` setting, as every other ask does.
- `browser_request_user` fails at once with `no_person`.
- The unattended grant may name hosts in `browser_submits`, at most 32 lowercase host names. On those hosts a submit or an upload runs without asking. A consequential or payment control always asks.
