This walks a Kubernetes install of the `elitea` chart end to end. It is one chart for everything: the platform, NATS JetStream with its stream bootstrap, the vector store and, where a cluster needs it, the sandbox-runtime installer. Read [Production deployment overview](/deployment/overview) first for the topology and what the chart does not provision. For a first install on an empty cluster, [Deploy from scratch](/deployment/from-scratch) has every Secret, certificate authority, database step and edge rule in one place, with a complete values file.

## Prerequisites

<CardGroup cols={2}>
  <Card title="Cluster access" icon="server">A Kubernetes cluster with `kubectl` and `helm` configured against it. Helm 4.3 or newer is recommended; Helm 3.8 or newer also renders the chart, which is what Argo CD uses. With Helm 4, `--atomic` is `--rollback-on-failure`.</Card>
  <Card title="PostgreSQL" icon="database">Reachable, with an administrator DSN available for the database-preparation Job (`CREATE DATABASE`). No extension is needed: vectors are kept in Qdrant through elitea-vector (`vector.enabled`), not in PostgreSQL.</Card>
  <Card title="NATS JetStream" icon="server">Bundled: the chart runs it (`nats.enabled`, on by default) and creates its streams with a hook Job (`natsBootstrap`). The platform needs no Redis: the runtime command bus, live updates and presence are on NATS, and the chart refuses values that still set `runtimeRedis`.</Card>
  <Card title="Object storage" icon="package">An S3-compatible bucket, created ahead of the first sync and named by `main.env.STORAGE_CONTAINER`.</Card>
  <Card title="cert-manager" icon="shield-check">Required. The bundled NATS CA, the NATS client identities and the LLM gateway's mTLS hop (on by default) are all cert-manager `Certificate`s. The mTLS issuers default to `ClusterIssuer`s `elitea-internal-ca` and `elitea-runtime-ca` (`certManager.issuers`), yours to create; or set `certManager.issuers.create: true` and the chart makes them, namespaced, over your runtime CA Secret.</Card>
</CardGroup>

## Secrets to create beforehand

Nothing secret goes in a values file — a Helm parameter renders into a ConfigMap, readable by anyone with `get` on the namespace. Create these Kubernetes Secrets first; the chart only ever takes their **names**.

<Accordion title="SECRETS_MASTER_KEY">
Wraps each project's vault key. Required by both elitea-main and the gateway, and it must be the same key: elitea-main reads the gateway's reference (`llmGateway.secrets.SECRETS_MASTER_KEY`, default Secret `elitea-llm-gateway-secrets`, key `secrets-master-key`) unless you override both. Generate: `python3 -c 'import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())'`
</Accordion>

<Accordion title="postgresql.existingSecret">
The database DSN, one Secret + key pair that every component reading the database (elitea-main, its migration Job, the scheduler, the LLM gateway, the workload-session Job) derives its `DATABASE_URL` from. Default names: Secret `elitea-main-db`, key `database-url`.
</Accordion>

<Accordion title="runtime.material.secretName (runtime plane only)">
Agent-execution signing keys and listener certificates (from `deploy/scripts/gen-runtime-certs.sh`). Required if `main.runtime.enabled: true`.
</Accordion>

<Accordion title="fileConfig.authConfig.material.secretName (production auth)">
Three files: the browser-attempt key, the PAT signing key and the Form users JSON. Required if using Form or mixed authentication. The auth document is `elitea.auth.form.v2`: it has no `redis` block, because the Form sign-in state is in PostgreSQL, and the attempt key is `credentials.attempt_key_file`. The Form users JSON is a sign-in path only when `main.env.ELITEA_FORM_LOGIN_ENABLED` is `"true"`; Form sign-in is off by default.
</Accordion>

<Accordion title="Gateway identity secret (GATEWAY_IDENTITY_SECRET)">
Required on both main and gateway; must be identical. HMAC key for signing/verifying identity headers.
</Accordion>

<Accordion title="main.breakGlass.noticeWebhook.existingSecret (optional)">
The out-of-band webhook of the break-glass notices, for when e-mail is down. Its URL carries the receiver's token, so it is a credential: the chart takes only the Secret's name, never the URL (the schema refuses a `url` key). The Secret holds two keys, the `https` URL (`key`, default `url`) and the signing secret the receiver checks `X-Webhook-Signature` against (`signingSecretKey`, default `signing-secret`, at least 32 random bytes):

```bash
kubectl create secret generic elitea-break-glass-webhook -n <namespace> \
  --from-literal=url='https://<receiver>/<path-with-token>' \
  --from-literal=signing-secret="$(openssl rand -base64 32)"
```

Then set `main.breakGlass.noticeWebhook.existingSecret: elitea-break-glass-webhook`. A receiver on a private address also needs `main.breakGlass.noticeWebhook.egressAllowlist`. Unset, no webhook is sent and the notices go by e-mail only. See [The out-of-band notice webhook](/deployment/configuration#the-out-of-band-notice-webhook) for the payload and the retries.
</Accordion>

## Two settings with no chart default

The chart **refuses to render** while either of these is empty — there is no safe guess for either, and a guessed value would look armed while guarding nothing:

| Setting | What it is |
|---|---|
| `llmGateway.env.GATEWAY_SELF_LLM_ORIGINS` | Every origin that reaches this deployment's `/llm` surface, public and in-cluster, comma-separated — e.g. `https://elitea.example.com/llm,http://elitea-main:8080/llm`. `global.publicUrl` fills exactly that when this is empty. |
| `llmGateway.egressPosture` | `"allowlist"` (only hosts in `GATEWAY_EGRESS_ALLOWLIST` / governance rows) or `"public-unrestricted"` (any public host, until the first governance row narrows it). Private-network reachability follows only from an entry that explicitly names a private address or block — never from the posture alone. |

One value fills most of the URL-shaped settings: `global.publicUrl` (for example `https://elitea.example.com`) fills `DEPLOYMENT_URL`, the OIDC redirect URI, the authentication document's `public_origin`, the gateway's self origins, the worker's base URL and SPIFFE ID and the Ingress host, where each is empty. `global.trustedProxyCidrs` fills both trusted-proxy lists. See [Configuration](/deployment/configuration#release-wide-settings). The chart also refuses a value that still holds a `<...>` placeholder of an example file, and lists every such path.

Also required: `platform.aiProjectId`, the id of the platform's public/shared project — it must name a project schema (`p_<id>`) that already exists. It fills `main.env.ELITEA_AI_PROJECT_ID`, `llmGateway.env.ELITEA_AI_PROJECT_ID` and `web.env.VITE_PUBLIC_PROJECT_ID` at once; `helm template` refuses a values file where the three copies disagree.

## Choose a values file

<Tabs>
<Tab title="values.yaml (base)">
The chart's own defaults. The runtime plane, the worker, elitea-vector with the bundled Qdrant, DeepWiki and Inventory are **on**, one switch each (`main.runtime.enabled`, `worker.enabled`, `vector.enabled` with `qdrant.enabled`, `deepwiki.enabled`, `inventory.enabled`); set one to `false` explicitly to leave it out. The base file alone does not render: the values only you know (the authentication document and its `public_origin`, the public project, `DEPLOYMENT_URL`, the worker's identity, the git allowlists, the network-policy peers, the gateway's self origins and egress posture) are listed together in one refusal, so a first `helm template` is the checklist. Qdrant needs a PersistentVolumeClaim (`qdrant.persistence`, 50Gi on the default StorageClass).
</Tab>
<Tab title="values-standalone.yaml">
The full capability set, matching `docker-compose.standalone-full.yml` — every capability flag on, the runtime plane on (agent execution, index ingest), sized for `postgresql.maxConnections: 200` across up to `main.autoscaling.maxReplicas: 4`. Needs both the runtime material Secret and the auth material Secret. This is the reference production shape.
</Tab>
<Tab title="values-auth-minimal.yaml">
The cheapest install that can seed an AI provider credential through the product's own API instead of hand-written SQL: production (Form) authentication plus `ELITEA_CONFIGURATIONS_ENABLED`, **no runtime plane** — no agent execution, no chat. Needs the auth material Secret, but no Redis, no runtime material Secret and no worker: the Form sign-in state is in PostgreSQL.
</Tab>
<Tab title="values-gke.yaml">
Google Kubernetes Engine with no static cloud credential: Cloud SQL with `sslmode=require` and a hand-prepared database, keyless GCS through Workload Identity, the GKE Ingress with its BackendConfig and FrontendConfig, Google's load-balancer ranges in the NetworkPolicy, and every Secret from Secret Manager through `externalSecrets`. Sized for about 4 vCPU and 9 GiB of requests in steady state, with every default on. See [Deploy on GKE with Argo CD](/deployment/gke-argocd).
</Tab>
<Tab title="values-staging.yaml">
A minimal single-replica shape (image tag `shadow-v0.1`, `DATABASE_URL` inlined for a throwaway environment, autoscaling and the pod disruption budget both off). Use it for a disposable smoke/shadow environment, not as a production starting point.
</Tab>
</Tabs>

## Install: one chart, one namespace

One release installs everything, in one namespace. NATS requires TLS and a client certificate from every client (mTLS, no anonymous or password access), and those certificates come from the chart's own NATS CA, a *namespaced* cert-manager `Issuer`, so NATS, its bootstrap and the platform share the release's namespace by construction. **cert-manager must be installed first.**

From a clone, build the chart's dependencies first. The upstream NATS chart and the sandbox-runtime installer are pinned in the committed `Chart.lock`, and `charts/` is never committed:

```bash
deploy/helm/elitea/build-deps.sh   # helm dependency build, from Chart.lock
helm install elitea deploy/helm/elitea \
  -f deploy/helm/elitea/values-standalone.yaml \
  --set postgresql.existingSecret=elitea-main-db \
  --set-string llmGateway.env.GATEWAY_SELF_LLM_ORIGINS=https://elitea.example.com/llm/v1 \
  --set-string llmGateway.egressPosture=public-unrestricted \
  --set-string platform.aiProjectId=1 \
  -n elitea --create-namespace
```

The published chart is the recommended source: `oci://ghcr.io/elitea-ng/charts/elitea --version <version>` in place of the path. Its package carries the same values files (`helm pull --untar` to read them) and both dependencies, so it needs no `helm dependency build`. In an air-gapped network, mirror that OCI chart; do not build from a clone.

The chart issues each NATS client (elitea-main, the LLM gateway, the scheduler, the worker) its own certificate and renders `tls://elitea-nats.elitea.svc.cluster.local:4222` for it — no NATS credential goes in any value. The stream and KV bootstrap is a `post-install,post-upgrade` hook Job; until it has run, the workloads restart, then settle. Its client certificates live one hour, and only as long as the Job: the Job's init container creates them, owned by the Job, after it deletes the expired certificate Secrets that the previous install or upgrade left behind. It waits until cert-manager reports each one Ready, then hands the certificates to the bootstrap container in memory. Its Role can read and delete only those Certificates and Secrets, by name, and create Certificates; only the init container holds the token.

<Warning title="No --wait on a first install">
`helm install --wait` waits for workloads that wait for the streams the bootstrap hook creates, and that hook runs only after the wait. Leave `--wait` off the first install; later upgrades may use it.
</Warning>

For three NATS nodes, add `-f values-nats-ha.yaml` (it raises the bootstrap's replica count too). To use a NATS you run yourself, set `nats.enabled=false` and point `natsClient.*` at it. Under ArgoCD the same chart orders itself with sync waves — see [GitOps with ArgoCD](/deployment/argocd).

<Check title="Prove it renders first">
`helm template` catches missing prerequisites before any kubectl apply:
```bash
helm template deploy/helm/elitea -f deploy/helm/elitea/values-standalone.yaml \
  --set postgresql.existingSecret=elitea-main-db \
  --set-string llmGateway.env.GATEWAY_SELF_LLM_ORIGINS=https://elitea.example.com/llm/v1
```
</Check>

## The migration job and DB bootstrap

`elitea-migrate` runs as a pre-install hook; the database may start empty. The `dbInit` Job (hook weight -20) handles `CREATE DATABASE` for the agent-state database before migrations run. It creates no extension.

## First-admin bootstrap

A fresh database seeds exactly one administrator, `dev@elitea.ai`, with no password on a single-sign-on deployment — name your own account instead through `identity.initial_global_admins` (a YAML list, wins when the authentication document has one) or `main.env.ELITEA_INITIAL_GLOBAL_ADMINS` (comma-separated, the usual path for a single-sign-on-only install with no document). With Form sign-in off (the default), the first OIDC or SAML sign-in that matches an entry — `oidc:<sub>`, `saml:<nameid>`, or `email:<address>` for an OIDC login with a verified address — is your first administrator. Write Form logins there only if you enable Form sign-in. The list applies only while no active account holds `super_admin`; after that, add administrators from the console of an existing administrator.

An entry is `oidc:<sub>`, `saml:<nameid>`, or `email:<verified address>` (matches only when the id_token asserts `email_verified: true`). The grant is one-shot: an account that already holds any administration role is left as is; one with none receives the grant on its next sign-in.

For OIDC with a verified e-mail address, use `email:<your address>`. You know this value before the first sign-in, so you can set it at install time.

For other cases, sign in once and open **Settings › Profile**. Each **Sign-in reference** row shows one exact value that the list accepts, for example `oidc:<sub>` or `saml:<nameid>`. Click a row to copy it. Add the value to the list, upgrade the release, and sign in again. You do not need to query the database. See [Install Elitea](/getting-started/install#first-login-and-setup) for the browser-side walkthrough of this same step.

## Capability flags this install serves

<Accordion title="How to read this table">
`cmd/elitea-main` gates whole route groups on these variables. `values.yaml` sets every one; `values-standalone.yaml` is the reference production set. `ELITEA_CONFIGURATIONS_ENABLED` ships **empty** in the base chart — `_helpers.tpl` derives `"true"` automatically once any authentication is configured and `ELITEA_AI_PROJECT_ID` is set; a stated value always overrides the derivation.
</Accordion>

| Flag | Default install | `values-standalone.yaml` | Needs |
|---|---|---|---|
| `ELITEA_ARTIFACTS_ENABLED` | on | on | object storage configured |
| `ELITEA_CONFIGURATIONS_ENABLED` | derived | on | any authentication **and** `ELITEA_AI_PROJECT_ID` |
| `ELITEA_PROJECT_INFO_ENABLED` | off | on | production authentication |
| `ELITEA_CONFIGURATIONS_MUTATION_ENABLED` | off | off | `ELITEA_CONFIGURATIONS_ENABLED` **and** `runtime.enabled` |
| `ELITEA_INDEX_TYPES_ENABLED` | off | on | production authentication |
| `ELITEA_APPLICATION_SKILLS_ENABLED` | off | on | production authentication |
| `ELITEA_RUNTIME_ENABLED` (`main.runtime.enabled`) | on | on | production authentication **and** runtime material |

<Warning>
`ELITEA_CONFIGURATIONS_MUTATION_ENABLED` stays off in every shipped values file. It composes a second, asynchronous write route that would win the path from the compatibility route every install currently serves — and the compatibility route already writes `status_ok` inline from the same admission decision, which is what makes a saved credential usable. Turning it on is a separate cutover with its own client-side work, not a fix for an invisible credential.
</Warning>

## Network policies

With `networkPolicies.enabled` (the default) the chart renders a NetworkPolicy for each workload it runs. They need a CNI that enforces NetworkPolicy (Calico, Cilium, GKE Dataplane V2 and others); on one that does not, the objects are inert. They are defence in depth beside each component's own checks, and some CNIs do not apply policy to host-network destinations.

| Workload | Ingress | Egress |
|---|---|---|
| elitea-main | 8080 from `networkPolicies.main.ingressFrom` / `extraIngressFrom` and `probeFrom`; the runtime listeners (9443-9446) from the worker; the platform listener also from DeepWiki and Inventory | not restricted |
| worker | none | DNS, elitea-main's runtime listeners, NATS 4222, PostgreSQL (`networkPolicies.egressPeers.postgresql`), the sandbox supervisors, elitea-vector, the OTel collector, `worker.networkPolicy.privateEgress`, and the public internet on 443 minus every private, link-local and cluster range |
| sandbox supervisor | its profile ports from the worker and elitea-main | not restricted |
| elitea-web | 80 from elitea-main and `networkPolicies.web.extraIngressFrom` | not restricted |
| scheduler | its health port from `probeFrom` and `metricsFrom` only | not restricted |
| LLM gateway | gRPC from elitea-main and `networkPolicies.llmGateway.extraIngressFrom`; 8083 from `probeFrom` and `metricsFrom` | DNS, NATS, PostgreSQL, the OTel collector, `llmGateway.networkPolicy.egress`, and the public internet on 443 minus every private, link-local and cluster range |
| OTel collector | OTLP 4317/4318 from the chart's pods that export traces and `networkPolicies.otelCollector.extraIngressFrom` | not restricted |
| PgBouncer | its port from the chart's pods that read the database Secret, the dbInit Job and `networkPolicies.pgbouncer.extraIngressFrom` | not restricted |
| DeepWiki, Inventory, elitea-vector, Qdrant, NATS | see the comments in `values.yaml` | not restricted |

`networkPolicies.metricsFrom` is the Prometheus that scrapes the closed metrics ports. The gateway's autoscaler reads `gateway_llm_sse_active_connections` from it, so list it when the gateway autoscales on that metric.

### Egress of the worker and the LLM gateway

Two values have no default, and the chart lists them with the other missing values while either egress policy renders:

| Setting | What it is |
|---|---|
| `networkPolicies.clusterCIDRs` | The cluster's pod and Service CIDRs, for example `[10.244.0.0/16, 10.96.0.0/12]`. Also list the node range and the control-plane endpoint when either uses public addresses. The public-internet rules except every listed block, so a cluster whose pods use public-range addresses doesn't count as public. Not needed with `allowPublicEgress: false` on both. |
| `networkPolicies.egressPeers.postgresql.to` | Where PostgreSQL is, as NetworkPolicyPeer entries: an `ipBlock` with a managed database's address (`{ipBlock: {cidr: 10.20.0.5/32}}`), or a `namespaceSelector` with a `podSelector` for one in the cluster. Admitted on `egressPeers.postgresql.ports` (5432). |

With `nats.enabled: false`, both policies admit every pod of `natsClient.namespace` on `natsClient.port`; `networkPolicies.egressPeers.nats.to` narrows that to your NATS pods.

To open more destinations:

- **Private toolkit hosts.** Add each on-premises host the worker's toolkits, index sources or remote MCP servers reach (a self-hosted Jira, GitLab, an in-cluster MCP service) to `worker.networkPolicy.privateEgress`, a CIDR and its ports each. The CIDR and IP entries of `main.env.ELITEA_WORKER_EGRESS_PRIVATE_PERMIT` are admitted for you. A host name entry there, and every entry of the console's **Private Permit**, needs its addresses in `privateEgress`. Link-local blocks are refused.
- **Other public ports.** `worker.networkPolicy.publicEgressPorts` and `llmGateway.networkPolicy.publicEgressPorts` (443 by default).
- **Self-hosted models.** Every model host `GATEWAY_EGRESS_ALLOWLIST` names that is private or in the cluster goes in `llmGateway.networkPolicy.egress`, as raw egress rules.
- **Anything else.** `worker.networkPolicy.extraEgress` takes raw egress rules: a vector store, supervisor or OTLP collector (`global.otelEndpoint`) the chart does not run.
- **DNS.** The rules admit pods labelled `k8s-app: kube-dns`. With NodeLocal DNSCache, or a resolver with other labels, set `networkPolicies.dnsEgress` (for example a rule to `169.254.20.10/32` on UDP and TCP 53).

`worker.networkPolicy.mode: proxy` replaces the worker's public rule with the egress proxy (`egressProxy.enabled`). The worker's toolkit clients connect directly, so in this mode toolkits reach only the private and extra destinations you list.

Turning off one of these egress policies (`worker.networkPolicy.egressEnabled: false`, `llmGateway.networkPolicy.enabled: false`) needs the statement `externallyManaged: true` beside it, as `networkPolicies.enabled: false` does.

### Service-account tokens

No pod mounts a Kubernetes service-account token unless it calls the Kubernetes API: the sandbox supervisor, the KEDA uninstall hook and the NATS bootstrap Job's `issue` container (through a projected token of its own). The worker runs as its own `elitea-worker` ServiceAccount (`worker.serviceAccount`). For a mesh or sidecar that reads the automounted token, set `<component>.serviceAccount.automountToken: true` for that component (`main`, `web`, `scheduler`, `llmGateway`, `deepwiki`, `inventory`, `otelCollector`, `worker`). GKE Workload Identity, EKS Pod Identity, IRSA and Azure Workload Identity do not need it: they use their own projected tokens or the metadata server.

## Pod security

Every container the chart renders, init containers included, runs with the `restricted` Pod Security settings by default:

- `runAsNonRoot: true` and a `RuntimeDefault` seccomp profile;
- `allowPrivilegeEscalation: false` and every capability dropped (`capabilities.drop: [ALL]`);
- `readOnlyRootFilesystem: true`. A path a component writes is an `emptyDir` of its pod (`/tmp`, the worker's output spool and scratch).

Each component reads `<component>.podSecurityContext` and `<component>.securityContext`. `pgbouncer.securityContext` applies to both the PgBouncer container and its `userlist` init container.

- **elitea-web** runs nginx as the image's `nginx` user (uid 101) on container port 8080, with its pid file, temp files and `config.js` under `/tmp`. The `elitea-web` Service still listens on `web.service.port` (80) and targets the named `http` port, so elitea-main's `ELITEA_WEB_UPSTREAM` and anything else that calls the Service are unchanged.
- **The one exception** is the worker's `material` init container. It runs as uid 0 with only `CHOWN`, `DAC_OVERRIDE` and `FOWNER`, on a read-only root filesystem, to hand the runtime material to the worker's uid, and exits before the worker starts.
- **Sandbox Pods** that the sandbox supervisor creates at run time (code, workspace runs, browser sessions) are not chart-rendered and carry their own policy. See [Cloud executor on Kubernetes](/deployment/cloud-executor-kubernetes).

Third-party subcharts (NATS, Qdrant) keep their own values. The CI test `deploy/helm/tests/render-pod-security.sh` fails when a chart container drops one of these settings.

## Troubleshooting the NATS bootstrap

Helm deletes the bootstrap hook Job when it succeeds, so a Job still in the namespace is one that failed or is still running.

| Symptom | Likely cause | Fix |
|---|---|---|
| The `elitea-nats-bootstrap` Job waits in `Init:0/1` or fails in its `issue` container | it cannot reach the Kubernetes API, a Secret or Certificate it must delete keeps a finalizer, or a bootstrap Certificate does not become Ready | `kubectl -n elitea logs job/elitea-nats-bootstrap -c issue`; the log names the object, the HTTP status and the API's reason, or the Certificate's conditions |
| The `issue` container of `elitea-nats-bootstrap` logs `curl: (7) Failed to connect to kubernetes.default.svc port 443` and `FAILED: GET Certificate elitea-nats-bootstrap-main-nats-client answered HTTP 000` on every attempt | an egress NetworkPolicy (default-deny, or one that blocks the private ranges) keeps the bootstrap pod from the Kubernetes API server. The old cleanup Job made these calls from a pod with other labels | allow egress from pods labelled `app.kubernetes.io/name: nats-bootstrap` and `app.kubernetes.io/instance: <release>` to the API server endpoints (`kubectl get endpointslice -n default -l kubernetes.io/service-name=kubernetes`) on TCP `6443` or `443`, or set `natsBootstrap.networkPolicy.enabled: true` with those addresses, each as a `/32`, in `apiServer.cidrs` (required). On Cilium, which matches the API server as the `kube-apiserver` entity, an `ipBlock` may not match: use a `CiliumNetworkPolicy` with `toEntities: [kube-apiserver]` (details in the [upgrade note](https://github.com/elitea-ng/elitea-platform/blob/main/docs/upgrading/2026-11-22-2911-nats-bootstrap-job-needs-api-egress.md)). A cluster with no egress policy needs nothing |
| An `elitea-nats-bootstrap-cleanup` Job is still in the namespace after the upgrade | a 7.6.0 to 7.8.0 chart left it behind (its delete policy did not cover every outcome), and the current chart no longer renders it | delete it: `kubectl -n elitea delete job elitea-nats-bootstrap-cleanup` |

## What a Kubernetes install does NOT give you

<AccordionGroup>
<Accordion title="No PostgreSQL">
The chart provisions no database. The migration hook fails against a cluster where PostgreSQL does not already exist or where the Secret/host settings have not been pointed at it. NATS, by contrast, is part of the release: elitea-main's live updates — the project SSE stream and canvas presence — need it with JetStream (`ELITEA_EVENTS_NATS_URL`, derived from the `natsClient` block), and so does the runtime plane: its command bus is JetStream in the RUNTIME account (`ELITEA_RUNTIME_NATS_URL`, as the `elitea-main-runtime` identity), consumed by the workers from their own WORKER account. The chart refuses `main.runtime.enabled` with no NATS to publish to.
</Accordion>
<Accordion title="No edge by default">
No Ingress or HTTPRoute renders until `main.ingress.enabled: true`. Then it is one `/` rule to elitea-main, which is the whole edge: elitea-main redirects `/` to `/app/`, relays `/app` and `/docs` to elitea-web, and serves its MCP endpoint under `/app` itself. On GKE, `main.ingress.gke` adds the BackendConfig and FrontendConfig the Google load balancer needs.
</Accordion>
<Accordion title="Bring your own NATS">
The bundled server lives in the release's namespace, signed by the chart's namespaced `elitea-nats-ca` Issuer. To use a NATS you run elsewhere, set `nats.enabled: false`, back a cert-manager `ClusterIssuer` with a CA used for NATS only, and point `natsClient.service`, `natsClient.namespace` and `natsClient.tls.issuerRef` at it; the bootstrap's identities follow `natsClient` (`natsBootstrap.tls.certificate.issuerRef`). The bootstrap Job still runs against your server unless `natsBootstrap.enabled: false`. Your server must run JetStream and map the same client identities, or elitea-main refuses to start. `deploy/helm/elitea/NATS.md` has the contract.
</Accordion>
<Accordion title="Who can mint a NATS identity">
Anyone who may create a cert-manager `Certificate` in the NATS namespace, or read its Secrets (the CA key is one), can obtain any NATS client identity. Restrict both with RBAC; the optional approver-policy (`nats.security.approverPolicy`) limits what the NATS issuers sign. See `deploy/helm/elitea/NATS.md`.
</Accordion>
<Accordion title="No secrets">
Every sensitive value is a Kubernetes Secret — see "Secrets to create beforehand" above. In production, turn on `externalSecrets` and the chart renders an ExternalSecret for each one from your secret manager's store; [Deploy on GKE with Argo CD](/deployment/gke-argocd) shows it with Google Secret Manager.
</Accordion>
</AccordionGroup>
