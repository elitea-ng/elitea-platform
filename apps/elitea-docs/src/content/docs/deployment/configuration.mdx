Once the chart has installed and you have signed in as the first administrator (see [Install with Helm](/deployment/helm-install#first-admin-bootstrap)), most day-to-day configuration moves into the admin console rather than back into a values file. This page is the map of what still lives where.

## Identity: OIDC, SAML, SCIM

Configure identity providers under **Configuration › Authentication** in the admin console — see [Authentication](/admin/authentication) for the click-through. What matters at the deployment level:

- **Sign-in is OIDC or SAML.** The local username/password (Form) sign-in is **off by default**: `main.env.ELITEA_FORM_LOGIN_ENABLED` must be `"true"` for the Form users file to be a sign-in path. With it off, the authentication document is still read (the gateway edge and the runtime depend on it), but no Form login page is mounted and no configured password is accepted. Every Form user needs a real address (`email`, or `attributes.email`); one without is refused at sign-in. See `docs/UPGRADING.md` in the platform repository.
- **The first global admin** is a chart/environment setting, not a console one — `identity.initial_global_admins` in the auth document, or `main.env.ELITEA_INITIAL_GLOBAL_ADMINS`. See the Helm install guide.
- **An OIDC-only install now gets the configuration plane.** Before, only a Form authentication document (`ELITEA_AUTH_CONFIG_FILE`) composed the principal validator the configuration write path needs; now `env.OIDC_ISSUER_URL` alone composes it too, as long as `ELITEA_AI_PROJECT_ID` is set. A deployment with no authentication at all is still refused, in both the chart and the binary.
- **SCIM** provisions accounts and groups at `/api/v2/scim/v2`. It authenticates with a dedicated SCIM client credential (a bearer secret, or OAuth2 client credentials at `/api/v2/scim/oauth/token`), not with a personal access token. Create the client and bind groups to project roles in the console (see [Authentication](/admin/authentication#connect-an-identity-provider-with-scim)). `ELITEA_SCIM_ACCESS_TOKEN_TTL` sets the access token lifetime (default `1h`).

## The first global administrator

A fresh database seeds only `dev@elitea.ai`. On a single-sign-on deployment, this account has no password. Set `identity.initial_global_admins` or the equivalent environment variable before you rely on the admin console.

## E-mail: SMTP bootstrap defaults

`SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_TLS`, `EMAIL_FROM`, `EMAIL_REPLY_TO` and `PUBLIC_BASE_URL` are a **default layer**, not the whole configuration. **Admin → E-mail** writes a second layer into the database, and `internal/emailsettings` merges the two field by field on every send — the database wins where it has a value.

<Steps>
<Step title="Set the bootstrap defaults">
Ship `EMAIL_FROM` and `PUBLIC_BASE_URL` at minimum through `main.env`; `SMTP_PASSWORD` belongs in the `secrets:` block (a Secret), never as a plaintext parameter.
</Step>
<Step title="Let an administrator name the relay">
A change in the console needs no restart or re-sync — the merge runs per message.
</Step>
<Step title="Check what resolved">
```bash
curl -s -H "Authorization: Bearer $ADMIN_PAT" \
  https://elitea.example.com/api/v2/admin/email/administration | jq
```
`.settings` is what the console stored, `.effective` is the merged document the next message uses, `.sources` names `database`/`environment`/`unset` per field, and `.configured`/`.reason` say whether a message can be sent.
</Step>
</Steps>

<Note>
`ELITEA_EMAIL_SUPPRESS: "true"` renders every message and sends none — the setting for a shadow or staging deployment. It outranks the console.
</Note>

## Egress allowlists

Two separate allowlists guard two separate outbound paths, both fail-closed by default in the dangerous direction:

<Tabs>
<Tab title="LLM gateway — GATEWAY_EGRESS_ALLOWLIST">
Names the hosts a saved provider credential's `api_base` may point at. It is the **floor**: the gateway also reads `egress_allowlist` rows from `gateway.governance_config` (edit them at **Admin → LLM Proxy → Governance**, no re-sync needed) and enforces the **union**. An authored row can only *add* a destination — nothing an admin authors can withdraw a host the chart named.

One grammar for both sources: a bare host, `host:port`, a `*.domain` wildcard, or a CIDR block. **The first entry anywhere turns the restriction on** — with none in either source, a credential may name any public host.

A private endpoint needs its **address** named, not only a hostname — bifrost's SSRF-safe dialer refuses RFC 1918 and loopback destinations unless an entry explicitly names a private address or block, because the gateway never resolves a name before deciding (that would reopen the DNS-rebinding race the allowlist exists to close). Link-local addresses (`169.254.0.0/16`, `fe80::/10` — cloud metadata endpoints) are refused no matter what the allowlist says.

`GET /governance/status` on the gateway (proxied at `GET /api/v2/admin/gateway/status`, and shown on **Admin → LLM Proxy → Status**) reports the merged list by source and whether a private destination is actually reachable.
</Tab>
<Tab title="Webhooks — ELITEA_WEBHOOK_EGRESS_ALLOWLIST">
Governs where a tenant-created webhook may dial. **Unset is the safe default**: every RFC 1918, ULA and loopback destination is refused, both when a webhook is created and again at dial time (the destination is re-resolved, not trusted from create time). Set it only to let webhooks reach a private receiver you control; link-local and multicast addresses are refused unconditionally regardless of this variable.

This variable is not a named key in `values.yaml` — set it like any other elitea-main environment variable:
```bash
--set-string main.env.ELITEA_WEBHOOK_EGRESS_ALLOWLIST="10.0.0.0/8"
```
</Tab>
<Tab title="Remote MCP — ELITEA_MCP_EGRESS_ALLOWLIST">
Governs where elitea-main may dial for a Remote MCP server: **Load Tools**, the OAuth and client-registration proxies, and the authorization metadata those servers name. It uses the same grammar and the same split as the webhook allowlist. **Unset refuses** every loopback, RFC 1918 and ULA destination, and each connection re-resolves the host before it dials. Name a private range (for example `10.0.0.0/8`) to let users reach MCP servers on your internal network. Link-local and multicast addresses stay refused whatever this variable says.

```bash
--set-string main.env.ELITEA_MCP_EGRESS_ALLOWLIST="10.0.0.0/8"
```
</Tab>
</Tabs>

## Budgets need GATEWAY_NATS_URL

Admin → Budgets writes spend-ceiling rows, but the LLM gateway is what **enforces** them, through a NATS JetStream counter — `GATEWAY_NATS_URL` names that server. In Kubernetes the chart derives it from the top-level `nats` block as `tls://elitea-nats.<namespace>.svc.cluster.local:4222`, in the platform's own namespace, and mounts the gateway's NATS client certificate beside it; an override must also be `tls://` and carry no credential.

<Warning>
Leave it unset and the gateway starts, logs a warning, and serves `/llm` with **no budget enforcement**: every budget write still answers 200, every limit reads back exactly as authored, Settings → Usage still reports accrued spend — and no call is ever refused. `GET /governance/status`'s `rate_limits_enforceable` is `false` exactly when this is the case, and Admin → Budgets raises its own warning banner from that field once any budget row exists. The Compose standalone stack runs no NATS service and leaves this unset deliberately, for the same reason.
</Warning>

## Worker implementation: python (default) or rust

`worker.implementation` selects which agent worker image the chart runs; the values are not interchangeable and the chart handles the difference rather than the operator.

<Tabs>
<Tab title="python (default)">
Every catalogued toolkit type and every internal chat-agent tool is available, at the cost of the larger interpreter/dependency image. This is the default in both the Helm chart and `standalone-stack.sh`.
</Tab>
<Tab title="rust">
A smaller, faster process with the platform's native agent runtime (checkpointing, step-limit enforcement) and no Python dependency surface — but, as of this release, **18 toolkit types** are unimplemented (`ado_boards`, `ado_plans`, `ado_repos`, `ado_wiki`, `aha`, `bitbucket`, `confluence`, `figma`, plain `gitlab`, `jira`, PowerPoint, `qtest`, TestIO, TestRail, XRAY Cloud, Zephyr Enterprise, Zephyr Essential, Zephyr Scale) and **six internal chat-agent tools** are skipped with a visible notice instead of run (Image creation, Data Analysis, Elitea MCP Tools, Planner, Swarm Mode, Smart Tools Selection). Every tile still shows, greyed with a reason, rather than disappearing.
</Tab>
</Tabs>

`runtime.json` — the worker's own configuration document — is byte-identical either way; only the process and its capability surface differ.

## Object storage and artifacts

`main.env.STORAGE_BACKEND` / `STORAGE_CONTAINER` point at an S3-compatible bucket. It must **exist before the first sync** — the readiness probe tolerates a missing bucket, but the very next boot step (setting the bucket's retention lifecycle) does not, so a missing bucket looks like a green install that then crash-loops. `objectInit.enabled: true` creates it for a self-hosted S3-compatible endpoint you administer directly (RustFS, MinIO); a managed cloud object store almost always withholds `CreateBucket` from an application-scoped credential, so create it out of band there.

## DeepWiki and Inventory: disk needs

Both are the same pattern — a Go `subapp-host` serving the SPI, reaching an engine sidecar over a Unix socket (for DeepWiki the Rust-native `elitea-deepwiki-engine-native` image, for Inventory the Rust-native `elitea-inventory-engine` image). Both are **on by default**, and each is **one switch**: `deepwiki.enabled` / `inventory.enabled`. The chart derives elitea-main's side from the provider's block — `ELITEA_DEEPWIKI_ENABLED` / `ELITEA_INVENTORY_ENABLED`, the git allowlist (copied from `deepwiki.env` / `inventory.env`), the client-certificate paths and mounts, and the platform gRPC target — so the two halves cannot drift apart. A `main.env` value that agrees is kept; one that disagrees fails the render with the switch to set instead. To leave either out, set `enabled: false` explicitly. The one value the chart cannot default is the git allowlist (`ELITEA_DEEPWIKI_GIT_ALLOWLIST`, `ELITEA_INVENTORY_GIT_ALLOWLIST`): the render lists it with every other missing value in one message. Their callback client certificates (`elitea-deepwiki-callback-client`, `elitea-inventory-callback-client`) are issued by cert-manager from the `elitea-runtime-ca` issuer, and their identity Secrets have fixed names (`elitea-deepwiki-secrets`, `elitea-inventory-secrets`, key `identity-secret`).

<Warning>
DeepWiki's engine is one Rust binary (`elitea-deepwiki-engine-native`), and its `native` runner needs a PostgreSQL URL (`deepwiki.secrets` or `postgresql.existingSecret`); the chart refuses to render without one. Inventory's engine is likewise one Rust binary (`elitea-inventory-engine`): its `native` runner needs a PostgreSQL URL (`inventory.secrets` or `postgresql.existingSecret`) and its own git allowlist, because it clones sources itself; the chart refuses to render without either. Both native runners keep their dense vectors in Qdrant through elitea-vector, not in PostgreSQL, so each also needs `vector.enabled` (on by default, with the bundled Qdrant; or `deepwiki.env.ELITEA_DEEPWIKI_VECTOR_URL` / `inventory.env.ELITEA_INVENTORY_VECTOR_URL` naming an elitea-vector deployed elsewhere); the chart refuses a native runner with neither. Graphs a previous Python engine left in a toolkit's bucket move over with the `import_graph` tool or the `import-graph` command. The Python DeepWiki and Inventory engines are removed; upgrading from it is in `docs/UPGRADING.md`.
</Warning>

Each provider's scratch space (`deepwiki.scratch` `8Gi`, `inventory.scratch` `20Gi` by default) is ephemeral clone/index space, not durable storage — a wiki publishes to PostgreSQL, and a replica that dies mid-generation only loses work already being redone. `ELITEA_DEEPWIKI_GIT_ALLOWLIST` / the Inventory equivalent are read fail-closed by both halves (the facade and the provider); two values that disagree mean an invocation that starts and then fails.

See [DeepWiki and Inventory](/menus/deepwiki-and-inventory) for the product-facing side.

## Observability

Traces flow over OpenTelemetry to the chart's own `otelCollector` (on by default, `otel/opentelemetry-collector-contrib`), which receives OTLP from elitea-main, elitea-scheduler and elitea-main's own tracing ingest proxy. The shipped pipeline exports to `debug` (log-only) — swap the `otelCollector.config` exporter for a real sink (an OTLP/HTTP endpoint, a vendor backend) before relying on traces outliving the pod. There is no bundled Langfuse or third-party APM integration; every other component's `OTEL_EXPORTER_OTLP_ENDPOINT` should point at the collector's Service (`http://<fullname>:4318` in-namespace).

## Export audit evidence to a SIEM

Set any of these as `main.env` keys. Both endpoints empty (the default) means export is off: no relay starts, no listener opens, nothing dials out. A bad value refuses the boot. What the export does and does not guarantee is in [Audit trail](/admin/audit-trail#export-to-your-siem); the event format is in the [audit event schema reference](/reference/audit-event-schema).

| Key | Default | Meaning |
|---|---|---|
| `ELITEA_AUDIT_EXPORT_OTLP_ENDPOINT` | empty | OTLP logs receiver. For `http`, the collector's base URL (`/v1/logs` is appended); for `grpc`, `host:port` or a URL whose scheme picks TLS (`https`) or plaintext (`http`). |
| `ELITEA_AUDIT_EXPORT_OTLP_PROTOCOL` | `http` | `http` or `grpc`. |
| `ELITEA_AUDIT_EXPORT_OTLP_HEADERS_FILE` | empty | Absolute path of a JSON object of request headers (an API key for a hosted SIEM). |
| `ELITEA_AUDIT_EXPORT_WEBHOOK_URL` | empty | Signed webhook receiver. `https`, or `http` only when the allowlist below names the receiver. No credentials in the URL. |
| `ELITEA_AUDIT_EXPORT_WEBHOOK_KEYS_FILE` | empty | Absolute path of the signing keys file. Required with the webhook URL. |
| `ELITEA_AUDIT_EXPORT_EGRESS_ALLOWLIST` | empty | Same grammar as `ELITEA_WEBHOOK_EGRESS_ALLOWLIST`. A receiver on a private address must be named here; link-local, multicast, reserved and cloud-metadata addresses stay refused. |
| `ELITEA_AUDIT_EXPORT_AUDIT_EVENTS` | `true` | Also export the admin audit trail (`centry.audit_events`), not only security audit events. |
| `ELITEA_AUDIT_EXPORT_AUDIT_EVENTS_FROM` | `now` | `now` starts at the newest audit trail row; `beginning` replays the table on the first run. |
| `ELITEA_AUDIT_EXPORT_BATCH_SIZE` | `200` | Events per pass, 1 to 5000. The webhook sends 100 per request. |
| `ELITEA_AUDIT_EXPORT_INTERVAL` | `5s` | Pause between audit trail passes, 1s to 1h. |
| `ELITEA_AUDIT_EXPORT_MAX_PERMANENT_ATTEMPTS` | `5` | How many times the receiver may refuse the same batch as malformed (400, 413, 422) before it is dead-lettered. |
| `ELITEA_AUDIT_EXPORT_METRICS_ADDR` | `:9464` | Listener for the export's Prometheus `/metrics`. Empty disables it. |

The webhook keys and OTLP headers are files, never environment values. Put them in a Kubernetes Secret and let the chart mount it:

```bash
kubectl -n elitea create secret generic audit-export \
  --from-file=webhook-keys.json --from-file=otlp-headers.json

helm upgrade elitea ./elitea --reuse-values \
  --set main.auditExport.secretName=audit-export \
  --set-string main.env.ELITEA_AUDIT_EXPORT_WEBHOOK_URL=https://siem.example.com/elitea \
  --set-string main.env.ELITEA_AUDIT_EXPORT_WEBHOOK_KEYS_FILE=/etc/elitea/audit-export/webhook-keys.json
```

The keys file is read at start and again every 30 seconds, so a rotated key needs no restart:

```json
{"keys":[{"id":"2026-10","secret":"<at least 32 characters>","created":"2026-10-01T00:00:00Z"}]}
```

To rotate, give your receiver the new key first, then list it beside the old one with a later `created`. Elitea signs with the newest key and names it in the `X-Elitea-Key-Id` header; the receiver verifies with whichever it holds. Remove the old key once nothing needs it. At most two keys are accepted.

<Note>
`main.auditExport.metrics` shapes the PodMonitor and the alert rules (`lagSeconds`, default 900; `backlogEvents`, default 10000). Where network policies are on, name your Prometheus in `networkPolicies.main.metricsFrom` so it can reach port 9464. The export needs shared migration 0196, applied by the normal migration job.
</Note>

## Enterprise credential governance

Off by default. `main.env.ELITEA_ENTERPRISE_CREDENTIAL_GOVERNANCE_ENABLED` pins every new run to a governed profile and an immutable policy revision, mounts the agent identity admin API, and can require an external Vault/OpenBao store. See [Enterprise credential governance](/deployment/credential-governance) before you turn it on.

## Maintenance and the banner

Both are console-editable under **Configuration**, not chart settings: a dismissible banner with its own icon/style/message, and a maintenance mode that answers `503` with a splash screen to every caller without administration access (the admin console and authentication routes stay reachable, so the window is reversible from inside itself). See [Features and configuration](/admin/features-and-configuration#configuration) for the click-through.
