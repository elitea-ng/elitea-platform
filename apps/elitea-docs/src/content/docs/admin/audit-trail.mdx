Audit Trail is a read-only view over what happened on the deployment — there is nothing to edit or configure here. Use it to answer "who did this, and when," whether you are investigating an incident, confirming a change actually landed, or checking whether a scheduled job ran.

## Review activity

<Steps>
  <Step title="Choose User or System events">
    User events are actions a person took; System events are platform-generated (for example a scheduled job firing). Each has its own tab.
  </Step>
  <Step title="Filter">
    Narrow by date range (with quick presets like 30 minutes, today, yesterday, 7 days, or 30 days, plus an explicit From/To), event type, project, user, or errors-only.
  </Step>
  <Step title="Use the heatmap">
    A calendar-style heatmap shows activity density over time, so a spike is visible before you drill into individual events.
  </Step>
</Steps>

## Traces and spans

A second view mode, alongside events, shows execution traces and their individual spans — each row names the action and, when there is one, the tool or model that ran it. Spans can be filtered by duration band (under 10 ms, up to over 10 seconds), which is the fastest way to find what is running slowly across the deployment rather than one conversation at a time.

## Investigate one person

From the Users page's row menu, the activity drawer filters this same audit data to one account — useful when investigating a specific person's actions rather than browsing the whole trail. See [Users and roles](/admin/users-and-roles).

## What is recorded

A row is written for every change made on the audited areas of the platform: the administration pages, personal access tokens, SCIM, secrets, configurations, projects, budgets, the agent governance routes, and the Marketplace featuring and delisting of a listing. A request on these areas refused for lack of permission writes a row too, a read included. A change whose request fails on an unexpected error still writes its row, with status 500. A successful read writes none.

A platform test drives every administration change it can list (the routes that check an administration permission, the central project-settings override, and the write paths of the role separation matrix) as an administrator, and fails when one writes no row. A new administration change mounted outside the audited areas therefore fails the build instead of going unrecorded.

## Role use on administration rows

Every row of a request to the administration surface also records the capacity the person acted in. The page does not show these fields yet; the break-glass review, the reason prompt and the access export will. They are in the `centry.audit_events` table today:

| Column | Meaning |
|---|---|
| `acting_roles` | The administration roles the person held when the request was made, by name. Empty for a credential that acts with no role, such as a personal access token with no administration access or an agent run token. |
| `credential_kind` | The credential that sent the request: `session` (single sign-on), `form` (Form sign-in), `sealed` (a sealed break-glass session), `token` (a personal access token), `native` (the desktop or mobile app), `run` (an agent run token), `system` (a project system token) or `scim` (a SCIM client). Empty when the kind is unknown. |
| `elevation_id` | The break-glass elevation the request was made under, when there was one. |
| `central_override` | The write went through the central override of a platform administrator. |
| `reason_code`, `reason`, `reason_missing` | The reason given for a dangerous or critical action, and whether a required reason was missing. |
| `elevation_flagged` | The action was done under a break-glass elevation, with a permission only the elevation gave, and is one the platform marks for the elevation review. See [what an elevation cannot do](/admin/break-glass#what-an-elevation-cannot-do). |

A request that never checked administration permissions leaves these fields empty.

Every row written since the chain's form `elitea.audit_events.v2` was introduced covers these fields in its tamper-evident chain: a change to one of them breaks the chain's verification. The reason text is the exception: it is never part of the chain and never exported, so it can be erased. Rows written before that release keep their older chain form, which does not cover these fields, and still verify. The [SIEM export](/reference/audit-event-schema#details-for-admin_audit) carries the same fields, without the reason text.

## Reasons for dangerous actions

Every dangerous or critical administration action asks why it is made: deleting or suspending a user, changing who is an administrator, editing the role matrix, an identity provider or SCIM trust change, deleting a project, releasing a legal hold, shortening a retention policy, a guardrail or global provider change, the platform-wide stop, maintenance mode, resetting branding, revoking a credential and a bulk invite. The upgrade note of the release that introduced reasons lists every route and action.

A caller gives the reason in two parts:

| Field | Header (a request without a body) | Meaning |
|---|---|---|
| `reason_code` | `Elitea-Reason-Code` | One of `incident`, `request`, `maintenance`, `correction`, `offboarding` or `other`. |
| `reason` | `Elitea-Reason` | Free text. Required with `other`. In a header it is percent-encoded UTF-8 of at most 500 bytes after decoding; in a body at most 2000 bytes. |

A non-empty body field wins over its header. The permission matrix save reads the headers only. A reason the server cannot accept, such as an unknown code, a header over 500 bytes or a text with a control character, is refused with `400` and the code `reason_invalid`.

The admin audit row records `reason_code`, `reason` and `reason_missing`. The reason code is also recorded on the security event of an access change (`admin.access.changed`); the text is not, so it stays erasable.

During the warning period, until the sunset date of the old permission names, an action without a reason code is still served. Its response carries the header `Elitea-Reason-Missing: 1` and its audit row has `reason_missing` set. A request that is refused, for example for a missing permission, is not flagged. After the sunset date such a request will be refused. Personal access tokens are treated like any other caller. Proxy and ingress access logs must not record the `Elitea-Reason` header: see the [hardening checklist](/deployment/hardening-checklist#identity-and-credentials).

## Export to your SIEM

Audit Trail is the place to look; it is not where evidence should be kept. The hash chain on security audit events makes tampering detectable, but immutability and long retention belong to your SIEM or WORM store. Elitea sends two streams there, in one versioned envelope, [`elitea.audit.v1`](/reference/audit-event-schema):

- **Security audit events** from the security audit outbox (credential decisions, grant, binding, mandate and delegation changes). These exist when enterprise credential governance is on. Approval events (`ai.elitea.security.v1.agent.approval`) are written for every run, with or without governance: one event for each pause, decision, timeout and unattended outcome of a sensitive tool or review node. Each stop by the [agent circuit breaker](/admin/enterprise-controls/runtime-safety#agent-circuit-breaker) writes one `ai.elitea.security.v1.agent.breaker` event (action `agent.breaker.tripped`) with the rule, the observed value and the limit. Each change of the [platform preamble](/admin/enterprise-controls/content-controls#platform-preamble) writes one `ai.elitea.security.v1.config.changed` event (action `config.platform_preamble.revised`) with the revision and the SHA-256 of the text. Each [OIDC relink](/admin/authentication#relink-an-account-after-the-identity-provider-re-created-a-user) writes one `ai.elitea.security.v1.identity.link.changed` event (action `identity.oidc_link.replaced`, `.cleared` or `.added`) with the user and the operator. It holds no subject and no hash of one. Each change of an [agent's memory](/how-tos/agents-pipelines/agent-memory) writes one `ai.elitea.security.v1.agent.memory.changed` event (action `agent.memory.remembered`, `.approved`, `.rejected`, `.edited`, `.archived`, `.deleted`, `.cleared` or `.opted_out`) with the agent, the entry and who made the change; it holds no note text. Each [agent proposal](/how-tos/agents-pipelines/agent-proposals) and each Copy to project writes one `ai.elitea.security.v1.agent.proposal.changed` event (action `agent.proposal.proposed`, `.created`, `.dismissed`, `.seeded` or `agent.copied_to_project`) with the proposal and who made the change; it holds no draft or memory text. Each [workforce](/how-tos/agents-pipelines/agent-workforce) step writes one `ai.elitea.security.v1.agent.workforce.changed` event (action `agent.workforce.proposed`, `.approved`, `.rejected`, `.asked_owner`, `.owner_commented`, `.appealed`, `.appeal_granted`, `.appeal_upheld`, `.reinstated`, `.guard_refused`, and for the automatic policy `.policy_changed`, `.auto_hired`, `.auto_hire_undone`, `.auto_hire_kept`, `.policy_applied`, `.policy_objected`, `.policy_held` or `.orphan_flagged`) with the agent, the proposal and who acted (`policy:<rule>` when the policy acted). Each event carries its position in the tamper-evident chain.
- **The audit trail on this page** (`centry.audit_events`): one event per completed request, scheduled job or admin task.

Two transports are built in, and you can use either or both:

| Transport | Use it when | Set |
|---|---|---|
| **OTLP logs** | Your collector or SIEM speaks OpenTelemetry | `ELITEA_AUDIT_EXPORT_OTLP_ENDPOINT` |
| **Signed webhook** | You run your own receiver, or a SIEM with an HTTP intake | `ELITEA_AUDIT_EXPORT_WEBHOOK_URL` and `ELITEA_AUDIT_EXPORT_WEBHOOK_KEYS_FILE` |

With neither set, export is off, no relay starts and nothing dials out. The full list of settings is in [Post-install configuration](/deployment/configuration#export-audit-evidence-to-a-siem), and the field-by-field schema, a sample event, signature verification and a collector configuration are in the [audit event schema reference](/reference/audit-event-schema).

### What the export guarantees

- **At least once.** A row is marked exported, or a receiver's position in the audit trail advances, only after that receiver accepted it. If your receiver is down, nothing is lost: events wait and are sent in order when it returns. Deduplicate on `event_id`.
- **No row is skipped.** The audit trail is read in commit order: a row is exported only once every transaction that could still add an earlier row has finished. A long-running database write transaction therefore delays export (the lag alert shows it) rather than letting a late row slip past.
- **Each receiver has its own position.** With both transports on, a receiver that is down does not make the healthy one receive the same events again; when it returns it resumes from where it stopped.
- **Asynchronous.** Export runs in background relays. It never slows or fails the request or run that produced the event, and it holds no database transaction open while it calls your receiver.
- **Outages do not drop evidence.** When the webhook receiver refuses a batch as malformed or too large (HTTP 400, 413 or 422), Elitea splits it in halves and sends each again, down to single events, so the other events in the batch are delivered. Only a single event the receiver refuses on its own, on five passes, is dead-lettered, by itself. A receiver that is down, rate limiting, or rejecting your credentials (401, 403, 404, 429, 5xx) is never dead-lettered; the lag alert fires instead. A security audit record that cannot be decoded is dead-lettered alone (sink `decode`) and the rest of its batch is sent. A dead-lettered event is still in its source table and is also listed in `elitea_runtime.audit_export_dead_letters`.
- **Retention never outruns the export.** While audit export is on, the audit trail retention sweep in elitea-scheduler does not delete a row that has not yet reached every receiver, however old it is. If you switch the export off, delete its positions (`DELETE FROM elitea_runtime.audit_export_cursors WHERE stream = 'admin_audit'`) so retention resumes; the scheduler logs a warning while it is holding rows back for a position that has not moved within the retention window.
- **Egress is guarded.** A webhook receiver on a private or loopback address is refused unless `ELITEA_AUDIT_EXPORT_EGRESS_ALLOWLIST` names it. Redirects are never followed.

### Approval events

Each approval event names the actor (`principal_ref`, `user:<id>` or `system:elitea-main`), the outcome (`data.action`, for example `agent.approval.approved` or `agent.approval.unattended_failed`), the tool (`tool_name`), the toolkit (`toolkit_name`) and the SHA-256 digest of the tool arguments (`arguments_digest`). The arguments are never in the event. `invocation_id` is the interrupt id, and `decision_id` is the row of `elitea_runtime.approval_ledger`. See [Approval evidence and unattended runs](/admin/enterprise-controls/runtime-safety#approval-evidence-and-unattended-runs).

### What it does not do

- It does not make the stored events immutable, and it does not retain them for you. Keeping them is your SIEM's job; the shared-responsibility split is in the enterprise controls section.
- Existing audit trail history is not replayed by default. Export starts at the newest row when you turn it on; a row still being written at that exact moment may count as history. Set `ELITEA_AUDIT_EXPORT_AUDIT_EVENTS_FROM` to `beginning` before the first start to send the whole table.
- Audit trail rows are not chained yet, so the `chain` object is present only on security audit events.

### Watch it

elitea-main serves Prometheus metrics for the export on port 9464 (`ELITEA_AUDIT_EXPORT_METRICS_ADDR`): `elitea_audit_export_lag_seconds`, `elitea_audit_export_backlog`, and the `delivered`, `failed` and `dead_lettered` counters. The chart ships a PodMonitor and three alerts, `EliteaAuditExportLag`, `EliteaAuditExportBacklog` and `EliteaAuditExportDeadLettered`, wherever the Prometheus Operator API is served. The same port serves the runtime safety metrics and has their alerts (see [Agent circuit breaker](/admin/enterprise-controls/runtime-safety#agent-circuit-breaker)).
