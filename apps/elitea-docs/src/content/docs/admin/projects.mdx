The admin **Projects** page is the deployment-wide project list. Every project — team or personal — appears here, regardless of who owns it. This is the one place an administrator sees and acts on every project at once, rather than one project's own Settings page at a time.

## Manage an existing project

<Steps>
  <Step title="Find the project">
    Search the table by name.
  </Step>
  <Step title="Suspend or unsuspend it">
    A suspended project's members lose access until it is unsuspended.
  </Step>
  <Step title="Add a project admin, change a member's role, or remove a member">
    All three are in **Manage project member**, from the project's row menu. Type the member's email address: for someone already in the project the dialog offers **Update role** and **Remove from project**. Removing a member keeps their account; only their roles in this project go.
  </Step>
  <Step title="Export">
    **Export to CSV** downloads the current list.
  </Step>
</Steps>

## Administer a project you are not a member of

You do not need to be a member of a project to manage it from here. The **Project administrator** role, and the **Admin** and **Super admin** roles, can:

- **Manage the members of any project** (`projects.members.manage`): list them, add someone, change a role, or remove someone.
- **Read and change the guarded settings of any project** (`projects.settings.view` to read, `projects.settings.manage` to change): the cloud executor, worker egress, AI disclosure, browser and computer-use settings. These five are the only configurations this reaches. A project's credentials, model configurations and toolkit configurations stay with its members.

None of this reaches the project's content: its conversations, artifacts and secret values still need a membership.

Every change you make to a project you are not a member of is recorded in the [audit trail](/admin/audit-trail) as a **central override**, so the project's own members can see that an administrator, not one of them, made it.

You cannot use member management to widen your own permissions: adding yourself to a project, or giving yourself a role there, with permissions you do not already hold is refused. The refusal names two ways in: ask a member of the project who manages its members, or ask an operator of the deployment to run `elitea-main admin-role`. Leaving a project is always allowed.

## Create or delete a project

Both actions run a multi-step process rather than a single database write: creating a project provisions its record, quota, dedicated schema, permission set, a system user and token, vault secrets and storage buckets together (vectors need no per-project store: they live in the platform's vector store, keyed by project); deleting one reverses the same steps, deletes the project's vectors, and ends in dropping the project's schema. Each step's status is tracked individually, and a failed attempt is compensated rather than left half-applied.

<Warning>
Deleting a project destroys its data irreversibly. There is no undo.
</Warning>

## Approving a member's project request

A member does not have to ask you directly. From the project switcher, **+ Request a project** opens a small form — a name and a justification — that files a request the same way the App Requests moderation pattern already handles application access (see [App requests and toolkit types](/admin/app-requests-and-toolkit-types)). It lands on **this same App Requests page**, under the "Project Request" issue type.

<Steps>
  <Step title="Filter the queue">
    On [App Requests](/admin/app-requests-and-toolkit-types), set the Issue Type filter to **Project Request**.
  </Step>
  <Step title="Approve or reject">
    **Approve** runs the same multi-step creation process described above — schema, permissions, vault, the lot — with the requester made the new project's admin. **Reject** requires a reason, exactly like any other app request, and creates nothing.
  </Step>
  <Step title="The requester is notified either way">
    Approving names the new project's id in the queue and in the requester's notification; rejecting delivers your reason.
  </Step>
</Steps>

<Note>
Unlike every other request this queue handles, approving a "Project Request" is not clerical: it is the one decision on this page that creates something rather than only recording an answer.
</Note>
