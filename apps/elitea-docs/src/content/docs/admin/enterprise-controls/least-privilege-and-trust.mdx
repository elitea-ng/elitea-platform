Least-privilege controls limit what an agent can reach and act on, and give reviewers the evidence to keep it that way. This page describes the controls of ADR-0044 that are available now. Delegation narrowing between agents and signed assertions for remote agents are planned in [issue 1501](https://github.com/elitea-ng/elitea-platform/issues/1501).

## Connector approval

### The risk

A toolkit type or an MCP server gives an agent a new way to read data and act. When any project member can add one, the platform's reach grows without anyone reviewing what the connector can do, which hosts it calls and which data it touches. An MCP server can also change the tools it offers after it was added.

### What is enforced

A platform setting, **catalogue mode**, has two values:

- `open` (the default): today's behaviour. Toolkit types are offered as the [toolkit type policy](/admin/app-requests-and-toolkit-types#control-which-toolkit-types-are-offered) allows, and MCP servers can be added freely.
- `approved_only`: a toolkit type, a prebuilt MCP server or a custom MCP server URL is usable only after a **connector request** for it is approved. The governed agent profile forces this mode, and so does every run that carries a governed security context.

In `approved_only` mode:

- **Unapproved connectors are refused everywhere.** They are left out of the selection lists, and creating, forking or updating a toolkit that uses one is refused with `403 connector_not_approved`, naming the connector to request. When an agent version is frozen for a run, unapproved connectors are dropped, and runtime admission refuses any command that still names one (`CONNECTOR_NOT_APPROVED`), including toolkits configured before the mode was switched.
- **Approval needs a second person.** The approver holds `connector.approve` (granted to the platform `super_admin` and `admin` roles) and cannot be the requester; the database refuses a self-approval.
- **Approval grants and allowlists in one step.** In one transaction it writes the toolkit type grant for the requested projects and adds the declared hosts to the [worker egress allowlist](#worker-egress-allowlist) of those projects (or to the platform allowlist for a platform-wide request), with a configuration revision naming the approver.
- **A custom MCP server's tools are pinned at approval**, by name and schema digest. Tools the server adds or changes later are hidden from discovery and the tool lists, and a call to one is refused, until a new request for them is approved.
- **Optional architecture review.** With **Require architecture attestation** on, a request can be approved only when a valid `architecture` [attestation](/admin/enterprise-controls/agent-lifecycle#attestations) for it exists (subject `connector`, subject id = the request id, recorded in the requesting project).

A connector request records the requester, the target (toolkit type, prebuilt MCP server or custom URL), the projects, the declared tools with their categories, the egress hosts, the data classes it touches and a justification. Its states are draft, submitted, approved, rejected and withdrawn.

### Configure and use

<Steps>
  <Step title="Seed requests for what is in use">
    Before switching modes, open **Admin › Connector requests** and select **Create requests for connectors in use**. It files a submitted request for every connector configured in any project, with the projects using it, the tools their toolkits select (a custom MCP server's tools as its last **Load tools** stored them, so they can be pinned) and the hosts of their URL settings. A connector that already has an open or approved request is skipped, so running it again is safe. Tool categories are not known from a toolkit's settings, so every tool starts as `write`. Review and approve them. The administrator who created them cannot approve them.
  </Step>
  <Step title="Switch the mode">
    Open **Configuration › Connector Catalogue** and set **Mode** to `approved_only`. The page warns you how many connectors in use still have no approved request; each of them stops working at once.
  </Step>
  <Step title="Request a connector (project members)">
    When a toolkit or MCP server is refused, select **Request connector**. For MCP, **Load tools** prefills the discovered tools and their schemas. Enter the projects, hosts, data classes and justification, and submit. Follow the request on the toolkit page.
  </Step>
  <Step title="Approve or reject (connector approvers)">
    Open **Admin › Connector requests**, review the declared tools, categories, hosts and data classes, and approve, or reject with a reason.
  </Step>
</Steps>

<Warning>
The worker must be upgraded together with elitea-main before you rely on MCP tool pinning: an older worker does not apply the pinned tool list, so only direct calls are checked.
</Warning>

### Evidence

Each state change of a request (created, submitted, withdrawn, approved, rejected) is a security audit event of type `ai.elitea.security.v1.connector.approval`, with the actor, the request and its target, and is exported with the rest of the [audit evidence](/reference/audit-event-schema). The request itself, with who approved it and when, stays in `centry.connector_requests`.

### Customer responsibility

- The architecture or security review behind an approval happens in your own process; record its result as an attestation.
- Decide who holds `connector.approve`, and keep requesters and approvers apart.


## Worker egress allowlist

### The risk

An agent's tools make outbound HTTP calls from the worker: web fetches, toolkit clients (Jira, Confluence, GitHub and others), OpenAPI tools, remote MCP servers and index runs. Without a restriction, a tool can reach any public host. A prompt injection, a malicious document or a misconfigured toolkit can then send data to a host that nobody approved. The private, link-local and cloud-metadata ranges were already refused for web fetches, but any public host was allowed.

### What is enforced

The platform has a **worker egress mode**:

| Mode | What a run may reach |
| --- | --- |
| `open` (the default) | Any public host. This is the behaviour of earlier releases. |
| `allowlist` | Only the hosts in the run's allowlist. Any other host is refused. |

A run uses `allowlist` mode when the platform's mode is `allowlist`, or when the run is governed (credential governance is on; see [Credential governance](/deployment/credential-governance)). A governed run always uses `allowlist`, whatever the platform's mode is.

The main service builds the allowlist for each run when it sends the run to a worker. The allowlist is the union of:

- the **platform entries**, set under **Configuration › Worker Egress**;
- the **project entries**, from the project's `worker_egress` setting;
- the host of every URL that the run's toolkits, MCP servers and configurations are configured with (for example, a Jira toolkit's base URL);
- the fixed API hosts that a toolkit type always calls, even when its settings do not name them (for example, `api.figma.com` for Figma, `graph.microsoft.com` for SharePoint, and `*.googleapis.com` for Google Cloud toolkits);
- for an OpenAPI toolkit, the host of its specification URL and the host that its operations call: the `base_url` setting when it is set, otherwise the first `servers` entry of the specification, with each `{variable}` replaced by its `default`;
- for a GitHub toolkit with the base URL `https://api.github.com`, the host `github.com`, which the pull-request push of a workspace uses (a GitHub Enterprise base URL already names its push host);
- for a governed run, the target hosts of the credentials that the run may use (for example, Microsoft Graph for a SharePoint credential).

Only toolkit and configuration **settings** add hosts. User input, chat history and tool arguments never add a host, so nothing that a user or a document types can widen a run's allowlist. A project entry only adds hosts to that project's runs. It does not change the mode, which is the platform's decision.

The allowlist travels inside the signed worker command, so a worker cannot widen it. The worker enforces it on every outbound connection of the run: web fetches and every redirect hop, all toolkit clients, OpenAPI tools, delegated sign-in token calls and metadata discovery, remote MCP servers, index runs, and the pull-request push of a workspace. A client opened outside any run is refused too: the worker has no unrestricted default. A refused call fails with the tool error `egress_host_not_allowed`, which names the host. The agent sees this error and can report it. The call never fails silently.

The allowlist narrows the existing rules. It never widens them. For web fetches, private, link-local, cloud-metadata and reserved addresses stay refused in every mode, even if an entry names them.

#### Entry format

Each entry is one of:

| Entry | Matches |
| --- | --- |
| `api.example.com` | That host, on any port |
| `api.example.com:8443` | That host on that port only |
| `*.example.com` | Every subdomain of `example.com` (not `example.com` itself) |
| `*.example.com:443` | Every subdomain, on that port only |
| `203.0.113.0/24` | Every address in that block |

The platform list holds at most 512 entries, and a project list at most 256. A run's assembled allowlist holds at most 1024 entries and 24 KiB.

#### When a policy cannot be built

If the allowlist for a run cannot be built, the run fails at once. It is not retried, and it does not run with a shorter list. This happens when:

- a platform or project entry is malformed;
- the assembled list is longer than 1024 entries or larger than 24 KiB;
- a governed run's security context is missing.

The run fails with the code `EGRESS_POLICY_INVALID`. Its message names the bad entry and who must correct it, for example:

```text
The platform's worker egress allowlist entry "https://jira.example.com" is not a valid host, host:port, *.domain or CIDR block (...). A platform administrator must correct it under Configuration, Worker Egress.
```

A chat answer shows this as `error_code: egress_policy_invalid`. A synchronous toolkit tool call answers HTTP 422 with `reason: egress_policy_invalid`, and nothing is admitted. Configuration validation makes no network call, so it is never refused for its policy. If the main service only could not read a source (for example, the database was briefly unavailable), the dispatch is retried until the run's deadline.

#### Limits

- Endpoints that the operator configured for the worker itself, such as web-search provider origins in `ELITEA_WEB_EGRESS_ALLOWLIST`, are not judged by this policy, because the main service cannot list them. They are still reported as reached.
- Toolkit clients reach operator-approved hosts, including hosts on your private network, so they never had the private-address guard of web fetches. For them, the allowlist is the only egress check inside the platform.
- The task status of a run that failed with `EGRESS_POLICY_INVALID` can show `DEADLINE_EXCEEDED`. The run's events, the chat answer and index records show the refusal code.
- A refused policy is settled at the next dispatch pass. A chat answer and a synchronous tool call report it immediately.
- A governed toolkit that holds only a credential digest uses the credential grants that exist when the run is dispatched.
- The worker's summary does not count bytes (`bytes_up` and `bytes_down` are 0). If the worker restarts before it sends the summary, or if the run is not settled within 12 hours, that summary is lost. The refusal itself still reaches the agent and the run's events.
- An index run counts each request to a host, not each document.
- A remote MCP server with no selected tools is checked when the run starts, and appears only in the refused hosts if it is refused.
- The main service does not download an OpenAPI specification that a toolkit names by URL. If that specification's first server is an absolute URL on a different host, set the toolkit's `base_url`, or add that host to the platform or project entries. A relative server, or no server, uses the host of the specification URL, which is added automatically.

### Configure and use

<Steps>
  <Step title="See which hosts your agents reach">
    Open **Configuration › Worker Egress** in the admin console. The panel under the form lists the hosts that runs reached and the hosts that were refused, per project and agent, for the last 7, 30 or 90 days. It reads the worker's summaries, which are kept 30 days by default. Sandbox runs go through the egress proxy, which has its own per-project allowlists, so their hosts are not listed here; the API's `source=proxy` returns them.
  </Step>
  <Step title="Seed the platform allowlist">
    Select **Copy as allowlist**. This copies the reached hosts as entries, one per line: a bare host (any port) where only ports 80 and 443 were used, and one `host:port` entry for each port otherwise. Remove the hosts that you do not approve, and paste the rest into the **Platform Allowlist** field. Toolkit base URLs, and the fixed API hosts of each toolkit type, are added to each run automatically, so you do not need to list them.
  </Step>
  <Step title="Add project entries if necessary">
    A project that needs more hosts than the platform list can add its own. A project admin (permission `models.project_settings.edit`) creates one configuration of type `worker_egress`:

    ```bash
    curl -X POST "$DEPLOYMENT_URL/api/v2/configurations/configurations/$PROJECT_ID" \
      -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
      -d '{"elitea_title":"worker_egress","label":"Worker egress","type":"worker_egress",
           "section":"project_settings","data":{"allowlist":["api.partner.example","*.internal.example.com"]}}'
    ```
  </Step>
  <Step title="Switch the mode">
    Set **Mode** to `allowlist` and save. Each replica of the main service reads the section again after at most 5 seconds, so new runs use the allowlist within 5 seconds. If the database cannot be read, a replica keeps the last value that it read and tries again after a short wait (from 0.5 seconds, doubled after each failure, up to 30 seconds). Runs in flight keep the policy that they started with.
  </Step>
  <Step title="Watch the refused hosts">
    For the first days, check the refused hosts in the panel. A refused host that a real workflow needs is either added to the platform or project list, or is a call that the allowlist correctly stopped.
  </Step>
</Steps>

To find the same data with the API, call `GET /api/v2/admin/worker_egress/hosts` (permission `configuration.governance`). The parameters are `days` (1 to 90, default 30), `source` (`worker`, `proxy` or `all`) and `project_id`.

### Evidence

- **One audit event per run turn.** The audit trail gets an event of type `tool` with entity type `execution` and the run's execution id as entity name. Its action lists the hosts reached and refused, for example `worker egress: reached api.example.com:443, jira.example.com:443; refused paste.example:443 (host_not_allowed x2)`. The structured log line `egress_audit.turn_summary` carries the full summary. These events go to your SIEM with the other audit events (see [Audit evidence and retention](/admin/enterprise-controls/audit-evidence-and-retention)).
- **The summaries table.** `elitea_runtime.egress_run_summaries` keeps each run's summary for 30 days (`ELITEA_EGRESS_AUDIT_RETENTION_DAYS`, at most 365). Rows written by the worker have a replica key `worker:<command id>`.
- **The configuration history.** Every save of the platform section (`/api/v2/admin/…`) and of a project's `worker_egress` setting (`/api/v2/configurations/…`) is recorded as an `api` audit event with the user, the route and the result. The event does not include the entries; read the current list from the section.
- **The run's events.** A run refused for its policy has an `execution.failed` event with the code `EGRESS_POLICY_INVALID`.

### Customer responsibility

- Decide which public hosts your agents may reach, and review the platform list on a schedule.
- Seed the allowlist from the observed hosts before you switch to `allowlist`, and watch the refused hosts after the switch.
- Keep network egress control at your perimeter as well. This allowlist is enforced inside the worker; a firewall or egress gateway is your independent second layer.
- Keep the list of hosts that the operator configured for the worker (web-search providers, model endpoints) under your change process, because this policy does not judge them.

## Credential inventory

### The risk

Credentials an agent can use (personal access tokens, toolkit secrets, OAuth tokens, governed credential grants) accumulate. Without one view, nobody can tell which ones are still used, who owns them, and which agents depend on them, so unused credentials stay valid indefinitely.

### What is available

**Admin › Credential inventory** (permission `credentials.inventory.read`) lists every credential an agent can use, never its value:

| Kind | Examples |
| --- | --- |
| Personal access token | Tokens users and integrations authenticate with |
| Toolkit secret | Secrets referenced by a toolkit's settings |
| MCP OAuth token | Tokens an MCP server's OAuth flow issued |
| Provider OAuth grant | OAuth grants for model or service providers |
| Credential reference and use grant | Governed credentials (ADR-0039) |

Each row shows the owner, project, scope, creation, expiry, **last used**, the agents that use it, and whether it is **stale**. Filter by kind, project and stale.

**Last use** is recorded when a token authenticates, when a toolkit secret or OAuth token is resolved for a run, and when the credential broker redeems a reference. It is precise to one hour: each credential is written at most once an hour.

**Staleness.** A daily routine, `main.credential_staleness`, flags credentials unused for longer than the threshold (90 days by default) and notifies their owners once. A credential with no recorded use counts from the later of its creation and the first time the routine saw it, so an upgrade does not flag every older token at once.

### Configure and use

Open **Configuration › Credential Review** (permission `credentials.inventory.manage`):

| Setting | Default | Meaning |
| --- | --- | --- |
| `stale_after_days` | 90 | Days without use before a credential is stale |
| `stale_action` | `flag` | `flag` only flags and notifies. `revoke` also revokes stale personal access tokens and credential use grants. |
| `trimming_window_days` | 30 | The window the [permission trimming report](#permission-trimming) compares against |

<Warning>
`revoke` deletes stale personal access tokens and revokes stale credential grants without asking. Run with `flag` first and review the list.
</Warning>

To revoke one credential by hand, select **Revoke** on its row (permission `credentials.inventory.manage`) and enter a reason. Toolkit secrets, MCP and provider OAuth tokens and credential references are issued by other systems: Elitea flags them, but revoking them is answered with `409 credential_not_revocable`; rotate or revoke them where they were issued.

### Evidence

- Audit events `credential.stale.flagged` and `credential.revoked` (with the reason and who revoked it).
- Owner notifications `credential_stale` and `credential_revoked_stale`.

## Permission trimming

### The risk

Agents are granted more than they use: a toolkit added for a test, a tool nobody calls, a credential grant or an egress host left after a change. Every unused grant is reach an attacker or a confused agent could use.

### What is available

The trimming report compares what each agent is granted (tools, toolkits, credential grants and their scopes, egress hosts) with what its [run step records](/admin/enterprise-controls/audit-evidence-and-retention#run-step-records) and egress summaries show it used in the window (30 days by default). Each grant shows its uses and last use; one not used in the window is a **removal candidate**.

- **Per agent:** the **Permission trimming** tab in the agent's **⋮ › Governance** dialog (permission `agents.trimming.manage`, held by the project `admin` role).
- **Across projects:** **Admin › Permission trimming** (`credentials.inventory.read` to read, `credentials.inventory.manage` to remove).

**Remove** acts on one item at a time through the normal edit path, with its validation: a tool or toolkit is removed from the agent's draft version, a credential grant is revoked, and an egress host is removed from the project or platform allowlist (which also needs `models.project_settings.edit` for a project entry). Published versions are not changed; publish the edited draft through the usual [approval](/how-tos/agents-pipelines/publishing#publish-with-approval).

A weekly routine, `main.permission_trimming`, recomputes the report and notifies the agent's owners (its registry owners, else its author) of **new** candidates only.

### Evidence

Each removal is an audit event `permission.trimmed` with the agent, the item and who removed it. Owner notifications are `permission_trimming_candidates`.

### Customer responsibility

- Decide the window that reflects how your agents are used; a grant used only at quarter end needs a longer window.
- Act on the report: the platform lists candidates and removes on request, it does not remove on its own.

## Entitlement export for access reviews

### The risk

An access review asks who holds which role, where, and what that role allows. Without an export, a reviewer reads the Users and Roles pages by hand, and a governance tool cannot run a campaign at all.

### What is available

- **CSV and JSON download.** `GET /api/v2/admin/entitlements` (permission `entitlements.export`, held by the platform `super_admin` and `admin` roles) answers one row per user, scope (platform, project or agent), role, capability and how it is held (`role`, `owner` for agent registry owners). `format=csv` streams every row from one snapshot as RFC 4180 CSV; `format=json` pages with `limit` and `offset`. Filters are `user_id` and `project_id`. The admin console's **Users** page has an **Export entitlements** button for the CSV.
- **A read-only SCIM 2.0 tree** at `/api/v2/scim/v2/entitlements` for identity governance tools: `/Users` with their groups, roles and grants, `/Groups` (one per platform role and per project role), and the discovery documents. Paging is `startIndex` and `count`; `filter` takes `userName eq "…"` and the other attributes in the discovery documents. Write requests answer `405`.
- **Capabilities, not only role names.** Each role's permissions are mapped to governance capabilities such as `configure_agents`, `approve_change_requests`, `attest`, `approve_connectors` and `read_run_evidence`.

### Configure and use

The SCIM tree uses the same SCIM client credential as provisioning (see [Authentication](/admin/authentication)), but no client can read it until you allow it:

<Steps>
  <Step title="Create or choose a SCIM client">
    Create a SCIM client for the governance tool on **Configuration › Authentication**, or choose an existing one. Note its id.
  </Step>
  <Step title="Allow the client">
    Open **Configuration › Entitlement Export** (permission `entitlements.export`) and add the client id to **SCIM Clients Allowed** (`scim_client_ids`). The list is empty by default, and every client that is not on it gets `403` with a SCIM error on every path of the tree. Provisioning is not affected.
  </Step>
  <Step title="Point the governance tool at the tree">
    Configure the tool with the base URL `https://<host>/api/v2/scim/v2/entitlements` and the client's credential.
  </Step>
</Steps>

The list is read on every request, so removing an id stops that client at once.

### Export format

**CSV columns**, one row per user, scope, role, capability and grant path:

| Column | Meaning |
| --- | --- |
| `user_id`, `user_name`, `display_name` | The account |
| `user_active` | `false` for a suspended user; their grants are dormant |
| `scope_type` | `platform`, `project` or `agent` |
| `scope_id` | The platform mode (`administration`, `developer`), the project id or the agent id |
| `scope_name` | Its display name |
| `project_id` | The project of a project or agent scope; empty for platform rows |
| `scope_active` | `false` for a suspended project |
| `role` | The role, or the registry owner role (`business_owner`, `technical_owner`) |
| `capability` | One governance capability the role carries; empty when the role carries none, so every role holder still appears |
| `permissions` | The permissions behind the capability, space-separated |
| `granted_via` | `role` or `owner` (agent registry ownership) |

The file is UTF-8 with CRLF line ends and a header row. Fields with commas, quotes or line breaks are quoted, and a cell starting with `=`, `+`, `-` or `@` is prefixed with `'` so spreadsheets do not run it. The `X-Entitlement-Rows` response header carries the number of data rows, so an import can detect a cut-off file.

```csv
user_id,user_name,display_name,user_active,scope_type,scope_id,scope_name,project_id,scope_active,role,capability,permissions,granted_via
101,alice@example.com,Alice,true,platform,administration,Platform (administration),,true,admin,suspend,safety.suspend,role
101,alice@example.com,Alice,true,project,201,Alpha,201,true,admin,approve_change_requests,models.applications.governance,role
101,alice@example.com,Alice,true,agent,31,Support Bot,201,true,technical_owner,edit_agent_registry,,owner
102,bob@example.com,Bob,true,project,201,Alpha,201,true,viewer,,,role
```

**Capabilities:** `configure_agents`, `configure_toolkits`, `configure_credentials`, `approve_credentials`, `publish_agents`, `approve_publication`, `approve_change_requests`, `override_release_gates`, `edit_agent_registry`, `attest`, `mark_recertification_due`, `suspend`, `override_caps`, `approve_connectors`, `manage_retention`, `manage_legal_hold`, `read_run_evidence`, `read_audit_trail`, `review_credentials`, `revoke_credentials`, `trim_agent_permissions`, `manage_access`, `manage_secrets`, `manage_agent_identity`, `approve_agent_identity`, `manage_projects`, `administer_platform`, `export_entitlements`. A test fails the build when a new permission is neither mapped to a capability nor marked as not relevant to access reviews, so the export cannot silently miss one.

**SCIM resources.** A `User` carries `groups` (its role groups), `roles` (`project:<id>:<role>`, `agent:<project>/<agent>:<role>`, `platform:<mode>:<role>`), `entitlements` (`<scope>:<capability>`) and the extension `urn:elitea:params:scim:schemas:extension:entitlements:2.0:User` with every grant as in the CSV. A `Group` (`platform-role-<id>` or `project-role-<id>`) lists its `members` and, in its extension, the scope, role, capabilities and permissions. `attributes` and `excludedAttributes=members` are honoured.

```json
{
  "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User", "urn:elitea:params:scim:schemas:extension:entitlements:2.0:User"],
  "id": "101",
  "userName": "alice@example.com",
  "active": true,
  "groups": [{ "value": "project-role-301", "display": "project Alpha / admin", "type": "direct" }],
  "roles": [{ "value": "project:201:admin", "display": "admin on project Alpha", "type": "project" }],
  "entitlements": [{ "value": "project:201:approve_change_requests", "type": "approve_change_requests" }]
}
```

A Group shows what its role grants on its own. The per-user rows also apply the rule that a project's own role definition takes precedence over the platform default role of the same name, so use the User resources or the CSV for the effective grants.

### Evidence

- **Every export is audited** in `centry.audit_events` before any row is sent: entity type `entitlements`, entity name `csv`, `json` or `scim`, the row count in the action, and the administrator or `scim:<client>` as actor. When the event cannot be written, the export is refused with `503`.
- **Refused SCIM reads** (`403`) are recorded as `api` audit events like other refused requests under `/api/v2/scim/`.
- **Changes to the allowed clients** are recorded as `api` audit events with the user, the route and the result, like every other configuration save.

### Customer responsibility

- Decide which governance tools may read the entitlement tree, and review the allowed clients on a schedule.
- Run access reviews on the exported data, and remove the roles that a review rejects.
