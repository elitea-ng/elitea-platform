Runtime safety controls act on agent execution while it runs, not on configuration. This page describes the controls of ADR-0041.

## Suspension and kill switch

### The risk

An agent can start to do damage after it is deployed. For example, it can send repeated messages to customers, call a toolkit with a leaked credential, or use a large part of the budget in a loop. Deleting the agent or editing its configuration is too slow, and it does not stop the runs that are in flight. An operator must be able to stop the execution immediately, at the correct scope, and start it again when the incident is closed.

### What is enforced

A **suspension** has one of four scopes:

| Scope | What it stops | Who can create it |
| --- | --- | --- |
| `agent` | Every run of one agent in its project | A project admin of that project, or a platform administrator |
| `project` | Every run in one project: agent chats, pipeline runs, index runs, direct toolkit runs | A project admin of that project, or a platform administrator |
| `toolkit_type` | Every call of one toolkit type (for example `github`) on the platform | A platform administrator |
| `platform` | Every run on the platform | A platform administrator, who must also type `STOP` |

When a suspension is created, the platform does these steps:

1. **Admission refuses new runs.** Every path that starts or continues a run checks the active suspensions before it writes anything: a chat turn, a continue or regenerate, a pipeline trigger or schedule, an index run, a direct toolkit run, a toolkit tool call, a desktop child turn, and the support assistant. A covered run is refused with HTTP 409 and the typed error `execution_suspended`. The error names the scope, but not the reason:

   ```json
   {
     "error": "An administrator stopped this agent.",
     "code": "execution_suspended",
     "message": "An administrator stopped this agent.",
     "scope": "agent",
     "scope_key": "31",
     "suspension_id": 12
   }
   ```

   A scheduled pipeline run that is refused is recorded as `failed` with the detail `skipped: an administrator suspended execution (execution_suspended)`.

2. **Runs in flight are cancelled.** In the same database transaction that saves the suspension, the platform sets the desired state of each covered run to `CANCELLED`. This is the same cancel that the admin **Tasks** page uses. The worker stops the run at its next lease renewal. The `cancelled_runs` field of the suspension gives the number of runs it cancelled. A platform suspension cancels every run in flight. A `toolkit_type` suspension cancels every run in flight that holds a toolkit of that type, including toolkits of the run's sub-agents: each run records its toolkit types when it is admitted. A run that is being admitted while the suspension is saved is either refused or cancelled: admission and the suspension are serialised in the database, so no run escapes both.

3. **Toolkit calls are refused at the worker.** For the `toolkit_type` scope, the suspended types are frozen into the guardrail policy of each new run. The worker removes the tools of a suspended type from the agent's tool set, and it refuses a call of that type with the code `execution_suspended`. Standalone toolkit tool calls of that type are refused at admission.

Each replica of the main service keeps a copy of the active suspensions. A change is sent to all replicas on the NATS subject `elitea.rt.v1.safety.suspension`, and each replica also reads the table again after 10 seconds at most, so a lost message does not extend the 10-second stop target. If a replica cannot read the table:

- with a copy that it read before, it keeps that copy and tries again after one second;
- with no copy (for example, just after it started), it refuses every run with HTTP 503 `suspension_state_unavailable`. It does not admit a run that a suspension could cover.

A suspension stays active until it is resumed. Resuming lets new runs start again. Runs that were cancelled stay cancelled; start them again if necessary.

#### Limits

- An agent suspension cancels only the runs that were admitted after migration 0194, because older runs do not record their agent. The project and platform scopes cancel all runs.
- A run admitted before migration 0201 did not record its toolkit types. A `toolkit_type` suspension reads them from the run's stored input, which names only the run's own toolkits, not those of its sub-agents. To be sure that such a run stops, also suspend its project or the platform.
- A suspension, like a run cap, takes effect at the run's next lease renewal, not instantly.
- A cancelled run ends with the state `cancelled`, not with `execution_suspended`.
- Desktop local agent loops run on the user's computer. A suspension refuses their next cloud-side turn, but it does not stop a loop that is running locally.

### Configure and use

**Stop one agent.** Open the agent, then select **Stop agent** next to **Delete**. Type the reason, then select **Stop agent** in the dialog. The page then shows **Agent stopped** with **Resume agent**. If the whole project is suspended, the page shows **Project stopped**.

**Every scope.** Open **Admin › Kill switch**. The page lists the active suspensions and refreshes every ten seconds. Select **Suspend**, then select the scope, the target, the reason, and who can resume it. To stop the whole platform, select the scope **Platform** and type `STOP`. Select **Resume** on a row to end that suspension. Turn on **Show resumed suspensions** to see the history.

**API.** The same operations are available with a personal API token:

| Method and path | Purpose |
| --- | --- |
| `GET /api/v2/admin/execution_suspensions?active=true` | List the suspensions (filter `project_id` is optional) |
| `POST /api/v2/admin/execution_suspensions` | Create a suspension of any scope |
| `POST /api/v2/admin/execution_suspensions/{id}:resume` | Resume a suspension |
| `GET /api/v2/elitea_core/execution_suspensions/prompt_lib/{project_id}` | List the suspensions of a project |
| `POST /api/v2/elitea_core/execution_suspensions/prompt_lib/{project_id}` | Suspend an agent of the project, or the project |
| `POST /api/v2/elitea_core/execution_suspensions/prompt_lib/{project_id}/{id}:resume` | Resume a suspension of the project |

The body of a create is `{"scope", "project_id", "application_id", "toolkit_type", "reason", "resume_requires", "confirm"}`. Only the fields of the scope are necessary. `project_id` and `application_id` must be between 1 and 2147483647; any other value is refused with 400. A second suspension of the same target is refused with 409 `already_suspended`, and the answer includes the active suspension.

**Self-test.** The routine `main.kill_switch_selftest` runs once a day by default. It suspends a synthetic agent, checks that admission refuses it within the stop target of 10 seconds, resumes it, and checks that admission accepts it again. It does not stage a real run. It does not run while maintenance mode is on. Change its schedule, or turn it off, in **Admin › Schedules & Tasks**. Each pass writes an audit event. A successful pass sets the Prometheus gauge `elitea_kill_switch_selftest_last_success_timestamp` (Unix seconds). Alert when the gauge is older than two schedule periods.

### Roles

The permission `safety.suspend` controls every route. Migration 0194 grants it to:

- the platform roles `super_admin` and `admin` (the administration mode): every scope, on the admin routes;
- the project role `admin` (the default mode), and each saved project `admin` role: the `agent` and `project` scopes of that project, on the project routes.

Each suspension has a **resume rule**:

| `resume_requires` | Who can resume |
| --- | --- |
| `any_admin` (default) | Any caller with `safety.suspend` on a surface that can see the suspension |
| `governance_role` | A platform administrator only |
| `two_person` | A platform administrator who is not the person who created the suspension. The database also enforces this rule. |

A project admin can resume only an `any_admin` suspension of their own project. A suspension made by a platform administrator for a project is visible on the project routes, but its rule can keep the project admin from resuming it.

### Evidence

Every create and resume is written to the audit trail (`centry.audit_events`) as part of the request record. The action is `safety.suspension.created` or `safety.suspension.resumed`, the entity type is `execution_suspension`, and the entity name is the scope and its key. Example:

```json
{
  "timestamp": "2026-10-28T09:15:02.418Z",
  "user_id": 4,
  "user_email": "ops@example.com",
  "project_id": 7,
  "event_type": "api",
  "action": "safety.suspension.created",
  "http_method": "POST",
  "http_route": "/api/v2/elitea_core/execution_suspensions/prompt_lib/{projectID}",
  "status_code": 201,
  "is_error": false,
  "entity_type": "execution_suspension",
  "entity_id": 12,
  "entity_name": "agent:31"
}
```

The self-test writes a `schedule` event with the action `safety.kill_switch.selftest`, for example the entity name `refused=true resumed=true stop_latency_ms=3`, and `is_error` set when a pass fails. The table `elitea_runtime.execution_suspensions` keeps every suspension with its reason, the user who created it, the time, the number of runs it cancelled, and who resumed it, when, and why. Rows are not deleted.

### Customer responsibility

- Decide who in your organization can stop and resume execution, and give `safety.suspend` only to those people. Remove it from project roles if only the platform team may stop agents.
- Use `two_person` for platform suspensions if your change process needs a second approver to restart production.
- Monitor `elitea_kill_switch_selftest_last_success_timestamp` and the `safety.kill_switch.selftest` audit events.
- Keep the [emergency stop runbook](/deployment/emergency-stop-runbook) in your incident procedure, and practise it.
- After you resume, start again the runs that were cancelled, if they are still necessary.

## Whole-run time cap

### The risk

The worker limits the time of each turn of a run, but a long autonomous run can continue for many turns. Without a limit on the whole run, a looping agent can keep running and spending for days.

### What is enforced

Under **Configuration › Run Caps**, a platform administrator (permission `configuration.governance`) sets **Maximum Run Time (seconds)**: 0 (off, the default), or 60 to 604800 (7 days). It applies to agent runs.

The time counts from the run's original start. A resumed run keeps that start, so time spent waiting for a human approval counts too. The main service checks the cap whenever the worker renews the run's lease or reads its desired state. A run past the cap is cancelled with the reason `cap_reached`, and the worker stops it on the same call. When the cap is off, the check adds no database query.

The run ends with the state `cancelled`. Its event and the agent's answer carry a typed error:

```json
{ "code": "CAP_REACHED", "cap": "max_wall_seconds", "retryable": false }
```

The answer is marked as an error, so the user sees why the run stopped. The metric `elitea.runtime.run_caps.reached` with the label `cap=max_wall_seconds` counts the runs stopped by the cap.

#### Limits

- The cap is one platform-wide value. Caps per agent or per project, and caps on tool calls, spend and records read, are planned ([issue 1498](https://github.com/elitea-ng/elitea-platform/issues/1498)).
- The cap takes effect at the next lease renewal, so a run can pass it by up to one renewal interval.

### Customer responsibility

- Choose a cap that is longer than your longest legitimate run, including the time that people take to approve steps.
- Alert on `elitea.runtime.run_caps.reached` if a stopped run needs attention.

## Approval evidence and unattended runs

### The risk

A sensitive tool or a pipeline review node pauses a run until a person approves the step. An auditor must be able to prove who approved each step, what the step was, and when. A record that only the chat window shows changes with the conversation, and it is not tamper-evident. A run that a schedule or a webhook starts has no person to approve a step. If such a run approves a step on its own, the approval control does not apply to automated runs.

### What is enforced

**Every approval is a ledger row.** The table `elitea_runtime.approval_ledger` (migration 0211) records each event of each approval:

| Phase | Outcomes |
| --- | --- |
| `pause` | `paused`: the run stopped at the step |
| `notice` | `unattended_waiting`: an unattended run waits, and the platform notified its owner |
| `decision` | `approved`, `rejected`, `edited`, `answered`, `other`, `timed_out`, `cancelled`, `superseded`, `unattended_failed`, `unattended_skipped` |

Each row records the actor (a user, or the platform), the tool, the toolkit, the digest of the tool arguments, the decision and the time. The digest is `sha256:` followed by the SHA-256 of the canonical JSON of the arguments. The arguments themselves are not recorded. Rows cannot be changed: a database trigger refuses an update.

The platform writes a row on every path that pauses or decides a step:

- a decision in the chat window, or with the continue API (a pause of the agent itself);
- a decision on one card of a parallel or fan-out run, with the per-interrupt decisions API;
- a confirmation of a sensitive tool from the desktop app;
- a Stop, a regenerate or a new message that ends a pause (`cancelled` or `superseded`);
- the end of a run that leaves a card open (`cancelled`, reason `run_ended`);
- the expiry of an unattended wait (`timed_out`).

The row is written in the same database transaction as the decision. If the row cannot be written, the decision is refused.

**One winner.** A step has one decision. When two people decide the same step at the same time, the platform applies one decision, and the other person gets HTTP 409. A person who answers after the step was decided, timed out or skipped also gets HTTP 409.

**Every row is an audit event.** In the same transaction, each row is written to the security audit outbox as one `ai.elitea.security.v1.agent.approval` event, at the next position of the hash chain of the project. These events are written for every run. They do not need the credential governance profile.

**The chat window shows the ledger.** The pending steps in the message metadata (`hitl_interrupts`) are a view for the UI. The ledger is the record. Each pending step in the chat window has a `pause` row, and each decided step has a `decision` row.

**Unattended runs never approve.** When a run that a schedule or a webhook trigger started gets to a step that needs approval, the platform does one of three things, set by `on_approval_required`:

| Value | What happens | Ledger outcome |
| --- | --- | --- |
| `fail` (default) | The run ends with the error `approval_required_unattended`. | `unattended_failed` |
| `skip` | The platform refuses the step. The model receives a tool result that says the step was skipped because the run has no approver, and continues without the step. | `unattended_skipped` |
| `notify_and_wait` | The run pauses, and the run's owner gets a notification. The owner can approve or reject the step in the conversation. If nobody answers in time, the run ends with the error `approval_timed_out`. | `unattended_waiting`, then the decision or `timed_out` |

No value approves a step. A `skip` of a step that has no refusal action, and an unattended pause that also waits for a credential authorization, use `fail`.

### Configuration

**Platform default.** Open **Configuration › Approvals** (permission `configuration.governance`):

| Field | Values | Default |
| --- | --- | --- |
| **Unattended Default** (`approvals.unattended_default`) | `fail`, `skip`, `notify_and_wait` | `fail` |
| **Unattended Wait (hours)** (`approvals.unattended_wait_hours`) | 1 to 720 | 24 |

**Per schedule and per trigger.** Set `on_approval_required` on the schedule or on the trigger of a pipeline version. If you do not set it, the platform default applies. The settings read shows the value that applies.

| Method and path | Field |
| --- | --- |
| `PUT /api/v2/pipeline_schedules/prompt_lib/{project_id}/{version_id}` | `on_approval_required` in the body |
| `POST /api/v2/pipeline_triggers/prompt_lib/{project_id}/{version_id}` (create or rotate) | `on_approval_required` in the body |

A save or a rotation without the field keeps the stored value. Any other value is refused with HTTP 400.

Each run keeps the value that applied when it started (table `elitea_runtime.unattended_run_policies`). A later change does not change a run that is in flight.

### Evidence

Read the ledger of a run:

```sql
SELECT created_at, path, phase, outcome, action, actor_kind, actor_user_id,
       tool_name, toolkit_name, argument_digest, reason, audit_event_id
FROM elitea_runtime.approval_ledger
WHERE execution_id = '<execution id>'
ORDER BY id;
```

`audit_event_id` is the `id` of the audit event of the row. This is an example event of an approval:

### What is not enforced

- A rejection in the desktop app occurs on the user's computer and sends nothing to the server. The ledger has the `pause` row of the step, and no `decision` row.
- A credential authorization pause (a toolkit that needs the user to sign in) is not an approval. It is not in the ledger, and `on_approval_required` does not apply to it.
- When a parallel or fan-out run fails for a missing approver, the members that are already running continue until the worker sees the cancellation at its next lease renewal.
- On a `skip` of a card of a parallel or fan-out run, the card names the run's owner as the person who decided. The ledger row names the platform (`actor_kind` `system`).
- Pauses that started before migration 0211 have no `pause` row. A decision on such a pause is recorded.

### Customer responsibility

- Keep `approvals.unattended_default` at `fail`, unless a reviewed process needs `skip` or `notify_and_wait`.
- Use `notify_and_wait` only when the owner of the schedule or trigger can answer before the wait expires.
- Send the `agent.approval` events to your SIEM, and alert on `unattended_failed` and `timed_out`.

## Tool categories and approval policy

### The risk

A list of sensitive tools names each tool one by one. A new toolkit, or a new tool in a toolkit, does not ask for approval until someone adds it to the list. An agent that can delete records, post to people outside the organisation or move money can then act without a person.

### What is enforced

Each tool is in one category:

| Category | Meaning |
| --- | --- |
| `read` | Reads data and changes nothing. |
| `write` | Creates or changes data. A tool that is not declared is `write`. |
| `delete` | Deletes data. |
| `external_send` | Sends something that people outside the run see: an email, a chat post, a ticket or pull request comment. |
| `payment` | Moves money. |
| `code_execution` | Runs code or a query that the model wrote. |

The categories of the built-in tools are declared in one contract, [`libs/proto/contracts/tool-categories-v1.json`](https://github.com/elitea-ng/elitea-platform/blob/main/libs/proto/contracts/tool-categories-v1.json). The worker compiles it in, and the main service reads the same file. The tools that are not `read` or `write`:

| Category | Tools |
| --- | --- |
| `external_send` | GitHub `comment_on_issue`; GitLab and GitLab Org `comment_on_issue`, `create_pr_change_comment`; GitLab `comment_on_pr`; Bitbucket `add_pull_request_comment`; Azure DevOps Repos `comment_on_pull_request`; Aha! `add_comment`; Jira `add_comments`, `update_comment_with_file`; Figma `post_file_comment`; Slack `send_message`; Gmail (`yagmail`) `send_gmail_message` |
| `delete` | Every `delete_*` tool, `remove_index` and OneNote `onenote_delete_page` |
| `code_execution` | Data Analysis `pandas_analyze_data`; Sandbox `pyodide_sandbox`, `stateful_pyodide_sandbox`; SQL `execute_sql`; BigQuery `execute` |
| `payment` | No built-in tool yet |

The tools of a custom MCP server take the category that the approver gave each tool when the connector request was approved (the pinned tools carry it). A tool without a category is `write`.

A tool call needs a human approval when one of these rules applies:

- **Platform rule.** The administrator's sensitive action tools name the tool. This is the list under [Sensitive action authorization](/how-tos/chat-conversations/sensitive-action-authorization-guardrail). It applies at every tier.
- **Policy rule.** The approval policy names the tool's category for the risk tier of the run's agent.

The rules only add approvals. An agent author cannot remove an approval that a rule requires. A toolkit setting cannot move a declared tool to another category.

The tier is the risk tier on the root agent's registry record (a missing record is `low`). An agent, pipeline or sub-agent that the root agent calls uses the root agent's tier, not its own.

The default policy is the ADR default:

| Tier | Categories that need approval |
| --- | --- |
| `low` | None |
| `medium` | None |
| `high` | `delete`, `external_send`, `payment` |
| `critical` | `delete`, `external_send`, `payment` |

#### Limits

- The policy applies only after an administrator saves **Configuration › Approval Policy**. Until then, only the platform rule applies, as in earlier releases. Save the section only after every worker runs this release: a worker from an earlier release refuses commands that carry the policy.
- A tool that is not declared is `write`. A policy that names `write` asks for approval on every tool that is not declared, and on every MCP tool without a category. When you port a toolkit, declare the categories of its tools in the contract.
- Direct tool calls from outside a run (the platform's MCP endpoint) do not use the policy. They refuse every tool that is not read-only.
- A change to the policy applies to the commands that the main service sends after the change, at once on the replica that saved it and within 15 seconds on the other replicas.

### Configure

Under **Configuration › Approval Policy**, a platform administrator (permission `configuration.governance`) sets, for each tier, the categories whose tools need approval. The defaults are the table above.

### Evidence

When a tool call pauses because of a rule, the pause carries the field `approval_rule`:

```json
{ "source": "policy", "risk_tier": "high", "category": "external_send" }
```

The `source` is `platform` for the platform rule, `policy` for the policy rule, and `builtin` for the cloud workspace's own approvals (destructive commands, push and pull request). The platform rule is named when both rules apply. The field is on the `hitl_interrupt` and `hitl_interrupts` of the chat frame, so the decision record of the pause can name the rule.

### Customer responsibility

- Set each production agent's risk tier, so the policy applies the correct row.
- Decide which categories need approval at each tier. Add `code_execution` at `high` and `critical` if the model's code or queries can reach production data.
- Keep the platform's sensitive action tools for single tools that need approval at every tier.

## Required approval in pipelines

### The risk

A pipeline can call a tool from a toolkit node without a model. If the path to an `external_send` or `payment` tool has no `hitl` node, the pipeline sends the message or makes the payment without a person.

### What is enforced

**Configuration › Approval Policy › Tiers That Require a HITL Node in Pipelines** names the tiers where the rule applies. Under the rule, every path from the pipeline's entry point to a toolkit or MCP node that calls an `external_send` or `payment` tool must go through a `hitl` node. The check follows every edge: transitions, default outputs, decision and router routes, HITL routes, parallel branches, map workers and recovery routes.

A pipeline that breaks the rule does not start. The start request returns HTTP 422 with the code `PIPELINE_HITL_REQUIRED` and a message that names the node, the tool, its category and the path that has no `hitl` node, for example:

```text
Node "post" calls "send_message", which is a tool in the external_send category. The approval policy requires a hitl node on every path to such a tool for high-tier agents, and the path "draft" -> "route" -> "post" has none. Add a hitl node before "post".
```

The check runs at every start of a pipeline: chat turns, schedules and triggers. Pipelines cannot be published (publish refuses them with `pipeline_not_publishable`), so the run start is where the rule applies.

The default is off: no tier requires the node.

#### Limits

- The check reads the pipeline's toolkit and MCP nodes. A model node (`llm` or `agent`) that can call an `external_send` tool is covered by the policy rule at call time, not by this check.
- The check uses the tier of the pipeline's own registry record.

### Configure

Select the tiers under **Tiers That Require a HITL Node in Pipelines**. The [hardening checklist](/deployment/hardening-checklist) recommends `high` and `critical`.

### Evidence

The refused start returns the error above. No run starts, so no run step is written.

### Customer responsibility

- Add a `hitl` node before each node that sends outside the organisation or pays, in pipelines at the tiers you select.
- Set the tiers of pipelines on their registry records.


### Nested pauses

A human approval can pause a run inside a nested composition. Examples are an agent that calls an agent or a pipeline, and a pipeline that runs a saved pipeline. Each pause shows one approval card with the path of its callers. The worker keeps a checkpoint at each level. After an approval or a rejection, the paused level continues one time. Then each caller continues. When a person rejects, the tool is not called, and the caller reads the rejection result.

A pause can have a maximum of 3 delegations above it. The delegation depth limit under **Configuration › Delegation** also applies. The worker does not offer an attached pipeline that can pause in a position that it cannot resume. The worker writes a log entry with the reason `pipeline.child_pause_unsupported` and a detail code that names the pause kind. The [HITL node page](/how-tos/pipelines/nodes/interaction-nodes#hitl-nodes-in-nested-agents-and-pipelines) lists the pause kinds. To find the pipelines that the worker did not offer, search the worker logs for this reason.
