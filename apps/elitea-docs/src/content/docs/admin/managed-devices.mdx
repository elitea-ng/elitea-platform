## Mobile app

An MDM or EMM can configure the mobile app on the devices it manages. On iOS the values arrive as **AppConfig** (managed app configuration); on Android as **managed configuration** (app restrictions). The keys are the same on both platforms, and the app applies a change while it runs, without a relaunch.

| Key | Type | Effect |
|---|---|---|
| `server_url` | string | The organization's workspace. The connect screen shows it read only, marked "Managed by your organization", and offers no other server. Must be an `https://` address. |
| `lock_server` | boolean | With `server_url`: the device keeps only that workspace. Workspaces on other servers are signed out and their data removed, as at "Log out & wipe", and "Add workspace" is gone. Removing the key restores nothing. |
| `require_device_lock` | boolean | `true` asks for Face ID, Touch ID, a fingerprint or the passcode to open the app. |
| `idle_lock_seconds` | integer (1–86400) | Relock after this many seconds in the background, when shorter than the workspace's setting. |
| `allow_screenshots` | boolean | `false` blocks screenshots and screen recording of the app. |
| `support_contact` | string | The IT support line the app shows in Settings and About, for example `IT Service Desk, +1 555 0100`. It replaces the workspace's [support contact](#it-support-contact). |

The app signs in only as a registered native client: register it on **Admin › Platform › Client applications › Native clients** (see [Branded apps](/admin/brand-apps)). The lock keys only ever tighten the workspace's [native client policy](/admin/features-and-configuration); they never loosen it. A value of the wrong type is ignored. The configuration belongs to the device: signing out of a workspace does not remove it.

### What the app reports back

While a managed configuration is set, the app reports its state to the MDM, so you can see a misconfigured or signed-out app in the console. On iOS this is managed app feedback, the `com.apple.feedback.managed` dictionary. On Android it is keyed app states, which Intune, Workspace ONE, Test DPC and the Android Management API show.

| Key | Fine | Needs a look |
|---|---|---|
| `managed_config` | `applied` | `ignored_keys`, with the names of keys whose value had the wrong type |
| `connection` | `managed_server`, `unmanaged_server` (no `server_url` set), `not_connected` | `managed_server_invalid` (`server_url` is not a workspace address), `not_managed_server` (connected somewhere other than `server_url`) |
| `sign_in` | `signed_in`, `signed_out` | `signed_out_device_revoked`, `signed_out_credential_rejected`, `signed_out_policy`, `signed_out_managed_server` |
| `policy` | `ok` | `update_required`, with the minimum version the workspace asks for |

The app never reports user content: no server address, account, project, name, email, message or error text. Without a managed configuration it reports nothing. When you remove the configuration, Android devices report `not_managed` on every key once.

### Microsoft Intune

- **iOS:** Apps › App configuration policies › Add › Managed devices. Choose the app and enter the keys in the configuration designer, or as XML:

  ```xml
  <dict>
    <key>server_url</key><string>https://ai.example.com</string>
    <key>lock_server</key><true/>
    <key>require_device_lock</key><true/>
    <key>idle_lock_seconds</key><integer>60</integer>
    <key>allow_screenshots</key><false/>
  </dict>
  ```

- **Android Enterprise:** the same policy with platform Android Enterprise. Intune lists the app's keys with their types; fill them in.

### Workspace ONE UEM

On the app's assignment, turn on "Send Application Configuration" (iOS) or "Application Configuration" (Android) and add one row per key, with the value types above.

### Other MDMs and testing

Any MDM that supports AppConfig (Jamf, Kandji) or Android managed configurations works the same way. To test without an MDM, use an MDM test profile on iOS or Google's Test DPC on Android ("Manage application restrictions").

The app's source documents every key, both platforms and the full Intune and Workspace ONE samples in `apps/elitea-mobile/docs/mdm-appconfig.md`.

## Desktop app

### Download from the release

Every Elitea release, and every nightly pre-release, carries the desktop packages as release assets. Open the release on GitHub (**Releases** in the `elitea-ng/elitea-platform` repository), then **Assets**. The files are named `<Name>-<version>-<os>-<arch>[-unsigned].<ext>`:

| Platform | Asset | Signed |
|---|---|---|
| macOS 12 or later, Apple silicon (M1 or later) only | `Elitea-<version>-macos-arm64.dmg`: the disk image people download. Open it and drag the app to Applications. | Yes. The disk image and the app inside with Developer ID Application, both notarised and stapled. |
| macOS 12 or later, Apple silicon only | `Elitea-<version>-macos-arm64.pkg`: the installer package, for the MDM | Yes. The package with Developer ID Installer, the app inside with Developer ID Application. Both notarised and stapled. |
| Windows 10 2004 or later, x64 | `Elitea-<version>-windows-x64-unsigned.msi`: for Intune, SCCM or `msiexec /i <file> /qn` | **No**, until a Windows code-signing certificate is set up |
| Windows 10 2004 or later, x64 | `Elitea-<version>-windows-x64-unsigned.msix` | **No**: see below |
| Linux, x86_64, glibc 2.39 or later (Ubuntu 24.04, Debian 13, Fedora 40 and later) | `Elitea-<version>-linux-x86_64.AppImage`: one file that runs on most distributions | **No**: Linux packages carry no code signature. Check the file against `SHA256SUMS`. |
| Debian 13, Ubuntu 24.04 and later, x86_64 | `Elitea-<version>-linux-x86_64.deb` | **No**, as above |

`SHA256SUMS` lists the SHA-256 of each file. Check a download before you deploy it: `shasum -a 256 -c SHA256SUMS` on macOS (files you did not download show as missing), `sha256sum -c --ignore-missing SHA256SUMS` on Linux, or compare `Get-FileHash <file>` in PowerShell with its line. The release notes' **Desktop downloads** section says the same per release.

Intel Macs are not supported. The macOS app is built for Apple silicon only, and the installer package refuses to install on an Intel Mac. Scope the MDM assignment to Apple silicon computers: in Jamf, a smart group on **Architecture Type** `arm64`; in Intune, a filter on the device's processor architecture.

### Install on a Mac yourself

1. Download `Elitea-<version>-macos-arm64.dmg` from the release and open it. A window opens with the app on the left and the **Applications** folder on the right.
2. Drag the app onto **Applications**.
3. Eject the disk image (the eject button next to it in the Finder sidebar), then open the app from Applications or Launchpad.

The disk image is signed and notarised, and the ticket is stapled to it, so it opens without a Gatekeeper warning, also offline. To check a download yourself: `spctl -a -t open --context context:primary-signature -v <file>.dmg` says `accepted`, and `xcrun stapler validate <file>.dmg` says `The validate action worked!`.

For more than a handful of Macs, deploy the `.pkg` through the MDM instead ([macOS](#macos) below): it installs silently, with no window and no drag.

Earlier releases shipped the app zipped (`.app.zip`) next to the `.pkg`; the disk image replaced it.

### Windows packages are unsigned for now

The Windows packages carry no code signature until a Windows signer (Azure Artifact Signing or a code-signing certificate) is configured for the release. Once it is, the same files are built signed, and their names lose `-unsigned`. Until then:

- **The MSI** installs, but Windows SmartScreen first says that it protected your PC from an unrecognized app. Choose **More info**, then **Run anyway**. Some browsers also flag the download; keep it. Intune and SCCM install an unsigned MSI silently, with no prompt. If a policy refuses unsigned installers on your PCs (AppLocker, WDAC, Smart App Control), wait for the signed build or allow the file by its hash from `SHA256SUMS`.
- **The MSIX** does not install by double-click. It installs only on a recent Windows 11 with Developer Mode on (Settings › System › For developers), from PowerShell: `Add-AppxPackage -Path <file> -AllowUnsigned`. The Microsoft Store and Intune do not take it. Use the MSI unless you are testing the MSIX.

The desktop host builds and passes its tests on Windows. On Windows, local commands that need a sandbox are refused: see **Local work on Windows** in [Features and configuration](/admin/features-and-configuration).

### Install on Linux

The Linux files have no `-unsigned` in their names because Linux has no code signature for them to wait for. Check the download against `SHA256SUMS` instead.

**The AppImage** runs without installing anything:

1. Download `Elitea-<version>-linux-x86_64.AppImage` and `SHA256SUMS` from the release, and check the file: `sha256sum -c --ignore-missing SHA256SUMS`.
2. Make it executable: `chmod +x Elitea-<version>-linux-x86_64.AppImage`. In a file manager, this is **Properties › Permissions › Allow executing file as program**.
3. Run it: `./Elitea-<version>-linux-x86_64.AppImage`, or double-click it.

An AppImage mounts itself with FUSE 2. If it says `dlopen(): error loading libfuse.so.2` or `AppImages require FUSE to run`, either install FUSE 2 (`sudo apt install libfuse2t64` on Ubuntu 24.04, `libfuse2` on older Debian and Ubuntu, `fuse-libs` on Fedora), or run it without FUSE: `./Elitea-<version>-linux-x86_64.AppImage --appimage-extract-and-run`. Without FUSE, the file unpacks into a temporary folder on each start, so start-up takes a few seconds longer. In a container, `APPIMAGE_EXTRACT_AND_RUN=1` in the environment does the same.

An AppImage adds no menu entry by itself. To get one, with the app's icon, use AppImageLauncher or Gear Lever, which move the file into a folder of your choice and register it. Or unpack it once with `./Elitea-<version>-linux-x86_64.AppImage --appimage-extract`, then copy `squashfs-root/*.desktop` to `~/.local/share/applications/` with its `Exec=` line pointing at the AppImage. To update, replace the file with the next release's. The app does not update itself on any platform.

**The `.deb`** installs the app with a menu entry and pulls in the libraries it needs (WebKitGTK 4.1, GTK 3): `sudo apt install ./Elitea-<version>-linux-x86_64.deb`. The package recommends `bubblewrap`, which apt installs unless you turn recommends off. A newer `.deb` upgrades the app in place.

**What the Linux app needs, and what it does not do yet:**

- **bubblewrap (`bwrap`) for local work.** The app confines each command the agent runs with bubblewrap (`/usr/bin/bwrap`, `/usr/local/bin/bwrap` or `/bin/bwrap`), which the app does not include. Install it with `sudo apt install bubblewrap` or `sudo dnf install bubblewrap`. Without it, the app falls back to Landlock, which cannot hide credentials or keep `.git` read-only, so it refuses commands that a sandbox must confine. Some distributions block unprivileged user namespaces, which bubblewrap needs. Ubuntu 24.04 does this through AppArmor (`kernel.apparmor_restrict_unprivileged_userns`). Where commands fail to start under bubblewrap, ask your administrator to allow it. See **Local work** in [Features and configuration](/admin/features-and-configuration).
- **No system keyring.** The sign-in is stored in an owner-only file under `$XDG_CONFIG_HOME/ai.elitea.desktop/`, as on the other systems. The app needs no Secret Service or libsecret.
- **The GitHub CLI login in approval rules does not work yet.** An Allow rule's `credential` and `hosts` grant nothing on Linux, so network commands are asked as before ([#3012](https://github.com/elitea-ng/elitea-platform/issues/3012)).
- **No managed configuration.** The app reads no device-management settings on Linux, such as `lock_server` or `support_contact`. The organization's **Native client policy** still applies after sign-in.
- **x86_64 only.** There is no arm64 build yet.
- **No tray icon on some desktops.** GNOME without the AppIndicator extension shows none. That is why, while a turn runs, closing the window minimizes the app on Linux instead of hiding it.
- **Commands inherit the AppImage's environment.** A command the agent runs from the AppImage starts with the variables the AppImage sets for its own GTK libraries, such as `APPDIR` and `GDK_PIXBUF_MODULE_FILE`. A GUI program started from such a command can pick up the AppImage's libraries. The `.deb` has no such variables.

### A package of your own brand

A brand built from this code ([Build your own brand](/development/build-your-own-brand)) signs its packages with its own certificates and hands them to its device management. To build a package from this repository without a release, run GitHub Actions › **Desktop — package for device management** › Run workflow with the **version** to stamp (for example the release the package is for, `7.9.0`) and **keep_artifacts** ticked: the run keeps the packages as artifacts for 7 days. The version is required: it names the disk image's volume and window (`Elitea 7.9.0`) and the app's version. The macOS package of such a run is always signed.

Windows shows a notification only for an app that its Start Menu shortcut or its package names. The `.msi` shortcut sets `System.AppUserModel.ID` to the brand's desktop identifier, and the app sends its notifications under that identifier. The `.msix` app sends them under its package identity (`<PackageFamilyName>!App`).

### IT support contact

The apps show an **IT support** line in About and Settings, so people know whom to ask. Set it for every device in **Admin › Configuration › Native client policy › IT Support Contact**, or per device through the device management with the key `support_contact`. The device's value wins. One line of at most 200 characters; an `https://` address, an email address or a phone number in it becomes a link. Without either, the apps show no line.

| App | Where it shows | Device management key |
|---|---|---|
| iPhone, iPad, Android | Settings › About, and About | `support_contact` in the AppConfig or managed configuration (above) |
| macOS | The account menu, Settings › Troubleshoot, and the About panel (from the next launch) | `support_contact` in a configuration profile with a Custom Settings (`com.apple.ManagedClient.preferences`) payload for the app's bundle identifier. Only a value the profile enforces counts, not one written with `defaults write`. |
| Windows | Not yet | — |

On the desktop app an `https://` line opens in the browser; an email address or a phone number opens Settings › Troubleshoot, where the line can be copied.

### macOS

The `.pkg` installs the app into `/Applications` with no interface and no reboot, for every user of the Mac.

- **Jamf Pro:** Settings › Packages › New, upload the `.pkg`, then add it to a policy (Packages › Install) scoped to the target computers. Because the package is signed and notarised, no Gatekeeper exception is needed.
- **Intune for macOS:** Apps › macOS › Add › macOS app (PKG), upload the `.pkg`. Intune reads the bundle id and version from it.
- **Kandji, Mosyle and others:** add it as a custom app (installer package).
- **By hand or from a script:**

  ```bash
  sudo installer -pkg Elitea-1.62.0-arm64.pkg -target /
  ```

A newer package upgrades the app in place; it keeps the person's settings and the macOS privacy grants (Accessibility, Screen Recording), which stay valid while the bundle id and the signing team do not change. Allow these grants ahead of time with a Privacy Preferences Policy Control (PPPC) profile for the bundle id and team, where the MDM supports it (Screen Recording can only be allowed by the person).

### Windows

- **Intune:** Apps › Windows › Add › Line-of-business app, upload the `.msi`; Intune installs it silently. The `.msix` can be added the same way (Apps › Windows › Add › Line-of-business app accepts both).
- **Configuration Manager (SCCM):** create an application from the `.msi` (Windows Installer deployment type); the detection rule is the MSI product code.
- **By hand or from a script:**

  ```powershell
  msiexec /i Elitea_1.62.0_x64_en-US.msi /qn
  ```

The installer fetches the WebView2 runtime silently when the PC does not have it; on a PC without internet access, deploy WebView2 first.

## Certificates and per-app VPN

Both are features of the operating system, not of the app: the device management delivers them, and the app needs no setting of its own. Each is scoped by **app identifier**, so use the identifiers of the build you deploy. A brand built from this code sets its own in its brand manifest: `mobile.bundleId` (the iOS bundle id and the Android package name), `mobile.widgetBundleId` and `desktop.identifier`. ELITEA's are:

| App | Identifier |
|---|---|
| iPhone and iPad | `ai.elitea.app` (its widget extension: `ai.elitea.app.widgets`) |
| Android | `ai.elitea.app` (the package name) |
| macOS | `ai.elitea.desktop` |

**Trusted root certificates.** A workspace behind a private certificate authority needs that CA trusted by the app.

- **iOS:** deploy the CA in a Certificate payload. A profile installed by the MDM is trusted at once; one a person installs must also be turned on in Settings › General › About › Certificate Trust Settings.
- **Android:** the app trusts only the CAs that ship with Android. A CA the MDM pushes (in Intune: a Trusted certificate profile) lands in the user store, which the browser trusts but the app does not, so sign-in loads and the app's own requests then fail. Serve the workspace with a certificate from a public CA, or terminate TLS with one at the edge the devices reach.
- **macOS:** deploy the CA in a Certificate payload to the System keychain. The desktop app trusts the macOS trust settings together with a built-in set of public roots, so a private CA works once macOS trusts it; distrusting a public root in macOS does not remove it from the app.

**Client certificates (mutual TLS).** The apps do not present a client certificate themselves. Where the workspace sits behind a gateway that asks for one, let the per-app VPN do it, or let only the identity provider ask: sign-in runs in the system browser (the sign-in sheet on iOS, a Custom Tab on Android, the default browser on macOS), which can use a certificate the MDM installed for it. The app's own requests after sign-in carry no certificate.

**Per-app VPN.** Assign the app to the VPN by its identifier:

- **iOS:** a per-app VPN payload with the app (`ai.elitea.app`) in its app list. In Intune: the VPN profile's Automatic VPN › Per-app VPN, then the app's assignment with that VPN. The widget extension makes no network requests (it shows what the app saved), so it needs no VPN.
- **Android:** an always-on VPN for the work profile, or the VPN app's own per-app list with the package `ai.elitea.app`.
- **macOS:** a per-app VPN payload whose app rule names the identifier `ai.elitea.desktop` and the app's full designated requirement, as `codesign -dr - "/Applications/<app>.app"` prints it.

**Sign-in and the VPN.** Sign-in opens the system browser, which a per-app VPN for the app does not cover. Where the identity provider is reachable only over the VPN, add its domains to the VPN as well: on iOS, the payload's Safari domains (`SafariDomains`); on Android, put the browser in the VPN app's list or use an always-on VPN; on macOS, add the default browser's app rule or the identity provider's domains to the VPN.
