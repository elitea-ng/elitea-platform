## Mobile app

An MDM or EMM can configure the mobile app on the devices it manages. On iOS the values arrive as **AppConfig** (managed app configuration); on Android as **managed configuration** (app restrictions). The keys are the same on both platforms, and the app applies a change while it runs, without a relaunch.

| Key | Type | Effect |
|---|---|---|
| `server_url` | string | The organization's workspace. The connect screen shows it read only, marked "Managed by your organization", and offers no other server. Must be an `https://` address. |
| `lock_server` | boolean | With `server_url`: the device keeps only that workspace. Workspaces on other servers are signed out and their data removed, as at "Log out & wipe", and "Add workspace" is gone. Removing the key restores nothing. |
| `require_device_lock` | boolean | `true` asks for Face ID, Touch ID, a fingerprint or the passcode to open the app. |
| `idle_lock_seconds` | integer (1–86400) | Relock after this many seconds in the background, when shorter than the workspace's setting. |
| `allow_screenshots` | boolean | `false` blocks screenshots and screen recording of the app. |
| `support_contact` | string | The IT support line the app shows in Settings and About, for example `IT Service Desk, +1 555 0100`. It replaces the workspace's [support contact](#it-support-contact). |

The lock keys only ever tighten the workspace's [native client policy](/admin/features-and-configuration); they never loosen it. A value of the wrong type is ignored. The configuration belongs to the device: signing out of a workspace does not remove it.

### What the app reports back

While a managed configuration is set, the app reports its state to the MDM, so you can see a misconfigured or signed-out app in the console. On iOS this is managed app feedback, the `com.apple.feedback.managed` dictionary. On Android it is keyed app states, which Intune, Workspace ONE, Test DPC and the Android Management API show.

| Key | Fine | Needs a look |
|---|---|---|
| `managed_config` | `applied` | `ignored_keys`, with the names of keys whose value had the wrong type |
| `connection` | `managed_server`, `unmanaged_server` (no `server_url` set), `not_connected` | `managed_server_invalid` (`server_url` is not a workspace address), `not_managed_server` (connected somewhere other than `server_url`) |
| `sign_in` | `signed_in`, `signed_out` | `signed_out_device_revoked`, `signed_out_credential_rejected`, `signed_out_policy`, `signed_out_managed_server` |
| `policy` | `ok` | `update_required`, with the minimum version the workspace asks for |

The app never reports user content: no server address, account, project, name, email, message or error text. Without a managed configuration it reports nothing. When you remove the configuration, Android devices report `not_managed` on every key once.

### Microsoft Intune

- **iOS:** Apps › App configuration policies › Add › Managed devices. Choose the app and enter the keys in the configuration designer, or as XML:

  ```xml
  <dict>
    <key>server_url</key><string>https://ai.example.com</string>
    <key>lock_server</key><true/>
    <key>require_device_lock</key><true/>
    <key>idle_lock_seconds</key><integer>60</integer>
    <key>allow_screenshots</key><false/>
  </dict>
  ```

- **Android Enterprise:** the same policy with platform Android Enterprise. Intune lists the app's keys with their types; fill them in.

### Workspace ONE UEM

On the app's assignment, turn on "Send Application Configuration" (iOS) or "Application Configuration" (Android) and add one row per key, with the value types above.

### Other MDMs and testing

Any MDM that supports AppConfig (Jamf, Kandji) or Android managed configurations works the same way. To test without an MDM, use an MDM test profile on iOS or Google's Test DPC on Android ("Manage application restrictions").

The app's source documents every key, both platforms and the full Intune and Workspace ONE samples in `apps/elitea-mobile/docs/mdm-appconfig.md`.

## Desktop app

The desktop app reaches people only through the organization's device management; it is not published for download. The brand owner builds the packages by hand: GitHub Actions › **Desktop — package for device management** › Run workflow, with **keep_artifacts** ticked. The run's artifacts (kept for 7 days) are the packages to upload to the MDM.

| Platform | Package | Signed with |
|---|---|---|
| macOS 12 or later, Apple silicon and Intel | `<Name>-<version>-universal.pkg` | Developer ID Installer; the app inside with Developer ID Application. Both notarised and stapled. |
| Windows 10 2004 or later, x64 | `.msi` and `.msix` | Azure Artifact Signing or the organization's code-signing certificate, timestamped |

Windows packages are built once the desktop host runs on Windows; until then only the macOS package is available.

### IT support contact

The apps show an **IT support** line in About and Settings, so people know whom to ask. Set it for every device in **Admin › Configuration › Native client policy › IT Support Contact**, or per device through the device management with the key `support_contact`. The device's value wins. One line of at most 200 characters; an `https://` address, an email address or a phone number in it becomes a link. Without either, the apps show no line.

| App | Where it shows | Device management key |
|---|---|---|
| iPhone, iPad, Android | Settings › About, and About | `support_contact` in the AppConfig or managed configuration (above) |
| macOS | The account menu, Settings › Troubleshoot, and the About panel (from the next launch) | `support_contact` in a configuration profile with a Custom Settings (`com.apple.ManagedClient.preferences`) payload for the app's bundle identifier. Only a value the profile enforces counts, not one written with `defaults write`. |
| Windows | Not yet | — |

On the desktop app an `https://` line opens in the browser; an email address or a phone number opens Settings › Troubleshoot, where the line can be copied.

### macOS

The `.pkg` installs the app into `/Applications` with no interface and no reboot, for every user of the Mac.

- **Jamf Pro:** Settings › Packages › New, upload the `.pkg`, then add it to a policy (Packages › Install) scoped to the target computers. Because the package is signed and notarised, no Gatekeeper exception is needed.
- **Intune for macOS:** Apps › macOS › Add › macOS app (PKG), upload the `.pkg`. Intune reads the bundle id and version from it.
- **Kandji, Mosyle and others:** add it as a custom app (installer package).
- **By hand or from a script:**

  ```bash
  sudo installer -pkg Elitea-1.62.0-universal.pkg -target /
  ```

A newer package upgrades the app in place; it keeps the person's settings and the macOS privacy grants (Accessibility, Screen Recording), which stay valid while the bundle id and the signing team do not change. Allow these grants ahead of time with a Privacy Preferences Policy Control (PPPC) profile for the bundle id and team, where the MDM supports it (Screen Recording can only be allowed by the person).

### Windows

- **Intune:** Apps › Windows › Add › Line-of-business app, upload the `.msi`; Intune installs it silently. The `.msix` can be added the same way (Apps › Windows › Add › Line-of-business app accepts both).
- **Configuration Manager (SCCM):** create an application from the `.msi` (Windows Installer deployment type); the detection rule is the MSI product code.
- **By hand or from a script:**

  ```powershell
  msiexec /i Elitea_1.62.0_x64_en-US.msi /qn
  ```

The installer fetches the WebView2 runtime silently when the PC does not have it; on a PC without internet access, deploy WebView2 first.

## Certificates and per-app VPN

Both are features of the operating system, not of the app: the device management delivers them, and the app needs no setting of its own. Each is scoped by **app identifier**, so use the identifiers of the build you deploy. A brand built from this code sets its own in its brand manifest: `mobile.bundleId` (the iOS bundle id and the Android package name), `mobile.widgetBundleId` and `desktop.identifier`. ELITEA's are:

| App | Identifier |
|---|---|
| iPhone and iPad | `ai.elitea.app` (its widget extension: `ai.elitea.app.widgets`) |
| Android | `ai.elitea.app` (the package name) |
| macOS | `ai.elitea.desktop` |

**Trusted root certificates.** A workspace behind a private certificate authority needs that CA trusted by the app.

- **iOS:** deploy the CA in a Certificate payload. A profile installed by the MDM is trusted at once; one a person installs must also be turned on in Settings › General › About › Certificate Trust Settings.
- **Android:** the app trusts only the CAs that ship with Android. A CA the MDM pushes (in Intune: a Trusted certificate profile) lands in the user store, which the browser trusts but the app does not, so sign-in loads and the app's own requests then fail. Serve the workspace with a certificate from a public CA, or terminate TLS with one at the edge the devices reach.
- **macOS:** deploy the CA in a Certificate payload to the System keychain. The desktop app trusts the macOS trust settings together with a built-in set of public roots, so a private CA works once macOS trusts it; distrusting a public root in macOS does not remove it from the app.

**Client certificates (mutual TLS).** The apps do not present a client certificate themselves. Where the workspace sits behind a gateway that asks for one, let the per-app VPN do it, or let only the identity provider ask: sign-in runs in the system browser (the sign-in sheet on iOS, a Custom Tab on Android, the default browser on macOS), which can use a certificate the MDM installed for it. The app's own requests after sign-in carry no certificate.

**Per-app VPN.** Assign the app to the VPN by its identifier:

- **iOS:** a per-app VPN payload with the app (`ai.elitea.app`) in its app list. In Intune: the VPN profile's Automatic VPN › Per-app VPN, then the app's assignment with that VPN. The widget extension makes no network requests (it shows what the app saved), so it needs no VPN.
- **Android:** an always-on VPN for the work profile, or the VPN app's own per-app list with the package `ai.elitea.app`.
- **macOS:** a per-app VPN payload whose app rule names the identifier `ai.elitea.desktop` and the app's full designated requirement, as `codesign -dr - "/Applications/<app>.app"` prints it.

**Sign-in and the VPN.** Sign-in opens the system browser, which a per-app VPN for the app does not cover. Where the identity provider is reachable only over the VPN, add its domains to the VPN as well: on iOS, the payload's Safari domains (`SafariDomains`); on Android, put the browser in the VPN app's list or use an always-on VPN; on macOS, add the default browser's app rule or the identity provider's domains to the VPN.
