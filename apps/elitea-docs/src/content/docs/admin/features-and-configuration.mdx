## Configuration

Configuration holds the sections Features does not: some editable directly here, some pointing to a dedicated page.

<Accordion title="Guardrails (editable here)">
Blocked toolkit types (a blocked type cannot be listed or created, and is stripped from every agent before it runs — existing toolkits of that type stay visible so an administrator can review and delete them, but stop working); blocked individual tools within an otherwise-allowed toolkit; tools that require the user to authorize each call ("sensitive action" tools, matched per toolkit or with `*` for every toolkit); the company name and message template shown in that authorization dialog.

These settings travel with every run, governed or not, and replace the worker's own `--toolkit-security-config` file for that run, even when they are empty. The file applies only to a run that carries no guardrails, so set sensitive tools here, not in the worker's file.
</Accordion>

<Accordion title="Cloud Browser (editable here)">
The cloud browser's egress (`open` lets the browser reach any public host; `allowlist` limits it to the run's egress allowlist and the project's browser domains, and a governed run always gets the allowlist), the most browser engine seconds one run may use (default 1800), and the most one project may use in a calendar month (default 0, no quota). See [Cloud Browser](/integrations/toolkits/cloud_browser_toolkit).
</Accordion>

<Accordion title="Banner (editable here)">
A dismissible banner shown across the app, with its own icon, style, and message.
</Accordion>

<Accordion title="Maintenance (editable here)">
Turns on maintenance mode: every caller without administration access gets a 503 and the splash screen, with its own title, message, and optional HTML. The admin console and authentication routes stay reachable so the window is reversible from inside itself.
</Accordion>

<Accordion title="E-mail (editable here)">
The outbound mail relay: SMTP host, port, TLS mode, credentials, from/reply-to addresses, and the public base URL used in links the platform sends. Environment variables (`SMTP_HOST` and its siblings) provide a second layer underneath these rows; a row set here wins over the environment field by field.
</Accordion>

<Accordion title="Notifications (editable here)">
**Web push** (default on) lets a person get a browser notification when a long run ends or when a run waits for an approval. The browser shows it also when no Elitea tab is open. Turn it off to stop all web push sends for the platform. The bell and Notifications Center do not change.

When you turn web push off, browsers cannot opt in, and Main sends nothing. Main keeps the stored subscriptions. When you turn it on again, Main sends only notifications that come after that time.

Web push also needs these items. When one is missing, web push is off and the switch has no effect:

- A vault. Main makes one VAPID key for the install and keeps it in the global vault as the hidden secret `web_push_vapid_private_key`. Do not delete this secret. A new key stops every stored subscription.
- A contact for the push services: `ELITEA_WEB_PUSH_SUBJECT` (a `mailto:` address or an `https:` URL). When it is empty, Main uses `PUBLIC_BASE_URL` if it is `https`.
- Egress to the browsers' push services (see [Notifications](/menus/settings/notifications#web-push)). Main uses `HTTPS_PROXY` when you set it. Without a proxy, Main connects directly and refuses private and reserved addresses.

Main sends the notification ids and the outcome only, never a message text. Each send is encrypted for one browser (RFC 8291) and signed with the install's key (RFC 8292). A push service that answers 404 or 410 removes that subscription. A push service that refuses the key (401 or 403) drops that send; three refusals in a row remove the subscription. Main tries other failures again with a longer wait each time, for at most 24 hours. A person keeps at most 10 browsers.
</Accordion>

<Accordion title="Native client policy (editable here)">
What this deployment requires of its mobile and desktop apps. The policy goes out with every token an app receives, so a change reaches signed-in devices within one access-token lifetime. The apps enforce the device settings; the server refuses app versions below the minimum. The section needs the `configuration.native_clients` permission.

The device and data-control keys: `require_device_lock`, `idle_lock_seconds`, `allow_screenshots`, `offline_retention_days`, `offline_max_mb`, `offline_attachments`, `min_client_version`, `allow_share_out`, `allow_share_in`, `allow_cloud_stt`, `notification_preview`, `allow_notification_actions` and `allow_system_surfaces`.

**Local work** (the desktop app runs agents on the user's machine). Every key but the first shows only while **Allow Local Work** is on:

| Key | Default | Effect |
| --- | --- | --- |
| `local_work_allowed` | Off | Local work at all. When off, the server refuses every local turn. |
| `local_work_shell` | On | Local turns may run shell commands. |
| `local_work_max_sandbox_mode` | `workspace-write` | The least confined sandbox a command may use: `read-only`, `workspace-write` or `full-access`. |
| `local_work_network` | Off | Sandboxed commands may reach the network. |
| `local_work_command_allow`, `local_work_command_deny`, `local_work_path_deny` | Empty | Command and path patterns, at most 200 of 512 bytes each. A deny wins. |
| `local_work_local_mcp` | Off | People may add MCP servers that run on their machine. |
| `local_work_local_index` | On | The app may index a workspace folder on the device. |
| `local_work_cloud_sync` | Off | A workspace folder may be synced to an artifact bucket. |
| `local_work_memory_write` | On | A local turn may save to the user's cloud memory. |
| `local_work_cloud_handoff` | Off | A Local work thread may be sent to the cloud executor. |
| `local_work_index_local_embeddings`, `local_work_index_remote_embeddings`, `local_work_index_model_mirror_url` | On, Off, empty | How a local index may be embedded. See [Desktop local index](/how-tos/indexing/desktop-local-index). |
| `local_work_web`, `local_work_host_intel` | Off | A local turn may use the Web Search and Host Intelligence toolkits. |
| `local_work_computer_use` | Off | A local turn may see and use the user's other applications (macOS, Windows and Linux, through each OS's accessibility interface; on Linux, Wayland sessions can only see). |
| `local_work_computer_use_apps_allow` | Empty | When not empty, the only applications computer use may touch. |
| `local_work_computer_use_apps_deny` | Empty | Applications computer use never touches, added to the built-in list. |
| `local_work_browser` | On | The desktop's browser pane exists for local threads. |
| `local_work_browser_agent` | On | The agent may drive the browser pane. Off, the person can still browse in it. |
| `local_work_browser_allow_domains` | Empty | When not empty, the only sites the pane loads. |
| `local_work_browser_deny_domains` | Empty | Sites the pane never loads. |
| `local_work_browser_http` | Off | Plain `http` pages may load. |
| `local_work_browser_private_network` | Off | Local and private network addresses (`localhost`, `192.168.x.x`, `.local` names) may load. Turn it on for developers who test a local app. |

**Computer use.** Turning `local_work_computer_use` on lets people turn it on for their own device. It is still off on each device until the person turns it on in Settings and, on macOS, grants the Accessibility permission. The agent then asks per application: once to see an app, and again to use it. Each call is a step record of the turn; typed text is recorded only as its length and digest, and screenshots stay on the device unless the project's `computer_use` setting turns on **Upload screenshots** (see [Let the agent use your other apps](/how-tos/chat-conversations/desktop-computer-use#what-is-recorded)). The person can allow an app for one thread or always. The agent asks every time before an action that sends, deletes, buys, pays, signs, submits or confirms, and it never remembers that answer. In plan mode the agent can only look. A scheduled or other unattended run never acts on an application without a person at the machine: every action is asked, even on an app the person allowed always or for the thread, and the request waits for an answer, then is declined. An unattended run can still see the apps the person allowed. Every request names the application it is about, except the list of running applications.

The app lists take bundle ids, such as `com.apple.mail`. A prefix such as `com.example.*` covers every application of that vendor. Each list holds at most 200 entries of at most 255 bytes. The save refuses anything else. A deny entry wins over an allow entry. The app always adds its own deny list, and no policy removes it:

- Elitea itself.
- Password managers: Keychain Access, Passwords, 1Password, Bitwarden, KeePassXC, LastPass, Enpass and Proton Pass.
- Terminals: Terminal, iTerm2, Warp, Ghostty, Alacritty, kitty, WezTerm, Hyper and Tabby. The agent has its own sandboxed shell, and a terminal would bypass that sandbox.
- Script Editor, Automator and Shortcuts.
- The login window and the system's password prompts.
- Screen Time.
- The security panes of System Settings: Privacy & Security, Touch ID & Password, Users & Groups, Passwords, Lock Screen, and Login Items & Extensions. The agent may use the other panes of System Settings, but only when the app can tell which pane is open. If it cannot, System Settings is refused.
</Accordion>

**Browser pane.** The desktop app has a browser pane beside each local thread. The person and the agent use the same page. The site lists take host names: `example.com` covers that site and every site under it, and `*.example.com` covers only the sites under it. Each list holds at most 200 entries, with no scheme, port or IP address; the save refuses anything else. A deny entry wins over an allow entry. A non-empty allow list is a ceiling: the pane loads nothing else, including local addresses. Link-local addresses (the cloud metadata endpoints) never load. A change applies to panes opened after it.

The agent reads pages and navigates without asking. It asks before it submits a form or uploads a file; the person can allow that kind of action for the site for the rest of the thread (allowing submits does not allow uploads). It asks before every download and never remembers that answer. While the agent is working, the pane refuses any download the person did not approve. It asks every time before it clicks a control, or presses Enter or Space on one, that buys, pays, deletes, sends or signs, and it never remembers that answer, even in bypass mode. When the app cannot tell which control has the focus, it asks before every Enter or Space. In plan mode the agent can only read the page. An unattended run's grant can name sites in `browser_submits`: on those sites the run submits forms and uploads files without asking. Bypass mode does not answer these asks in an unattended run. Every other ask waits for a person and is then declined. The agent never types into a password or card field, and sign-in is the person's.
