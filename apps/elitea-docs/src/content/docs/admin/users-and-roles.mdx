Users and Roles are two related admin pages: Users acts on individual accounts, and Roles defines what each role is allowed to do.

For an access review, **Export entitlements** on the Users page downloads who holds which role on the platform, each project and each agent, with the governance capabilities each role carries. Identity governance tools can read the same data over SCIM. See [Entitlement export](/admin/enterprise-controls/least-privilege-and-trust#entitlement-export-for-access-reviews) for the format.

## Manage users

Open **Users** in the admin console. The table lists every account on the deployment, with search.

<Steps>
  <Step title="Find the account">
    Search by name or e-mail.
  </Step>
  <Step title="Act on it">
    From the row menu: delete the account, grant or revoke the global admin role, or suspend/unsuspend it. A suspended account cannot sign in.
  </Step>
  <Step title="Review activity">
    Open the activity drawer for a per-user view built on the same audit data as the Audit Trail page.
  </Step>
  <Step title="Export">
    **Export to CSV** downloads the current list.
  </Step>
</Steps>

## Several administration roles per person

A person can hold several administration roles at once, for example `llm_manager` and `security_auditor`. They hold the union of the permissions of every role; there is no role switcher. Any role of the administration mode can be assigned, built-in or custom, except one that is never assigned (the legacy `system` role).

On the Users page, the **Administration roles** column holds a picker for each person. Open it, tick every role the person should hold, and close it: closing saves the whole set in one request. Built-in roles are shown by their display name (for example *LLM manager*) with a line on what the role is for; a custom role is shown by its name. The picker offers every role that holds at least one permission, except the legacy `system` role; the empty `editor` and `viewer` roles of a new deployment are not offered, but a role a person already holds is always shown so it can be taken away. When the server refuses a change, for example because you would change your own roles or give a permission you do not hold, the page says why and keeps the roles as they were. The CSV export lists the roles by the same names, separated by `;`.

You can also set the roles through the API.

**`POST /api/v2/admin/auth_users/administration`** with `action: set_admin_role` sets a person's roles. Send one of two forms:

- `role_names`, the set the person holds afterwards (`[]` for none):

  ```json
  {"action": "set_admin_role", "user_id": 11, "role_names": ["admin", "llm_manager"]}
  ```

- `role_name`, the single form existing automation uses: it replaces every role with that one role (`null` for none).

A request with both is a `400`, and so is a role the deployment does not define (the answer names it). The server applies the difference: a role in both the old and the new set is not touched, and each role given or taken writes one [record](#role-changes-are-recorded). Every [rule](#no-escalation) applies to each role given or taken, and if one role fails, nothing is written and the refusal names that role. The answer carries `role_names`, the person's roles after the change.

**`POST /api/v2/admin/modes/administration`** with `{"user_id", "mode": "administration", "role"}` adds one role and keeps the others; `DELETE` with `?id=<user_id>:administration:<role>` removes one.

**`GET /api/v2/admin/auth_users/administration`** lists every role of each person in `admin_roles`, sorted by name: no role ranks above another, so a person who holds only `llm_manager` is listed with `llm_manager`. The single `admin_role` field, which held the highest of `super_admin`, `admin`, `editor` and `viewer`, is no longer returned: read `admin_roles`.

### What the name `super_admin` reaches

Almost every administration check tests a permission. A few test the role **name** `super_admin` of the administration mode, on purpose:

- **Every project.** A standing holder of the role named `super_admin` passes the project access check of every project and is listed as a member of every project, with the role `super_admin`. A custom role does not, even one that holds every permission of `super_admin`, and neither will a break-glass elevation: an elevation gives permissions, not the role's name. Break-glass repairs the platform; it does not open project content.
- **The public project at sign-in.** A holder of `admin` or `super_admin` gets the extra public-project roles the deployment configures for administrators. Narrow roles do not.

Giving or taking the role `super_admin` needs the permission `admin.auth.users.super_admin`, not a role of that name, and no role other than `super_admin` holds that permission (the legacy `system` role also holds it on an upgraded deployment, and is never assigned). A source test lists every check by the names `super_admin` and `admin` with its decision, so a new one cannot appear unreviewed.

## Edit roles and permissions

Open **Roles**. It shows a permission matrix across three scopes, each a tab:

- **Central** — the administration-mode roles used across the deployment (the ones this admin console itself is gated on).
- **Public Project** — roles available inside the shared public project.
- **Support Project** — roles for the support project, if one is configured for this deployment. If none is configured, this tab reports that rather than an empty grid.

<Steps>
  <Step title="Toggle a permission">
    Click a cell to grant or revoke that permission for that role, within the selected scope.
  </Step>
  <Step title="Create, rename, or delete a role">
    Use the controls above the matrix. A new standard role only reaches projects that already exist once you use **Apply to Projects** next to it — creating the role does not retroactively push it everywhere by itself.
  </Step>
</Steps>

## Narrow administration permissions

Besides the broad central permissions such as `runtime.plugins` and `configuration.governance`, the deployment has narrow ones, each for one subject. The upgrade that adds them grants all of them to the `super_admin` role and all but `identity.sso.trust.manage` to the `admin` role, so both administrator roles keep everything they could do and hold the new names too. No existing grant is removed.

A route accepts a narrow permission beside the broad one it narrows, so a holder of the broad permission sees no change. The rows that say **Accepted** are wired today on the server; the other names are accepted as later releases wire their routes. The admin navigation shows a page to a holder of any permission its routes accept, broad or narrow, so a narrow role sees the pages it can use in the menu (see [what a narrow role sees](/admin/overview#what-a-narrow-role-sees)). The built-in narrow roles below hold only a narrow set.

The four `access.breakglass.*` names belong to break-glass elevation and allow nothing until that feature ships; then every holder of `admin` can use them.
</Note>

### The two legacy permissions end on a date

`runtime.plugins` and `configuration.governance` each cover many unrelated subjects. The narrow permissions above replace them:

- `runtime.plugins` is replaced by `platform.config.view` and `.manage`, `platform.email.manage`, `platform.maintenance.manage`, `platform.operations.view` and `.manage`, `mcp.catalogue.manage`, `identity.sso.view`, `.settings.manage` and `.trust.manage`, and the `llm.policy.*` and `llm.guardrails.manage` names for the guardrail and breaker sections.
- `configuration.governance` is replaced by the `llm.*` names for the gateway. The agent governance Configuration sections have no narrow pair yet and still need `configuration.governance`; a later release gives them one.

Both legacy names end on a sunset date, at least 90 days after the last replacement ships; a later release sets and announces the date. Until then:

- An existing grant of either keeps working, and a role that holds one can be saved unchanged.
- The Roles matrix marks both **Deprecated**, and the checkbox of a role that does not hold one is disabled.
- A save that adds either to a role that does not hold it is refused with `400` and the code `permission_deprecated`, for every caller, a super admin included. This applies to the Roles matrix and to the personal and team project matrix (`/admin/user_project_permissions`). Removing one is allowed, and cannot be undone from the matrix. Grant the narrow permission instead.
- No new route or section is gated on either name: a test holds the number of places that name them, and it may only go down.

## Built-in administration roles

Six built-in roles of the central administration mode hold a set of permissions that Elitea defines. The upgrade that adds the four new ones creates them with their sets; it assigns them to nobody. The Users page shows each built-in role by its display name; the Roles matrix still labels each column with the role name.

| Role | Display name | Permissions | Cannot |
|---|---|---|---|
| `super_admin` | Global administrator | Every administration permission except `configuration.service_descriptors`, which no upgrade grants. Alone among the assignable roles it holds `admin.auth.users.super_admin` and `identity.sso.trust.manage`. | Hold `security.signals.reidentify`; that permission goes to no built-in role. |
| `admin` | Platform administrator | Every administration permission except `admin.auth.users.super_admin`, `identity.sso.trust.manage` and `configuration.service_descriptors`. | Make a global administrator, or change whom an identity provider vouches for. |
| `llm_manager` | LLM manager | `llm.catalogue.view`, `llm.catalogue.manage`, `llm.policy.view`, `llm.policy.manage`, `llm.usage.view`, `llm.alerts.manage`, `models.admin.project_budgets.view`, `models.admin.project_budgets.edit`, `projects.projects.projects.view` | Manage users, roles, identity providers, SCIM, tokens, project members, branding, e-mail, maintenance, retention, the kill switch, the agent registry, delegation reviews, worker egress or guardrails. |
| `project_administrator` | Project administrator (all projects) | `projects.projects.projects.view`, `projects.projects.projects.edit`, `projects.projects.project.create`, `projects.projects.project.delete`, `projects.members.manage`, `projects.settings.view`, `projects.settings.manage`, `configuration.users.users.view`, `configuration.roles.roles.view`, `configuration.roles.user_project_permissions.view`, `invites.bulkusers`, `invites.bulkprojects`, `admin.moderation`, `admin.moderation.edit`, `models.admin.project_budgets.view` | Change platform configuration or LLM settings, identity providers or SCIM bindings, edit the project role matrix, assign administrative roles, suspend or delete users, or configure the credentials, models and toolkits of a project. It cannot read project content without a membership, and cannot give itself one. It can still add a second account, or another project administrator, to a project: that is detected by the `access.admin_membership_granted` signal, not prevented. |
| `security_auditor` | Security auditor | `models.admin.audit_trail.view`, `access.roles.view`, `access.breakglass.review`, and the security signal permissions when security signals ship | Use any route that writes or approves, other than attesting a break-glass review. Never `security.signals.reidentify`. |
| `emergency_access` | Emergency access | `access.breakglass.request` | Anything else: the role only lets its holder ask for a break-glass elevation. |

The administration `editor` and `viewer` roles are built-in too. Elitea defines no set for them: they keep the set they held at the upgrade (empty on a new deployment). On a deployment upgraded from the legacy platform, the administration `system` role is also built-in; it keeps its set and is never assigned.

**The sets are locked.** The server refuses to rename or delete a built-in role (`409`), and to change its permissions in the Roles matrix (`403` with the code `role_set_locked`), for every caller, a super admin included. A deployment that wants a different set creates a custom role and gives it the permissions. The operator command [`elitea-main admin-role reset <role>`](/deployment/operations#administrative-roles-from-the-command-line) puts a built-in set back to the one Elitea defines.

**Built-in is a record, not a name.** The upgrade records each built-in role in `elitea_auth.admin_role_seeds`. A role that already had one of the new names (for example a custom `llm_manager` or `security_auditor`) before the upgrade is left as it was: it gets no permission, is not recorded and is not locked, and can still be renamed and deleted. The upgrade runs once, so renaming the custom role later does not add the built-in one.

## No escalation

The server makes sure that no administrator can raise their own access, and that no administrator can give a central (administration) role or permission that they do not hold. It applies these rules to the Roles matrix, to role definitions, to the Users page, to the role assignments under `/admin/modes`, to project members, to bulk invites, to the personal and team project matrix and to SCIM group bindings. The central rules hold in the `administration` mode and in the retired `developer` mode alike.

The six rules for central roles:

1. **Grant and assign only what you hold.** You can add a permission to a central role, or remove one from it, only if you hold that permission yourself. You can assign or remove a central role only if you hold every permission of that role. Removing counts, so an administrator with fewer permissions cannot demote one with more.
2. **Not yourself.** You cannot give yourself a central role, or take one away from yourself, on the Users page or under `/admin/modes`. Another administrator makes that change. The first administrator comes from `identity.initial_global_admins`, which applies only while no active account holds `super_admin`, or from the operator command `elitea-main admin-role grant`.
3. **Your own role is locked.** You cannot change the permissions of a central role that you hold.
4. **Seeded only.** Six permissions are granted by the upgrade migrations only, and no change through the console or the API adds them to a role: `admin.auth.users.super_admin`, `identity.sso.trust.manage`, `access.breakglass.request`, `access.breakglass.approve`, `access.breakglass.manage` and `access.breakglass.review`.
5. **Locked sets.** The permissions of a built-in role cannot be changed (see [Built-in administration roles](#built-in-administration-roles)). A role that is never assigned (the legacy `system` role) is assigned to nobody.
6. **Loud.** Every refusal is in the Audit Trail with the action `role.escalation_refused`.

The role name `break_glass` is reserved: creating a role with that name, or renaming one to it, answers `400`.

**The global administrator's exemption.** A holder of `admin.auth.users.super_admin` through a standing role is exempt from rules 1 to 3: it can assign and remove roles, its own included, and edit a custom role it holds. Rules 4 to 6 bind it too: it cannot add a seeded-only permission to another role, edit a built-in set or assign the `system` role.

**What a break-glass elevation adds, and what it never adds.** An elevation adds the permissions of its level's role (`admin` or `super_admin`), read from that role at each request, to the one browser session it is bound to, until it ends or expires. Another browser session of the same person, a personal access token, a desktop or mobile session and a run token get nothing from it. It never adds the role's **name**, so it does not open project content (see [What the name `super_admin` reaches](#what-the-name-super_admin-reaches)) and the Audit Trail lists only your standing roles as the roles you acted with. It never adds the **exemption** either: the rules above read your standing roles only, so under a `super_admin`-level elevation you still cannot give yourself a role, edit a role you hold, give the `super_admin` role, or add yourself to a project you are not a member of, unless a standing role already allows it.

In projects:

- **Project members give only what they hold.** A project member who manages members (`/admin/users/default/{project}`) can give or take a project role only if they hold all of its permissions in that project.
- **SCIM group bindings give only what you hold.** A binding gives its role to the members your identity provider pushes later, and you can be one of them. To create, move or delete a binding, you must hold every permission of its role in its project.
- **No self-escalation in projects.** The admin Projects page, bulk invites, a change to a project role, to the Standard Roles template or to **Apply to Projects** cannot give you a permission in a project that you did not already hold there. Managing the members and roles of other accounts in any project stays the power of a central administrator. A super admin is exempt.
- **Seeded only** (rule 4) holds for project roles and the Standard Roles template too.

A new role always starts with no permissions. Only a super admin can use `append_user_role` on the personal and team project matrix, because it gives the roles to every member of every target project. Clearing a role of the retired `developer` mode needs no subset, because that mode grants nothing.

The server refuses a change that breaks a rule with `403` and a `code`:

| Code | Rule |
|---|---|
| `role_permission_not_held` | 1: you do not hold a permission that the change grants, removes, assigns or takes away |
| `role_self_assignment` | 2: the change gives or takes one of your own central roles |
| `role_own_set_locked` | 3: the change edits the permissions of a role you hold |
| `role_permission_reserved` | 4: the change adds a seeded-only permission to a role |
| `role_set_locked` | 5: the change edits a built-in set, or assigns a role that is never assigned |
| `role_super_admin_required` | only a super admin assigns or removes the `super_admin` role |
| `role_self_escalation` | the change would widen your own permissions in a project |
| `role_caller_unresolved` | your own permissions could not be read, so the change was refused |

The body also names the `role` and the `permissions`. The Roles page shows that reason in place of a generic error. Each refusal is in the Audit Trail with the action `role.escalation_refused`.

<Note>
Nobody can change the permissions of a built-in role through the console or the API, a super admin included (see [Built-in administration roles](#built-in-administration-roles)). The accounts in `identity.initial_global_admins` (`ELITEA_INITIAL_GLOBAL_ADMINS`) get `super_admin` on their first sign-in, but only while no active account holds `super_admin` (see [The first global administrator](/admin/authentication#the-first-global-administrator)).
</Note>

## The last administrator

A deployment always keeps one administrator. The **last administrator** is the last active (unsuspended) account that holds `admin.auth.users.super_admin`, which in practice means the last `super_admin`. The legacy `system` role holds that permission too, but it is never assigned, so its holders (platform accounts) do not count. When nobody holds that permission, it is the last active account with the `admin` role. That second case is for a deployment upgraded from the legacy platform, where people can hold `admin` while nobody holds `super_admin`. On a new deployment nobody holds either role until the first administrator is added, and then there is nothing to protect.

Nobody can demote, suspend, delete or deactivate the last administrator, a super admin included, on any path:

- the Users page and `POST /api/v2/admin/auth_users/administration` (`set_admin_role` and `delete`),
- `DELETE /api/v2/admin/modes/administration`,
- `PUT /api/v2/admin/user_suspend/administration/{id}`,
- SCIM deactivation and `DELETE` (see [Deprovision the last administrator](/admin/authentication#deprovision-the-last-administrator)).

The server answers `409` with the code `last_administrator`, and the Users page shows the reason. A bulk delete that includes the last administrator is refused whole: no account of the selection is deleted. Each refusal is in the Audit Trail with the action `role.last_administrator_refused`.

To replace the last administrator, give a second person the role first, then demote, suspend or delete the first one. If nobody else can give the role (the last administrator has left, or lost access), an operator with access to the `elitea-main` workload runs [`elitea-main admin-role grant`](/deployment/operations#administrative-roles-from-the-command-line). Only that command can override the rule, with `admin-role revoke --override-last-administrator`.

The check runs under the same database lock as every role change, so two administrators who demote each other at the same moment cannot both succeed.

## Role changes are recorded

Every change to a central role assignment that Elitea makes is recorded: on the Users page, under `/admin/modes`, and at the first sign-in of an initial administrator. A grant or a removal writes one record with the account, the role name and mode, what happened (`granted` or `revoked`), who did it, when, and the source of the change. Records cannot be edited or deleted. A record keeps the role name, so it stays readable after a custom role is deleted.

The source says how the change was made:

| Source | Meaning |
|---|---|
| `console` | An administrator signed in through the browser, on the Users page or under `/admin/modes`. |
| `api` | A caller with an access token, on the same routes. |
| `bootstrap` | The first sign-in of an account in `identity.initial_global_admins`. There is no actor. |
| `operator` | The operator command [`elitea-main admin-role`](/deployment/operations#administrative-roles-from-the-command-line), run inside the workload. There is no actor; the record keeps the command's `--reason`. |
| `migration`, `review`, `scim` | Reserved for an upgrade step, a confirmed provisional grant and a SCIM binding to an administration role. A `migration` record has no actor. |

### Security audit events

Each change of who holds what is also a chained security audit event, `admin.access.changed`, that your SIEM receives through the [audit export](/reference/audit-event-schema#adminaccesschanged): a role assigned or removed, a role's permission set edited, a role created or deleted, a membership written by a bulk invite, a global provider's route changed, and a change of identity trust. The event names the actor, the subject and the sets before and after by name. It carries a reason code when one was given, never the reason text. It is written in the same transaction as the change, so a change whose event cannot be written fails and nothing moves.

### Read the holders and the history

Two read routes answer "who holds which administration role" and "who changed it, when and how". The Access page that shows them comes in a later release.

- **`GET /api/v2/admin/access/roles`** lists every account that holds at least one administration role, once, with all its roles. Each role says whether it is built-in (`built_in`, with the built-in record's `marker`) or custom. Accounts without an administration role are not listed.
- **`GET /api/v2/admin/access/history`** lists the records below, newest first. Filter with `user_id` and `role`, page with `limit` (up to 200, default 50) and `offset`. Each row names the account, the role and mode, `granted` or `revoked`, the actor, the time and the source.

Both need `access.roles.view`, or one of the two broader permissions it narrows, `admin.auth.users` and `modes.users`. The built-in `security_auditor` role holds `access.roles.view`, so an auditor reads the holders and the history, but not the user directory: `GET /api/v2/admin/auth_users/administration`, which lists every account with its e-mail address, stays on `admin.auth.users`, and an auditor gets `403` there. The names of administrators appear only in these two reads, because a list of administrators is a target list for phishing.

Replacing an account's role writes two records: the old role `revoked` and the new one `granted`. Removing one of two roles writes one record and leaves the other role as it was. Assigning a role that the account already holds writes nothing and changes nothing. A refused change writes nothing either. Records start at the upgrade that added them: assignments made before it have none. Deleting an account revokes each of its central roles first, with one `revoked` record each that names who deleted it. A change made outside Elitea, such as SQL run by hand against the database, leaves no record.
