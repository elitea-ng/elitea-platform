Users and Roles are two related admin pages: Users acts on individual accounts, and Roles defines what each role is allowed to do.

For an access review, **Export entitlements** on the Users page downloads who holds which role on the platform, each project and each agent, with the governance capabilities each role carries. Identity governance tools can read the same data over SCIM. See [Entitlement export](/admin/enterprise-controls/least-privilege-and-trust#entitlement-export-for-access-reviews) for the format.

## Manage users

Open **Users** in the admin console. The table lists every account on the deployment, with search.

<Steps>
  <Step title="Find the account">
    Search by name or e-mail.
  </Step>
  <Step title="Act on it">
    From the row menu: delete the account, grant or revoke the global admin role, or suspend/unsuspend it. A suspended account cannot sign in.
  </Step>
  <Step title="Review activity">
    Open the activity drawer for a per-user view built on the same audit data as the Audit Trail page.
  </Step>
  <Step title="Export">
    **Export to CSV** downloads the current list.
  </Step>
</Steps>

<Screenshot id="admin-users-table" alt="Admin Users table with row actions" />

<Note>
Invitations do not have a dedicated accept-invite page. A new member accepts an invite by signing in; the invite is resolved by matching their identity on first login.
</Note>

## Edit roles and permissions

Open **Roles**. It shows a permission matrix across three scopes, each a tab:

- **Central** — the administration-mode roles used across the deployment (the ones this admin console itself is gated on).
- **Public Project** — roles available inside the shared public project.
- **Support Project** — roles for the support project, if one is configured for this deployment. If none is configured, this tab reports that rather than an empty grid.

<Steps>
  <Step title="Toggle a permission">
    Click a cell to grant or revoke that permission for that role, within the selected scope.
  </Step>
  <Step title="Create, rename, or delete a role">
    Use the controls above the matrix. A new standard role only reaches projects that already exist once you use **Apply to Projects** next to it — creating the role does not retroactively push it everywhere by itself.
  </Step>
</Steps>

## Narrow administration permissions

Besides the broad central permissions such as `runtime.plugins` and `configuration.governance`, the deployment has narrow ones, each for one subject. The upgrade that adds them grants all of them to the `super_admin` role and all but `identity.sso.trust.manage` to the `admin` role, so both administrator roles keep everything they could do and hold the new names too. No existing grant is removed.

No page or route accepts the narrow names yet. Later releases let each route accept its narrow permission beside the broad one. The built-in narrow roles below hold only a narrow set.

| Permission | Allows | Narrows |
|---|---|---|
| `llm.catalogue.view` | Read global providers, platform models, the default model and prices. Never a credential value. | `configuration.governance` |
| `llm.catalogue.manage` | Create, edit, check, revalidate and delete them; adopt provider models. | `configuration.governance` |
| `llm.policy.view` | Read gateway governance rules (routing, throttles, guardrails) and the guardrail and breaker sections; validate a rule expression. | `configuration.governance`, `runtime.plugins` |
| `llm.policy.manage` | Edit routing and throttle rules and the breaker section. | `configuration.governance`, `runtime.plugins` |
| `llm.guardrails.manage` | Edit guardrail rules and the guardrail sections, including the fail mode. | `configuration.governance`, `runtime.plugins` |
| `llm.usage.view` | Read gateway status, usage, request logs and budget alerts. | `configuration.governance` |
| `llm.alerts.manage` | Edit budget alerts. | `configuration.governance` |
| `platform.config.view` | Read Configuration sections that have no narrower permission, and Features. | `runtime.plugins` |
| `platform.config.manage` | Edit them. | `runtime.plugins` |
| `identity.sso.view` | Read identity providers, SCIM clients and SCIM group bindings. | `runtime.plugins`, `admin.auth.users`, `configuration.roles.user_project_permissions.view` |
| `identity.sso.settings.manage` | Edit what does not change trust: the display name, the button text and order, the attribute mapping other than its identity fields, and whether an existing provider is enabled; revoke and delete a SCIM client; edit SCIM group bindings to project roles (you still give only what you hold). | `runtime.plugins`, `admin.auth.users`, `configuration.roles.user_project_permissions.edit` |
| `identity.sso.trust.manage` | Change whom the platform trusts: create or delete an identity provider; change its issuer, metadata URL, client credentials, signing certificate, adoption flags and the identity fields of its attribute mapping; create or rotate a SCIM client. Equivalent to `super_admin`, and granted to `super_admin` alone. | none (today these actions need `admin.auth.users.super_admin`) |
| `platform.email.manage` | Read and edit e-mail settings; send a test. | `runtime.plugins` |
| `platform.maintenance.manage` | Read and set maintenance mode; use the application during a window. | `runtime.plugins` |
| `platform.operations.view` | Read system information, tracing status, background jobs and tasks. | `runtime.plugins` |
| `platform.operations.manage` | Cancel a background job; start the notice run. | `runtime.plugins` |
| `mcp.catalogue.manage` | Read and edit prebuilt MCP servers. | `runtime.plugins` |
| `projects.members.manage` | Add, change and remove members of any project, without widening your own access. | `configuration.users.users.create`, `.edit` and `.delete` |
| `projects.settings.view` | Read the guarded settings of any project. | none (new) |
| `projects.settings.manage` | Edit the guarded settings of any project. | none (new) |
| `access.roles.view` | Read who holds which administrative role, tokens with administration access, the elevation history and the access posture. | `admin.auth.users`, `modes.users` |
| `access.breakglass.request` | Request an elevation. | none |
| `access.breakglass.approve` | Approve or deny another person's request; end an elevation. | none |
| `access.breakglass.review` | Review an ended elevation. | none |
| `access.breakglass.manage` | Edit the break-glass settings; read the sealed credential list. | none |

`identity.sso.trust.manage` and the four `access.breakglass.*` permissions are seeded-only: an upgrade grants them, and they are not meant to be added to other roles from the Roles matrix.

<Note>
Six names are not a narrower part of an existing permission. `projects.settings.view` and `projects.settings.manage` are a privilege increase: once the project settings gate accepts them, both administrator roles can read and change the guarded settings (cloud executor, worker egress, AI disclosure, browser, computer use) of a project they are not a member of. `identity.sso.trust.manage` names a power that `super_admin` already has. The four `access.breakglass.*` names belong to break-glass elevation and allow nothing until that feature ships; then every holder of `admin` can use them.
</Note>

## Built-in administration roles

Six built-in roles of the central administration mode hold a set of permissions that Elitea defines. The upgrade that adds the four new ones creates them with their sets; it assigns them to nobody.

| Role | Shown as | Permissions | Cannot |
|---|---|---|---|
| `super_admin` | Global administrator | Every administration permission. Alone among the assignable roles it holds `admin.auth.users.super_admin` and `identity.sso.trust.manage`. | Hold `security.signals.reidentify`; that permission goes to no built-in role. |
| `admin` | Platform administrator | Every administration permission except `admin.auth.users.super_admin` and `identity.sso.trust.manage`. | Make a global administrator, or change whom an identity provider vouches for. |
| `llm_manager` | LLM manager | `llm.catalogue.view`, `llm.catalogue.manage`, `llm.policy.view`, `llm.policy.manage`, `llm.usage.view`, `llm.alerts.manage`, `models.admin.project_budgets.view`, `models.admin.project_budgets.edit`, `projects.projects.projects.view` | Manage users, roles, identity providers, SCIM, tokens, project members, branding, e-mail, maintenance, retention, the kill switch, the agent registry, delegation reviews, worker egress or guardrails. |
| `project_administrator` | Project administrator (all projects) | `projects.projects.projects.view`, `projects.projects.projects.edit`, `projects.projects.project.create`, `projects.projects.project.delete`, `projects.members.manage`, `projects.settings.view`, `projects.settings.manage`, `configuration.users.users.view`, `configuration.roles.roles.view`, `configuration.roles.user_project_permissions.view`, `invites.bulkusers`, `invites.bulkprojects`, `admin.moderation`, `admin.moderation.edit`, `models.admin.project_budgets.view` | Change platform configuration or LLM settings, identity providers or SCIM bindings, edit the project role matrix, assign administrative roles, suspend or delete users, or configure the credentials, models and toolkits of a project. It cannot read project content without a membership, and cannot give itself one. |
| `security_auditor` | Security auditor | `models.admin.audit_trail.view`, `access.roles.view`, `access.breakglass.review`, and the security signal permissions when security signals ship | Use any route that writes or approves, other than attesting a break-glass review. Never `security.signals.reidentify`. |
| `emergency_access` | Emergency access | `access.breakglass.request` | Anything else: the role only lets its holder ask for a break-glass elevation. |

The administration `editor` and `viewer` roles are built-in too. Elitea defines no set for them: they keep the set they held at the upgrade (empty on a new deployment). On a deployment upgraded from the legacy platform, the administration `system` role is also built-in; it keeps its set and is never assigned.

**The sets are locked.** The server refuses to rename or delete a built-in role, and to change its permissions in the Roles matrix, for every caller, a super admin included. The refusal is `409`. A deployment that wants a different set creates a custom role and gives it the permissions. The operator command `elitea-main admin-role reset <role>`, which a later release adds, puts a built-in set back to the one Elitea defines.

**Built-in is a record, not a name.** The upgrade records each built-in role in `elitea_auth.admin_role_seeds`. A role that already had one of the new names (for example a custom `llm_manager` or `security_auditor`) before the upgrade is left as it was: it gets no permission, is not recorded and is not locked, and can still be renamed and deleted. The upgrade runs once, so renaming the custom role later does not add the built-in one.

## No escalation

The server makes sure that no administrator can raise their own access, and that no administrator can give a central (administration) role or permission that they do not hold. It applies these rules to the Roles matrix, to role definitions, to the Users page, to the role assignments under `/admin/modes`, to project members, to bulk invites, to the personal and team project matrix and to SCIM group bindings:

- **Grant only what you hold.** You can add a permission to a central role, or remove one from it, only if you hold that permission yourself.
- **Assign only what you hold.** You can assign or remove a central role only if you hold every permission of that role. Removing a role counts, so an administrator with fewer permissions cannot demote one with more.
- **Your own role is locked.** You cannot change the permissions of a central role that you hold.
- **The super admin permission stays on the super admin role.** `admin.auth.users.super_admin` can be granted only to the administration `super_admin` role. This rule applies to super admins too.
- **Project members give only what they hold.** A project member who manages members (`/admin/users/default/{project}`) can give or take a project role only if they hold all of its permissions in that project.
- **SCIM group bindings give only what you hold.** A binding gives its role to the members your identity provider pushes later, and you can be one of them. To create, move or delete a binding, you must hold every permission of its role in its project.
- **No self-escalation in projects.** The admin Projects page, bulk invites, a change to a project role, to the Standard Roles template or to **Apply to Projects** cannot give you a permission in a project that you did not already hold there. Managing the members and roles of other accounts in any project stays the power of a central administrator.

A super admin (a holder of `admin.auth.users.super_admin`) is exempt from all rules except the fourth. A new role always starts with no permissions. Only a super admin can use `append_user_role` on the personal and team project matrix, because it gives the roles to every member of every target project. Clearing a role of the retired `developer` mode needs no subset, because that mode grants nothing.

The server refuses a change that breaks a rule with `403` and a `code`: `role_permission_not_held`, `role_own_set_locked`, `role_permission_reserved`, `role_super_admin_required`, `role_self_escalation` or `role_caller_unresolved`. The body also names the `role` and the `permissions`. The Roles page shows that reason in place of a generic error. Each refusal is in the Audit Trail with the action `role.escalation_refused`.

<Note>
Nobody can change the permissions of a built-in role through the console or the API, a super admin included (see [Built-in administration roles](#built-in-administration-roles)). The accounts in `identity.initial_global_admins` (`ELITEA_INITIAL_GLOBAL_ADMINS`) get `super_admin` on their first sign-in.
</Note>

## Role changes are recorded

Every change to a central role assignment that Elitea makes is recorded: on the Users page, under `/admin/modes`, and at the first sign-in of an initial administrator. A grant or a removal writes one record with the account, the role name and mode, what happened (`granted` or `revoked`), who did it, when, and the source of the change. Records cannot be edited or deleted. A record keeps the role name, so it stays readable after a custom role is deleted.

The source says how the change was made:

| Source | Meaning |
|---|---|
| `console` | An administrator signed in through the browser, on the Users page or under `/admin/modes`. |
| `api` | A caller with an access token, on the same routes. |
| `bootstrap` | The first sign-in of an account in `identity.initial_global_admins`. There is no actor. |
| `migration`, `operator`, `review`, `scim` | Reserved for an upgrade step, the operator command, a confirmed provisional grant and a SCIM binding to an administration role. A `migration` record has no actor. |

Replacing an account's role writes two records: the old role `revoked` and the new one `granted`. Assigning a role that the account already holds writes nothing and changes nothing. A refused change writes nothing either. Records start at the upgrade that added them: assignments made before it have none. A change made outside Elitea, such as SQL run by hand against the database, or the roles removed with a deleted account, leaves no record.
