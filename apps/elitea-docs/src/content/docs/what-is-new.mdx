Elitea ships frequent, small releases. This page summarizes the most recent user-visible changes; it is not a full changelog.

## Pipeline editor fixes

In the pipeline editor, the Agent, Toolkit and MCP node pickers and the LLM node's **Output contract** now open inside the node, and an LLM node's **Toolkits** list shows the tools a toolkit has enabled instead of **None (0/0)**. Removing a route from a Router node with the chip's **X** also removes its connection line. Router **Condition**, State Modifier **Jinja Template** and Decision **Description** fields get a copy and full-screen button on hover, and the plain **Value** full-screen editor now fills the whole window. The Type and Value rows of node inputs line up on one underline.

## Chat says why an agent could not answer, and Skills are in the + menu

When a message to an agent cannot start, the error now names the reason (for example, that the agent's model is not available in the project, or that the conversation no longer has the agent) instead of the same sentence every time. The **+** menu in the chat has a **Skills** row: it puts a `~` in the message box and opens the skill picker. The SharePoint **Login** button for a delegated credential now opens the Microsoft sign-in window; the platform reads the identity provider's OAuth metadata for it, so a provider on a private network needs the platform's MCP OAuth egress allowlist. See [Chat](/menus/chat).

## Fixes: notifications, toolkit sign-in, the toolkit list and participants

Every notification in the Notifications Center now has text; a kind of event the page has no sentence for shows its name (for example "Agent approval required"). The log-out icon next to a credential that signs in when you use the toolkit appears only while you are signed in, so it no longer reports a log-out that did not happen. Clicking **Toolkits & Indexes** or **MCPs** in the sidebar no longer takes you to the Create page while the list is loading again. When removing someone from a conversation is refused (the conversation's owner cannot be removed), the page says why. The toolkit editor in a chat says in words when **Save** saved, was blocked by fields that are not valid, or was refused by the server, and the SharePoint **Login** button says why when it cannot start the sign-in.

## Agent versions, import and publishing fixes

The version list puts the pinned default first and `base` last, and a pinned default stays selected when you reopen the agent. **Fork** copies the version you have open, not the newest one. **Share** is now two clear items, **Share version link** (opens that version) and **Share agent link**. **Compare versions** is also in the ⋮ menu. **Import** accepts `.md` agent files and `.zip` files of them as well as `.json`. A saved welcome message and conversation starters show in a new chat with the agent. An uploaded icon shows on the agent's card. An agent can hold up to 50 skills (it was 5). Publishing now marks the missing fields instead of doing nothing, and a passing check can be published when the platform runs on several replicas. **Build with AI** is back on the new-agent page, and the Stop agent button is readable in the light theme. See [Import and export](/how-tos/agents-pipelines/import-export) and [Forking](/how-tos/agents-pipelines/forking).

## The agent page has its chat back

The chat panel on the right of the agent page works again, also on a new agent right after you save it. Its conversation belongs to the agent and no longer lands in your **Chats** list; **Open in Chats** in the toolbar starts an ordinary conversation when you want one there. The Instructions field now grows with its text instead of filling the page. See [Test the agent](/menus/agents#test-the-agent).

## Length limits on names and descriptions

A name (agent, pipeline, toolkit, credential, personal access token, folder, conversation, skill) is now at most 128 characters and a description at most 2000. The forms in the web, desktop and mobile apps show a character counter near the limit and block Save past it; the API answers 400 with the field and the limit. **Run the migrations:** stored text over the limits is truncated. See [Create a personal access token](/getting-started/create-personal-access-token#name-limit).

## Fixes: language, toolkits, notifications, tokens

The web app now starts in the language you pick under **Language** in the account menu; before, it saved the choice and stayed in English (the choice is saved to your account, so the desktop app opens in the same language). The Toolkits page lists your toolkits when you come back to it after creating one. **Create new** next to a toolkit's configuration picker opens the create page in a new tab, so the toolkit you are filling in is kept; use the picker's refresh when you return. Deleting or marking notifications in the Notifications Center works again, and the expiry unit list on **Create personal token** is readable in the dark theme.

## Avatar packs move with the agent, and play on mobile

Fork, export and import now carry an agent's avatar pack and its files, so a forked or imported agent keeps every state. A generated loop now takes about as long as one picture. Generated and uploaded avatar files that no version uses are deleted after 7 days. The mobile app plays animated WebP and video states. See [Avatar](/menus/agents#avatar).

## Watch cloud sub-agents work

A sub-agent that a cloud run starts with `spawn_agent` now shows as a temporary participant under that call, live and after a reload. Its row has the sub-agent's name, a dashed avatar ring, a **Temporary** badge and its status. Opened, it shows the sub-agent's own tool calls, its text and its final answer. Arguments and results are short summaries, and secrets are masked. The web app, the desktop app and the mobile app show it. A reload shows the lanes once Main is upgraded too. See [Watch a sub-agent work](/how-tos/agents-pipelines/sub-agent-profiles#watch-a-sub-agent-work).

## Several agents in a desktop thread

A **Local work** thread in the desktop app can now hold more than one agent. Add agents from the composer's agent chip, under **Also in this thread**, to run on this computer or in the cloud, and write **@Name** to address a message: the agents you name answer one after another, in your order, and each answer says which agent gave it and where it ran. An agent in the cloud gets the conversation's text only, never your folder, its files or the thread's tools. **Run the migrations.** See [Use several agents in a thread (desktop)](/how-tos/chat-conversations/desktop-multi-agent/).

## Automatic hiring and dismissal of agents

A project can now hire and dismiss agents automatically, under **Settings → Agent workforce**, which only agent managers (`agents.workforce.manage`) see. Both are off until a manager turns them on. Automatic hiring creates an agent only from a low-tier, read-only proposal whose spec ran successfully enough times, unpublished and with no tools bound, on probation until a manager keeps it; for 14 days a manager can undo the hire. Automatic dismissal applies the project's rules to each agent's scorecard: watch and suspend apply at once, and retire waits for a grace period during which the owner can object. The policy never demotes or deletes and leaves critical-tier agents and agents under legal hold alone. Agents whose owners left the project are flagged for a new owner and moved to watch after 30 days. See [Automatic hiring and dismissal](/how-tos/agents-pipelines/agent-workforce/#automatic-hiring-and-dismissal).

## Proactive agents

An agent can now have a **heartbeat**: the platform wakes it on a timer, a small model reads its goals and the new messages, and the agent does nothing, sends you a message in its home thread with a notification, or starts a run under your mandate that waits for you at every approval. Add a `proactivity` block to the agent, publish it, and turn the heartbeat on in the agent editor's new **Heartbeat** tab, which also shows each wake. The agent must be at least medium risk with a reviewed release, except in your personal project. Daily limits on wakes, runs and spend, quiet hours, the kill switch and **Configuration › Proactive agents** keep it in bounds. Cloud agents only. See [Proactive agents](/how-tos/agents-pipelines/agent-heartbeat/).

## Agent scorecards and the dismissal ladder

Every agent now has a daily scorecard on a new **Workforce** tab: runs and failure rate, budget-cap stops, breaker trips, approval rejections, guardrail hits, spend against the project median, feedback and last use. A person, or a reviewer agent with the `can_review_agents` capability, can propose **Watch**, **Demote** (taking away exactly what it names), **Suspend**, **Retire** or **Delete**; a person with the new `agents.workforce.manage` permission or the agent's owner decides, after an impact preview. A retired agent leaves conversations, saved teams, nesting and schedules and can be **reinstated** for 30 days. The owner can appeal once to a different manager. Critical-tier agents and agents under legal hold are exempt. **Upgrade every worker before Main.** See [Agent workforce](/how-tos/agents-pipelines/agent-workforce/).

## Agents can propose new agents

An agent with the `can_propose_agents` capability can now propose that a sub-agent that worked well is kept as an agent of its own. The proposal appears under the answer in the chat and in a **Proposals** inbox on the Agents page. **Review** opens the agent form filled in from the sub-agent, with its soul, its tools and their categories, and memory entries to start with; nothing is saved until you select **Create agent**, and the new agent starts at the Low risk tier. An agent has at most 3 open proposals, and a dismissed one is not proposed again for 30 days. **Save locally as AGENTS.md / SOUL.md** downloads the proposal instead. A personal agent also has **Copy to project**: an independent copy in a team project, with the memory you pick. **Upgrade every worker before Main.** See [Agent proposals and Copy to project](/how-tos/agents-pipelines/agent-proposals/).

## Agent avatar packs

An agent version can now have its own avatar for each state: a still, and an image, an animated WebP, or a muted MP4 or WebM loop for idle, thinking, speaking, working, waiting, success, error and waking. Set them on the agent editor's new **Avatar** tab, which previews every state before you save. The server checks every file: at most 4 seconds, 512 px and 2 MiB, no sound, and an SVG with no script. With an image generation model, **Generate** makes still candidates from the persona and loops from the still. A state with no file keeps the default motion. **Run the migrations.** See [Avatar](/menus/agents#avatar).

## Sub-agent profiles and briefs

`spawn_agent` now takes a `profile`: a display name, a short role (the soul), the tools, the model (`inherit`) and an avatar key. It also takes a `context` brief: quotes of messages, this turn's attachments, facts and recalled memory entries. The platform checks that the agent itself sees each reference, and refuses the call when it does not. Each spawn of a cloud run is recorded once, by digest, never by its text. A local turn in the desktop app now checks a brief too: it accepts quotes of the messages its agent read and the images attached to the current message. It still refuses memory entries. See [Sub-agent profiles and briefs](/how-tos/agents-pipelines/sub-agent-profiles/#in-the-desktop-app).

## Limit an agent's tools

An agent version can now limit how often each tool may be called in a turn, name the tools it may use when another agent hands it the floor, and name the tools its sub-agents may get, writes included. Administrators set a ceiling on calls of one tool and the tools that write and may still run with nobody present, under **Configuration › Agent tools**. Every control only narrows the agent's tools. **Upgrade every worker before Main.** See [Limit an agent's tools](/how-tos/agents-pipelines/agent-tool-envelope/).

## Agents are summarized while idle, each with its own meter

When an agent's answer ends and the conversation goes quiet, the platform summarizes that agent's history just before the provider's prompt cache expires, as a cached continuation of the agent's own last request. Each agent has its own check: a person's message or another agent's answer doesn't cancel it, and the same agent's next turn does. Each agent's row in the participants panel shows how full its own context is. The desktop app does the same for each agent of a local thread. See [Idle compaction in the cloud](/how-tos/chat-conversations/context-management#idle-compaction-in-the-cloud).

## Watch and take over a cloud browser

When an answer's run used the cloud browser, the chat's side panel now has a **Browser** tab with the live page, its address and who drives it: **Agent** or **You**. Select **Take over**, or just click or type in the page, to use the browser yourself, for example to sign in; select **Hand back** and leave the agent a note. A person who may only read the conversation can watch but not take over. The view needs an administrator to turn on the live view. The desktop app shows the same tab in a chat, and in a Local work thread that runs in the cloud, in place of its local browser. See [Watch and take over](/integrations/toolkits/cloud_browser_toolkit#watch-and-take-over).

## Agent avatars in chat

**An agent's answer now shows the agent's own icon** instead of the Elitea mark, with the persona's display name and role. An ephemeral agent's answer has a dashed ring and a **temporary** marker, and a heartbeat message has a **woke up** marker. While an agent answers, its avatar moves with its state: thinking, speaking, working, waiting for you, waking up, done or failed. Only one avatar moves at a time, and reduced motion shows the still icon. The web app, the desktop app and the mobile app look the same. See [Agent avatars](/menus/chat#agent-avatars).

## Who is speaking in a chat

Every chat participant now has a kind (a person, an agent, a short-lived agent, or the system), and an agent shows its persona's display name, pronouns and role. Each message records whom it is for, whether it is agent-to-agent talk, and what started it. While an agent answers, the chat knows which participant is answering and whether it is thinking, speaking, working, waiting for you, done or failed. Existing messages are filled in when you upgrade. See [Who is speaking](/menus/chat#who-is-speaking).

## Agent personas

An agent version can now have a persona: a display name, pronouns, a role, a voice, values, boundaries, relationships with other agents and people, and a free-form body. Edit it on the agent editor's new **Persona** tab; the model reads it after the guardrails and before the instructions. A persona shapes how the agent speaks and grants nothing: Save refuses one that names a tool, a credential or a permission. Export, import and fork carry it, and in the desktop app a `SOUL.md` next to a Local work folder's `AGENTS.md` does the same for that folder. **Upgrade every worker before Main.** See [Persona](/menus/agents#persona).

## One page layout on the web and the desktop

**Every page now has the same layout in the browser and in the desktop app.** The title bar shows a breadcrumb, for example **Toolkits › New toolkit**; select the section to go back to its list. Pages no longer show a second, large title or a back arrow. Under it, one toolbar has the page's tabs or a count on the left, and on the right the search box, **Filters**, the card/table switch, secondary actions such as **Import**, and the primary **+ New** button (for example **+ New agent** or **+ New credential**). The search text is kept in the page address, and `/` goes to it. **Tags, type filters and the author card are now in the Filters tab of the side panel on the right**, instead of a column over the page: in the desktop app it is an inspector tab, and the web app has a new side panel with the same tabs, which also holds the chat's **Conversation** participants. **The web sidebar now has the structure of the desktop sidebar**: the project switcher, your chats and the platform sections, with a **+** on each section to create an item of that kind. It replaces the split **+ Chat** create button. **The desktop app now has the notification bell** in its sidebar, and shows a system notification when a notification arrives while the window is not in focus; turn the system notifications off with **Show system notifications** under **Settings › Notifications**. See [Page layout](/menus/page-layout). **The web sidebar now ends with the account menu of the desktop app**: select your name to reach **Settings**, **Credentials**, the **Catalog**, help, **Appearance**, **Language** and **Sign out**, and to see **the app and server versions** (select the line to copy it). Administrators also get **Admin portal**, in the browser and in the desktop app. The admin console has the same menu, with **Back to Elitea**, and no theme switch of its own: it follows the theme you choose in the app. See [Account menu](/menus/overview#account-menu).

## Grounding indicators

An agent can now cite its sources. In the agent editor, open **Advanced** and select **Require citations**. The worker numbers each tool result of the current turn, and the model cites the results as `[1]`, `[2]`. Under the answer, the chat shows **N of M sources cited** and **K statements without a citation**. Click the second part to see those statements. The message keeps the indicator as `meta.grounding`, and each run records a `grounding_check` step without the answer text. There is still no confidence score: a cited source does not prove the statement. An answer without tool results has no indicator. **Upgrade every worker before you turn on citations.** See [Grounding indicators](/admin/enterprise-controls/content-controls#grounding-indicators).

## Clearer egress refusals and an OIDC relink command

**Test connection now names the host that the egress allowlist refused**, and tells where to add it: first a governance entry under **Admin › LLM Governance** (type **Egress allowlist**), then the `GATEWAY_EGRESS_ALLOWLIST` floor of the LLM gateway. The machine-readable reason (`egress_not_allowed`) does not change. A toolkit check names the refused host and `ELITEA_TOOLKIT_CHECK_ALLOWLIST`, with one message for every refusal; the elitea-main log gives the reason and says whether an allowlist entry can help. A refused listing of a provider's models names the refused host too. Vertex AI needs its regional host, for example `europe-west4-aiplatform.googleapis.com`. See [When the egress allowlist refuses a provider](/admin/llm-proxy#when-the-egress-allowlist-refuses-a-provider).

When an identity provider re-creates a user, the user's OIDC `sub` changes and the login is refused with 409. The new operator command `elitea-main oidc-relink` moves the account to the new subject, or clears the old link so that the next login links again by email. It prints a plan first, refuses ambiguous cases and SCIM-provisioned accounts (use `--clear` for those), and writes a security audit event with no subject in it. The 409 now names its cause: only the re-created-subject case points to the command, and a SCIM account points to the provider's `adopt_scim_users` setting. See [When an OIDC login answers 409](/admin/authentication#when-an-oidc-login-answers-409). The authentication page also states the OIDC sign-in rules: `"email_verified": false` is always refused, whatever `OIDC_REQUIRE_EMAIL_VERIFIED` says. See [Relink an account](/admin/authentication#relink-an-account-after-the-identity-provider-re-created-a-user).

## Simpler Helm values for a production install

**One value now fills the public URL everywhere.** Set `global.publicUrl` and the chart fills `DEPLOYMENT_URL`, the OIDC redirect URI, the authentication document's `public_origin`, the gateway's self origins, the worker's base URL and SPIFFE ID and the Ingress host, where you have not set them. `global.trustedProxyCidrs` fills both trusted-proxy lists. `certManager.issuers` names the two mTLS issuers once for every component, and `certManager.issuers.create: true` makes the chart create them, namespaced, over your existing runtime CA. **The chart refuses a values file that still holds a `<...>` placeholder**, and lists each path. Components export traces to the bundled collector by default, or turn export off when there is none. Every container requests at least 50m CPU, the GKE Autopilot minimum. `deploy/scripts/mint-secrets.sh` mints every generated secret as one flat JSON object for a secret manager. `values-gke.yaml` uses all of this; **read "Release-wide settings" in `docs/UPGRADING.md` before you upgrade an install made from it.** See [Configuration](/deployment/configuration#release-wide-settings) and [Deploy on GKE with Argo CD](/deployment/gke-argocd).

## Content guardrails at the LLM gateway

A new governance entry type, **Content guardrail**, checks model content at the LLM gateway. An entry runs on the request before the provider call (`input`) or on the answer (`output`), for a platform, project, model or agent scope. Its detectors find bounded RE2 patterns and terms, the platform secret rules (for example AWS keys, GitHub tokens and private keys), or the findings of a classifier that you operate, through a documented HTTP adapter contract. Each detector blocks, masks or flags. **A blocked request gets HTTP 400 `guardrail_blocked`; a blocked stream ends with a typed error event.** A streamed mask holds back a short window of text, so that the client never gets a matched value, also when the value is split across chunks. Each check is recorded as a verdict without the matched text, and the run steps API returns the verdicts of a run. Nothing changes until you create an entry. See [Guardrail pipeline](/admin/enterprise-controls/content-controls#guardrail-pipeline).

## Output contracts

Agents and pipeline LLM nodes can now have an output contract: a JSON Schema, a regular expression, or a named format (`json`, `markdown` or `csv`). Set it under **Advanced › Output contract** in the agent editor, or in the settings of an LLM node. The worker sends a JSON Schema to providers that support a response schema, and validates each final answer. If an answer is not valid, the model gets one more try with the validation error. If the second answer is also not valid, the run stops with `OUTPUT_CONTRACT_VIOLATION`, and **a pipeline does not run the next node**. A save with a contract that is not correct fails with `OUTPUT_CONTRACT_INVALID`. Each check is a run step record. **Upgrade every worker before you save a contract.** The platform does not give a confidence score; the same page tells why, and how to get a confidence field from the agent. See [Output contracts](/admin/enterprise-controls/content-controls#output-contracts).

## AI disclosure, platform preamble and untrusted content

**Outbound tools now add an AI disclosure marker** to the text that they send outside the platform: Jira, GitHub, GitLab, Bitbucket, Azure DevOps and Aha! comments, GitHub, GitLab, Bitbucket and Azure DevOps pull request descriptions, new GitHub and Jira issues, new Azure DevOps work items, Confluence pages, Salesforce cases, Figma file comments, Slack messages and Gmail messages. The default text is `Generated with Elitea AI`, and Markdown targets also get the run id in a hidden comment. Administrators set the text under **Configuration › AI Disclosure**, and a project can change it in its **AI disclosure** project setting, but it cannot remove it. **Every tool result now reaches the model in an `<untrusted>` envelope**, and a short built-in preamble tells the model that this text is data, never an instruction. Administrators can add their own **Platform preamble**, which goes before every agent's system prompt; each change is a revision with an audit event, and each turn keeps the revision that it started with. At the high and critical tiers, a `delete`, `external_send` or `payment` call after a tool result in the same turn asks for an approval (`approval_rule` source `untrusted_read_then_act`). See [Content controls](/admin/enterprise-controls/content-controls).

## Agent circuit breaker

A new routine checks every agent once a minute. **An agent is stopped when more than 50 % of its latest 20 runs failed, or when one tool failed 5 times in a row in one run.** Limits for spend per hour and runs per hour are also available, but they are off by default. The stop is a kill-switch suspension: new runs are refused, runs in flight are cancelled, and the agent stays stopped until a person resumes it. A platform administrator must resume a high-tier agent, and two different platform administrators must resume a critical-tier agent. The agent's owners and the project admins get a notification, the security audit log gets an `agent.breaker` event, and **Admin › Kill switch** shows the rule and the observed value. When many agents fail at the same time (more than 5), the breaker stops none of them and raises an alert, because a shared dependency is the likely cause. Set the limits per risk tier under **Configuration › Circuit Breaker**; an agent's registry record can only make them tighter. The Helm chart adds Prometheus alerts for breaker trips and active suspensions; a platform stop is critical. See [Agent circuit breaker](/admin/enterprise-controls/runtime-safety#agent-circuit-breaker).

## Throttles per agent and per user

A **Rate limit** entry under **LLM Governance** can now name agents (`scope.agent_ids`) or users (`scope.user_ids`). Each named agent or user then gets its own per-minute counter at the LLM gateway, in addition to the project rate limit. When the counter is full, the gateway refuses the call with `429` and `Retry-After`; the agent and the user are not suspended. Like the project rate limits, throttles fail open when the shared counter is not available. The toolkit reference pages now also show the category of each tool, generated from the tool category contract. See [Throttles per agent and per user](/admin/enterprise-controls/runtime-safety#throttles-per-agent-and-per-user).

## Run caps per risk tier

Every agent run now has caps on its tool calls, model turns, spend and records read, set for each risk tier under **Configuration › Run Caps**, next to the existing maximum run time. **A run now stops after 200 toolkit or MCP tool calls by default.** The other caps are off until you set them. Agent authors can lower a cap for one agent in `meta.run_caps`; a save that raises one is refused with `RUN_CAP_ABOVE_TIER`. A run that reaches a cap ends with `CAP_REACHED` and a message that names the cap. A user with the new `safety.override_cap` permission (project admins and platform administrators) can let the conversation's next run pass that cap once; each override is a security audit event. Save the per-tier caps after every worker runs this release. See [Run caps](/admin/enterprise-controls/runtime-safety#run-caps).

## Approval ledger and unattended runs

Every pause and every decision of a sensitive tool or a pipeline review node is now a row in an append-only approval ledger, with the actor, the tool, the toolkit, the digest of the arguments and the decision. Each row is also a hash-chained `agent.approval` event in the security audit log, for every run. When two people decide the same step at the same time, one decision applies and the other gets HTTP 409. **Runs that a schedule or a trigger started never approve a step.** By default (`fail`), such a run now ends with `approval_required_unattended` when it gets to a step that needs approval. Set `on_approval_required` on a schedule or a trigger to `skip` (the model is told that the step was skipped) or `notify_and_wait` (the owner is notified and the run waits, 24 hours by default). The platform default is under **Configuration › Approvals**. See [Approval evidence and unattended runs](/admin/enterprise-controls/runtime-safety#approval-evidence-and-unattended-runs).

## Approval policy by risk tier and tool category

Every built-in tool now has a category: `read`, `write`, `delete`, `external_send`, `payment` or `code_execution`. Under **Configuration › Approval Policy**, administrators select for each risk tier the categories whose tools pause for a human approval. The default asks for `delete`, `external_send` and `payment` tools at the high and critical tiers. The policy adds to the sensitive action tools, and agent authors cannot remove an approval. Each pause names the rule that caused it (`approval_rule`). The same section can require a `hitl` node before every `external_send` or `payment` tool node in pipelines at selected tiers; **a pipeline that breaks the rule does not start** (`PIPELINE_HITL_REQUIRED`). The policy applies after the section is saved; save it after every worker runs this release. See [Tool categories and approval policy](/admin/enterprise-controls/runtime-safety#tool-categories-and-approval-policy).

## Nested pauses

A HITL node can now pause a pipeline that an agent or another pipeline calls, with a maximum of 3 delegations above the node. Each pause shows one approval card with the path of its callers. After you approve or reject, the paused pipeline continues one time, and then each caller continues. When you reject, the caller reads the result of the **Reject** route. **An attached pipeline that can pause in a position that the worker cannot resume is no longer offered to the agent.** Before, such a pipeline failed when it paused. The worker log names the pipeline and the pause kind. See [HITL nodes in nested agents and pipelines](/how-tos/pipelines/nodes/interaction-nodes#hitl-nodes-in-nested-agents-and-pipelines).

## Delegation narrowing

When an agent calls a saved agent or pipeline, a pipeline node runs one, or an agent starts a sub-agent, the delegated agent now runs with only the toolkits, tools, credentials, data classes and egress hosts that its caller also holds. A delegation that needs more is refused with `DELEGATION_GRANT_MISSING`, which names the missing grant. The model reads the refusal, and the run does not fail. **Configuration › Delegation** sets the maximum delegation depth (default 4) and a `report` mode that records missing grants without refusing them. Save it after every worker runs this release; data class narrowing starts when it is saved. Each delegation step records its depth and a digest of its grants. **Compositions deeper than 4, and callees that hold toolkits their callers do not hold, are refused after the upgrade.** See [Delegation narrowing](/admin/enterprise-controls/least-privilege-and-trust#delegation-narrowing).

## Signed assertions for remote agents

An agent's calls to a remote MCP server can now carry a short-lived signed assertion of which agent, run and user called, and with which toolkits (header `Elitea-Agent-Assertion`). The receiver verifies it against this deployment's published keys. Nothing is sent by default: administrators choose `allowlist` (named servers only) or `on` under **Configuration › Remote Agents**; governed runs always send one. The platform's MCP endpoint accepts these assertions from the issuers that an administrator lists under **Configuration › Remote Agents**, refuses replays and expired assertions, and limits every agent and tool that the caller calls to the caller's toolkits. In the governed profile, an agent invoked through MCP needs an OAuth token or a verified assertion; a personal access token alone is refused. A2A is not supported. See [Remote agents](/admin/enterprise-controls/least-privilege-and-trust#remote-agents).

## Connector approval, credential inventory and permission trimming

A new catalogue mode, `approved_only`, makes toolkit types and MCP servers usable only after a connector request is approved by someone other than the requester; approval grants the type and adds its hosts to the egress allowlist, and a custom MCP server's tools are pinned. The default stays `open`, and the governed profile forces `approved_only`. **Admin › Credential inventory** lists every credential an agent can use with its last use, and flags credentials unused for 90 days (revoking stale tokens is opt-in). The **Permission trimming** report compares what each agent is granted with what it used, for one-click audited removal, and notifies owners weekly. See [Least privilege and trust](/admin/enterprise-controls/least-privilege-and-trust).

## Entitlement export for access reviews

Administrators can download who holds which role on the platform, on each project and on each agent, with what each role allows (configure agents, approve change requests, attest, approve connectors and more), as CSV from the admin console's **Users** page. Identity governance tools can read the same data over a read-only SCIM tree at `/api/v2/scim/v2/entitlements`; no SCIM client can read it until an administrator lists it under **Configuration › Entitlement Export**. Every export is audited. See [Least privilege and trust](/admin/enterprise-controls/least-privilege-and-trust#entitlement-export-for-access-reviews).

## Enterprise controls documentation

A new [Enterprise controls](/admin/enterprise-controls/overview) section lists every agent-risk control the platform provides. For each control it says whether the control is available, partial or planned, where to configure it, what evidence it produces and what stays with your organisation's own systems. The section also includes a [shared responsibility](/admin/enterprise-controls/shared-responsibility) page, an [evidence guide for auditors](/admin/enterprise-controls/evidence-guide) and a [hardening checklist](/deployment/hardening-checklist).

## Run step records and chained audit trail

Every agent run now keeps a step record of each model call, tool call, retrieval (with the documents it returned and their scores), approval, delegation, cap, error and its answer, in order and tied to the agent release. The records are hash-chained per run, anchored in the security audit log, exported to your SIEM as the `run_steps` stream, and readable over the API with the new `runs.evidence.read` permission. Step content is kept by reference under the new `step_content` retention class, and a toolkit's `evidence_fields` setting limits what is kept of its results. The admin audit trail is now hash-chained too, with a verification endpoint. Both new retention classes keep forever by default, and no existing data is deleted. See [Audit evidence and retention](/admin/enterprise-controls/audit-evidence-and-retention) and [Reconstruct an agent run](/admin/enterprise-controls/reconstruct-a-run).

## Agent registry, change requests and release gate

Every agent now has a registry record with its owners, risk tier and certification state. Above the low tier, publishing needs a change request approved by someone other than the author, after the agent's evaluation gate passes. **Agents that existed before this release start at tier `medium`, so publishing them now needs one approval**; agents in personal projects and new agents start at `low` and publish as before. Certifications come due on a cadence and lapse if they are not renewed. Reviews done outside the platform are recorded as attestations. See [Agent lifecycle](/admin/enterprise-controls/agent-lifecycle).

## Agent releases and rollback

Publishing an agent now records an immutable release, and every save of a version records who changed what. Open **Release history** from the agent's **⋮** menu to see each release, what changed, and to roll back to an earlier release in one step. Published versions can no longer be changed in place. See [Agent lifecycle](/admin/enterprise-controls/agent-lifecycle).

## Session policy and run time cap

Platform administrators can set a maximum idle timeout and a maximum lifetime for browser sessions, and a maximum time for one agent run. Every session start, expiry, sign-out and revocation is now an audit event. Stopping a toolkit type with the kill switch now also cancels the runs in progress that use it. All new limits are off until you set them. See [Session policy](/admin/authentication#session-policy) and [Runtime safety](/admin/enterprise-controls/runtime-safety#run-caps).

## Worker egress allowlist

Platform administrators can limit the public hosts that agents, toolkits and MCP servers reach from the worker. **Configuration › Worker Egress** shows the hosts that runs reached in the last 30 days and copies them as an allowlist. In `allowlist` mode, a run may reach only those entries, its project's entries and the hosts of its own toolkits; any other host is a tool error that names the host. The default stays `open`. See [Least privilege and trust](/admin/enterprise-controls/least-privilege-and-trust).

A stop of an agent's answer before it writes anything no longer deletes the question on a conversation under legal hold.

## Kill switch

Administrators can stop one agent, one toolkit type, one project or the whole platform at once. Stopping an agent, a project or the platform cancels the runs already in progress. Nothing starts again until someone with authority resumes it, and every stop and resume is recorded in the audit trail. See [Runtime safety](/admin/enterprise-controls/runtime-safety) and the [emergency stop runbook](/deployment/emergency-stop-runbook).

## Audit export to your SIEM

Audit evidence can be sent to your SIEM over OpenTelemetry logs, or to a signed webhook, in one versioned schema. Export is off until an operator configures it. See [Audit event schema](/reference/audit-event-schema).

## Data retention and legal hold

Platform administrators can now set how long conversations, gateway request logs and audit records are kept, and place a legal hold on a project, an agent or a user. The defaults keep today's behaviour, so an upgrade deletes nothing new. A conversation under a legal hold cannot be deleted, not even by its owner.

## Sign-in is single sign-on by default

Deployments now sign people in through OIDC or SAML, with SCIM provisioning. The local username/password sign-in is off unless an operator turns it on, and every local user now needs a real e-mail address — none is invented from the login any more.

## Client deployment readiness

You can now configure a fresh deployment entirely from the UI — set the first global administrators, create a project, and add an AI provider — without running SQL by hand.

## Platform parity wave

A broad pass closed gaps across several areas at once: issue triage fixes, the toolkit catalogue, the support assistant bot, Inventory, and wiki source connections all received fixes and completions.

## Post-release fixes

Follow-up fixes landed for session handling, admin 403 errors, invite links, the maintenance splash screen, voice configuration, artifact bucket access-control lists, and the admin Tasks page. The secrets vault also gained write locking, so concurrent edits to the same secret no longer overwrite each other silently.
