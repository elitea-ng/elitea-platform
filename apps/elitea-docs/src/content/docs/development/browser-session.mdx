In the cloud, a browser tool call runs in a session pod (ADR-0049). The sandbox supervisor (`elitea-sandbox-supervisor`) starts and owns the pod. Inside it, `elitea-browser-session` drives a headless Chrome. `libs/rust/browser-session` (crate `elitea-browser-session`) holds both the binary and its driver, `CdpDriver`. `CdpDriver` implements the `BrowserDriver` trait from [the browser tool contract](/development/browser-tools/). It passes the same conformance kit as every other driver.

## The binary

| Command | Does |
| --- | --- |
| `elitea-browser-session idle` | Holds the container until SIGTERM. This is the image's default command. |
| `elitea-browser-session serve [--engine <path>] [--moli <path>] [--engine-log]` | The supervisor execs this into the container. It speaks the agent line protocol on stdin and stdout. |

The protocol is specified in `libs/proto/elitea/runtime/v1/browser_session_agent_v1.md`. Each message is one JSON object on one line, at most 12 MiB, with binary data in base64.

- The supervisor sends `start`, `call`, `view`, `ack`, `input`, `run_ended` and `destroy`.
- The agent answers with `ready`, `result`, `frame`, `notice`, `error` and `bye`.
- Calls run one at a time, in order.
- `view`, `ack` and `input` are handled at once, even while a call is running.
- The agent sends a new frame only after the previous one is acknowledged, so a slow viewer never queues frames.

The agent writes nothing else to stdout. It logs stable codes to stderr, and logs no page content.

## The engine

The engine is `chrome-headless-shell`, pinned to a Chrome for Testing version. The agent talks to it over the DevTools protocol on `--remote-debugging-pipe`: commands go to the engine's fd 3, and replies and events come back on fd 4. The engine opens no TCP or WebSocket listener, so nothing in the pod can reach CDP, not even on loopback.

The CDP client is small and lives in the crate (`cdp.rs`). It sends a command with an id and an optional flattened session id, matches the reply by id, and broadcasts everything else as an event. The driver names the few dozen methods it uses itself. There are no generated protocol bindings to keep in step with each Chrome release, and no general-purpose browser automation crate, which would want a WebSocket endpoint.

The engine starts with these settings:

- **Network.** All traffic goes through the run's egress proxy (`--proxy-server`, with only loopback bypassed). With no proxy in `start`, the engine has no network at all. The agent answers the proxy's authentication challenge with the run token through `Fetch.authRequired`, so the token is never in argv or the environment. A response carrying the proxy's refusal header, or a refused CONNECT tunnel, is `egress_refused`.
- **Leaks closed.** WebRTC sends no UDP that bypasses the proxy, and QUIC and DNS over HTTPS are off. Downloads are denied, and there is no extension or component update.
- **Sandbox.** The engine keeps its own sandbox. `--no-sandbox` is passed only when `start` says `engine_sandbox: false` and the agent sees that it runs under gVisor, which is then the boundary. Without gVisor, it refuses with `isolation_refused`.
- **One pane.** The viewport is 1280×800 by default. Popups and new windows are folded into the pane: their URL is checked, then opened there.

## Moli (`lite` and `auto`)

`start` names the engine: `full` (Chrome), `lite` (Moli) or `auto` (Moli, then Chrome). Moli is found with `--moli`, or at `/opt/moli/moli` when that file exists. An image without Moli answers `engine_start_failed` for `lite` and `auto`.

Moli has no pipe mode, so the agent runs `moli serve --host 127.0.0.1 --port <free port> --layout --screencast-interval-ms 100`. It reads the CDP WebSocket address from `/json/version` and accepts only `ws://127.0.0.1:<that port>/`. It then bridges the WebSocket into the same CDP connection Chrome's pipe uses, so the driver, the hard limits and the conformance kit are the same code on both engines. The environment is cleared, `HOME` and `TMPDIR` are the session's profile directory, and every request goes through `--http-proxy` with no bypass list. With no proxy, `--http-proxy` points at a closed loopback port. The run token is answered through `Fetch.authRequired`, as on Chrome. Moli has no process sandbox, so `lite` and `auto` are refused (`isolation_refused`) unless the agent runs under gVisor.

An `auto` session moves to Chrome once, and never back, when Moli fails a call in a way Chrome would not:

| Reason | When |
| --- | --- |
| `start_failed` | Moli does not start. |
| `unsupported_protocol` | Moli answers a command the call itself sent as unknown or unsupported. |
| `engine_lost` | Moli exits, or its connection closes, during the call. |
| `timeout` | Moli does not answer a command of the call within 30 seconds and the call fails, or a navigation (`browser_open`, `browser_reload`, `browser_back`, `browser_forward`) times out without reaching a new document. A navigation that reached its document and was only slow to finish loading is the site's and does not switch. |
| `engine_error` | Moli answers a command of the call with JSON-RPC's internal error (`-32603`), and the call fails. |
| `empty_snapshot` | A whole tree snapshot (not cut by `max_nodes`) gives out no ref while the page has visible links, buttons or fields, or custom elements (a hyphenated tag) it never defined, or has no node at all while the page has text. It is read again on Moli after half a second first, so a page that is still rendering stays on Moli. |

Only the call's own commands count (`scoped_faults` in `cdp.rs`). Screencast acks, the page tracker and other background traffic never cause a switch. A failure that would be the same on Chrome never switches either: a `browser_wait` whose condition does not hold, a stale ref, a refused scheme, or a page of plain text with no control on it. The empty-snapshot check asks a page script for text and for controls, looking through open shadow roots. It counts only controls that are rendered (`getClientRects`) and not inside `aria-hidden="true"`, since Chrome's tree leaves those out too. When the script does not run, it falls back to the links, buttons and fields in the DOM the snapshot already read (`DOM.getDocument` pierces shadow roots and frames, but has no layout). A `tabindex` below 0 is not a control. The pages Moli read with no ref keep their links in web components. The script also counts the hyphenated tags the page uses that `customElements` has no definition for: a web-component app whose scripts did not run on Moli has nothing to give a ref to (developer.salesforce.com/docs, #1599). It is only asked when the walk found no control, and a page that defines all its custom elements never trips it.

The agent starts Chrome, opens the page's URL again, and writes the notice `engine_switched`. When the call was a `browser_open`, Chrome opens that call's URL instead, so the old page is not loaded first. A read call (`browser_open`, `browser_snapshot`, `browser_screenshot`) is answered again on Chrome with `engine_switched: {from, to, reason, repeated: true}` in its result. An act (a click, typing, a key, a select, a scroll, a reload, a history step) already ran on Moli, so it is never run a second time: the agent gets Moli's result with `repeated: false` and a note to snapshot again. A `browser_wait` is not run again either: it waits on state the page reached on Moli, such as results after a search, and the page reopened on Chrome no longer has it.

One call, switch included, keeps within 80 seconds of its start: the agent line protocol's 90-second result limit less 10 seconds of headroom, well under the worker's 120-second call deadline. Chrome's start and the reopen get at most 30 seconds of it. A read is answered again only when at least 10 seconds are left after the switch, and only within the budget. Otherwise the switch still happens, so the next call runs on Chrome, but this call gets Moli's result with `repeated: false`. The session keeps its one control, so a person who took over still drives on Chrome. Open views move to Chrome's screencast without reconnecting. The supervisor relays that one notice to every open view, and the web pane shows it.

An `auto` start gives Moli 5 seconds to answer on its CDP port before it falls back to Chrome (`lite` gives it 20), so the fallback keeps most of the 60-second `ready` limit.

## What the driver does

| Part | How |
| --- | --- |
| Snapshot | `Accessibility.getFullAXTree` for each frame, with out-of-process iframes attached through flattened auto-attach. `DOM.getDocument` with shadow roots pierced supplies the `type` and `autocomplete` attributes that mark secure fields. The result is grafted in place and passed to `Snapshot::build`. A whole tree with no ref while requests are still in flight (an app still booting) waits up to 3 seconds for network idle and is read once more, on either engine. |
| Layout on Moli | Moli publishes layout only for a paint (a screenshot or a screencast frame), so after a scroll its `DOM.getContentQuads` answers the old position, and after the page's scripts change the DOM its `innerText` leaves out the new text. On Moli the driver takes a one-pixel screenshot before an element's box, a text wait (at most every 500 ms), the text snapshot and the `auto` page probe. It runs outside the call's fault count and is bounded to 2 seconds, so a refused paint never switches. Chrome lays out on demand and skips it. |
| Click | A mouse press and release at the centre of the element's content quad, after `DOM.scrollIntoViewIfNeeded`. An element with no box, or whose centre is still outside the viewport, gets its own activation (`click()`) instead, so the press never lands off the page. |
| Page scripts | Run in an isolated world, never in the page's own JavaScript world. |
| Refs | Bound to the snapshot they came from. A new document, DOM churn or the person's input invalidates them, and later calls report `stale_ref` with `refs_stale`. |
| Hard limits | `call::check_url` runs on every main-frame navigation. A page-started navigation to a refused scheme goes back to `about:blank`, and the call returns `scheme_refused`. Secure fields are refused on the snapshot flag and on the live element, and `browser_press` checks the focused element through frames and shadow roots. `ActRate` applies to every act. |
| View | `Page.startScreencast` as JPEG starts with the first viewer and stops with the last. Only the newest frame is kept, and acks are paced to `max_fps` (at most 10). |
| Control | **Take over** and the person's own input pause the agent. While the person drives, acts return `user_in_control`, but `browser_snapshot` and `browser_screenshot` still answer. If the person used the page during a call, the call returns `user_active`. `browser_request_user` waits up to 80 s, under the supervisor's 90 s, for a hand back or a decline. A run with nobody to ask (the `start` line's optional `attended: false`, for a schedule or webhook run) answers `no_person` at once. |

## The image

`libs/rust/browser-session/Containerfile` builds `elitea-browser-session` (bake target `elitea-browser-session`):

- the runtime is Debian 13 (`debian:trixie-slim`, pinned by digest), with the libraries the engine links and `fonts-liberation`;
- chrome-headless-shell is fetched from Chrome for Testing at `CFT_VERSION` in a separate stage and checked against a SHA-256 for each architecture, then unpacked to `/opt/chrome-headless-shell`;
- the agent is at `/usr/local/bin/elitea-browser-session`, running as uid and gid 10001 with `HOME=/tmp`;
- the build fails if `ldd` reports a library the engine needs and the image lacks.

The supervisor runs the container with a read-only root and memory-backed `/tmp` and `/dev/shm`.

The image is a Debian userland, so the release scan reports it but does not block on the base's unfixed findings (`.github/image-scan-exempt.txt`).

To move the engine, change `CFT_VERSION` and both checksums in the Containerfile and the same values in `.github/workflows/ci-browser-session.yml` together. The workflow fails when the two disagree.

The `lite` stage (`--target lite`, bake target `elitea-browser-session-lite`) adds Moli at `/opt/moli/moli`. It is fetched from the lexmount/moli release named by `MOLI_VERSION`, checked against a SHA-256 per architecture, and unpacked in its own stage. The full image stays the last stage, so a build without `--target` is unchanged. The lite image is built but not published until the bake-off admits Moli. The Moli pin moves only when the bake-off passes on the new version: change `MOLI_VERSION` and both checksums together, from the release's asset digests.

## Run the tests

Without an engine, the conformance tests report a skip. Point `ELITEA_BROWSER_ENGINE` at a chrome-headless-shell binary to run them:

```bash
cd libs/rust
cargo clippy -p elitea-browser-session --all-targets -- -D warnings
ELITEA_BROWSER_ENGINE=/path/to/chrome-headless-shell cargo test -p elitea-browser-session
```

`tests/conformance.rs` serves the contract's fixture pages on loopback. It runs `conformance::run` with no listed differences, then the hard limits and the view stream, then the line protocol against the real binary. `ELITEA_BROWSER_ENGINE_LOG=1` passes the engine's stderr through.

`ci-browser-session.yml` runs the same tests with `ELITEA_REQUIRE_BROWSER_CONFORMANCE=1`, so a skip fails the job. It then builds the image and runs the protocol test inside it under gVisor (`runsc`), read-only, with no network, as uid 10001. The image size and the engine version the image reports go to the job summary.

`tests/moli.rs` runs the same contract against Moli when `ELITEA_BROWSER_MOLI` names a Moli binary. It checks that Moli starts and reports `moli/<version>`, that its snapshot has refs, and that the hard limits hold. It prints the conformance kit's differences without asserting them. Under gVisor, and with `ELITEA_BROWSER_ENGINE` set, it also drives an `auto` session through the binary.

## The engine bake-off

ADR-0049 decision 9 offers `lite` and `auto` only after a bake-off. The pieces:

- `bakeoff/corpus.json` holds 40 tasks on public pages: Atlassian, Microsoft 365, Salesforce, ServiceNow, GitHub, documentation sites, government forms and single-page apps. There are 5 per class, and 16 `read`, 16 `extract` and 8 `act` tasks. Each task has a URL, optional steps (click or type by role and name, wait) and what must hold afterwards (text, a minimum number of refs, a URL). Sites move: a task that fails on `full` too is stale, and is fixed or replaced in the same class and kind, never per engine. Revision 2 replaced the 8 tasks that failed on `full` in the first real run (42435572555): a Trello board behind a resource check, a Jira "Features" item that is now a menu button, a Word page that is gone, two ServiceNow pages that block or have no text, a Jira article that says "work item" now, the Python library heading's new capitalisation, and the TodoMVC input's new label. Revision 3 replaced 3 more that failed on `full` in run 42445248146: the Jira Pricing link no longer navigates in a headless browser, and both ServiceNow docs articles render 3 refs and no article text without a sign-in. Their replacements are the Atlassian status page's Incident History link, the ServiceNow Community developer blog and the ServiceNow SDK repository on GitHub. Revision 4 replaced that Incident History task, which failed on `full` in run 42447498727 (the link is now a footer link with an arrow in its name): `atlassian-agile-kanban` opens atlassian.com/agile and follows its Kanban link.
- `tests/bakeoff.rs` (`the_bake_off`) runs every task on each engine, one fresh session per task, through the browser tools. The same scripted steps run on every engine. It writes one JSON line per engine and task: success, refs, time to first snapshot, peak memory of the engine's process tree, crash, hang and any `auto` switch. A crash is the engine that answered last being gone after the task, so an `auto` task that left a dead Moli for Chrome is not a crash. It only runs with `ELITEA_BAKEOFF_OUT` set.
- `scripts/ci/browser-bakeoff-report.mjs` applies the admission rule to those lines and writes the report. A run is only a comparison when `full` succeeds on at least half the corpus; below that the verdict is "no comparison", because the run measured the harness or sites that moved, not Moli.
- `.github/workflows/browser-bakeoff.yml` (manual dispatch only) builds the lite image, runs `tests/moli.rs` and the corpus inside it under gVisor, applies the rule, and keeps the lines, the report and the verdict as the `browser-bakeoff` artifact.

A passing verdict does not admit Moli by itself. The report goes into the ADR-0049 appendix, and the change that records it sets `platformconfig.BrowserLiteAdmitted` and publishes the lite image.

To run part of it locally on Linux:

```sh
ELITEA_BAKEOFF_OUT=/tmp/bakeoff.jsonl ELITEA_BAKEOFF_ONLY=docs-rust-std,github-repo \
ELITEA_BROWSER_ENGINE=/path/to/chrome-headless-shell ELITEA_BROWSER_MOLI=/path/to/moli \
cargo test -p elitea-browser-session --test bakeoff -- the_bake_off --nocapture
node scripts/ci/browser-bakeoff-report.mjs /tmp/bakeoff.jsonl
```

Outside gVisor the agent refuses `lite` and `auto`, and `full` with `engine_sandbox: false`, so a local run outside gVisor records start failures. Use the workflow for the numbers that count.
