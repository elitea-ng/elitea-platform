`libs/rust/desktop-control` (package `elitea-desktop-control`) is the layer that drives the person's other applications on their own computer (ADR-0047, #1581). Its caller is the desktop host's `computer` toolset (#1583, `apps/elitea-desktop/src-tauri/src/computer_tools.rs`; see [Let the agent use your other apps](/how-tos/chat-conversations/desktop-computer-use/)). The user-active guard (#1584) will build on it too.

## The trait

`DesktopDriver` is the whole interface. No vendor type crosses it.

| Call | What it does |
| --- | --- |
| `permissions()` | The Accessibility and Screen Recording grants, read live |
| `screen()`, `secure_input()` | The screen state and macOS secure input, read live; the toolset reads them before it asks the person anything |
| `list_apps()`, `list_windows(bundle_id)` | Running apps and their top-level windows |
| `snapshot(target, budget)` | One window's filtered accessibility tree, with refs |
| `act(ref, action)` | Press, set value, focus, select, scroll, expand, collapse, toggle |
| `type_text(ref or None, text)` | Text into an element, or into the focused element |
| `key(target, chord)` | One key chord, such as `cmd+shift+a`, into a window |
| `click_at(click)` | A coordinate click inside one window, in screen points. The window must be the topmost one at the point (CoreGraphics window order) |
| `open_app(bundle_id)` | Launch an app, or bring it forward, and wait up to 10 s for a window |
| `capture(target)` | A window or a screen region as PNG |
| `wait(condition, timeout)` | Polls for a window, a ref state, some text or a stable tree |
| `synthetic_marker()`, `is_synthetic_event(field)` | Tell the driver's own input events from the person's |
| `forget_snapshots()` | Make every ref handed out so far stale |

`default_driver(own)` returns the macOS driver on macOS, the Windows driver on Windows and the Linux driver on Linux (ADR-0047 decision 10, #1586). On any other OS it returns `Unsupported`, which fails every call with `platform_not_supported`.

On Windows and Linux the `bundle_id` of every call is that OS's application id: the executable image on Windows (`notepad.exe`), the desktop entry id on Linux (`org.gnome.TextEditor`, or the executable's own name from `/proc/<pid>/exe` when it has none, such as `xterm`; never the display name, and no id at all when only a 15-byte `comm` that may be cut is known). An interpreter is never the name (`linux_executable_name`, `is_interpreter_name`: `python3.12`, `node`, `bash`, `java`, `gjs`, `perl`, `ruby`, `lua`, `php`, `tclsh` and the like, any version): Terminator and GNOME Secrets both run as `python3.12`. Such an app is named by the script it runs, the first argument of `/proc/<pid>/cmdline` after the interpreter's options (the module for `python -m`, the jar for `java -jar`; a generic `main.js` or `index.js` takes its directory's name), or by `comm` when that is not an interpreter (a `#!` script's `comm` is its file name). When the two disagree, or neither names it (`python -c`, standard input), the app has no id and no call can name it. A call naming an interpreter as its app is refused with `invalid_args` before anything is asked, so "Always allow" can never be granted to one. Approvals, remembered answers and policy use it exactly as they use a macOS bundle id.

## Snapshots and refs

A snapshot keeps visible, on-screen nodes. Under `actionable_only`, the default, it keeps only the nodes you can act on, text nodes, and their ancestors, and it collapses inert wrappers that have a single child. `SnapshotBudget` caps the depth (12), the node count (400) and the text length (200). When a cap cuts the tree, or the platform stops early, the snapshot says `truncated: true`.

Refs have the form `@<snapshot>:eN`, for example `@s3:e12`. A ref is valid only while its snapshot is held, and only for the application the snapshot was taken of: `act`, `type_text` and a `RefState` wait name a `bundle_id`, and a ref whose snapshot was of another app, or of an app whose bundle id could not be read, fails with `stale_ref`. The driver keeps the most recent snapshots and evicts the oldest. The polls of `wait` take snapshots that are not stored, so a wait never evicts a held ref. A ref to an evicted snapshot, to a forgotten one, or to an element that no longer matches what the snapshot recorded fails with `stale_ref`. The caller then takes a new snapshot.

A window target names its application too (`WindowTarget::Window { bundle_id, id }`, `CaptureTarget::Window { bundle_id, id }`): a window id of another app fails with `window_not_found`. An unknown bundle id never matches.

## Hard limits

The driver enforces the hard limits of ADR-0047 decision 5 that only it can see, whoever calls it and in bypass mode too. Policy, per-app approvals and rate limits belong to the caller.

- **Locked or idle screen.** Every call except `permissions()` fails with `screen_unavailable` while the screen is locked, the screensaver is up, the main display sleeps, or this login session is not on the console (another user is switched in). On macOS the driver reads `CGSessionCopyCurrentDictionary` (`CGSSessionScreenIsLocked`, `kCGSSessionOnConsoleKey`), `CGDisplayIsAsleep(CGMainDisplayID())`, and whether the frontmost app is `ScreenSaverEngine`. `wait` checks again on every poll.
- **Secure input.** While macOS secure input is on (a password prompt anywhere), every act fails with `secure_field_refused`: `act` of any kind, `type_text`, `key`, `click_at` and `open_app`. Reads still run.
- **Secure fields.** A secure text field (`AXSecureTextField`) appears with `secure: true` and no value. Writing into one, with `type_text` or `act set_value`, fails with `secure_field_refused`. So does `type_text` with no ref or `key` while the focused element is secure.
- **No control of the app itself.** The host app's own windows are never read, acted on or captured. The library names no app: the host passes its own set to `default_driver(own)`, built with `OwnApps::for_app(bundle_id)` from the brand's identifier (ADR-0052; `ai.elitea.desktop` for ELITEA), plus its helper processes with `.with_extra(pids, bundle_ids)`. A process is the app's when its pid is the driver's own process or its bundle id is in that set. The app is left out of `list_apps` and `list_windows`. A snapshot, `act`, `key`, `click_at`, `open_app`, `wait` or window capture that targets it fails with `own_window_refused`, and so does a `click_at` whose point another window covers, and so do `type_text` with no ref, `key` and `click_at` while the app is the frontmost app.
- **Only the named app.** Input with no element target lands in the frontmost app. `type_text` with no ref, `key` and `click_at` go only into the app the call names, while it is frontmost; otherwise they fail with `not_frontmost`, also when the frontmost app's bundle id cannot be read.
- **Window-only capture.** A capture is always of one window alone, without its shadow (`screencapture -o -l`, the vendor's frame capture): no other window that overlaps it shows, and its pixels map 1:1 onto the window's frame times the display scale. A zoom (`CaptureTarget::WindowRegion`) is a crop of that capture; there is no screen-region capture.
- **Text length.** `type_text` and `act set_value` write at most 10,000 characters (`MAX_TYPED_CHARS`). Longer text fails with `invalid_args` before anything is sent.
- **Denied menu items.** `act` on a menu item titled Quit, Log Out, Shut Down, Restart, Sleep, Lock Screen, Force Quit or Switch User (case ignored, with or without the ellipsis and any trailing app or user name) fails with `menu_item_refused`, in any app's menus, the Apple menu's included: the menu path to the denied chords.
- **Denied chords.** They fail with `chord_refused` before any event is sent: quit, force quit, log out, lock screen, the power and eject chords, empty Trash, Spotlight and Siri. Adding a modifier to a denied chord does not get it through. Switch user has no entry: macOS has no default fast-user-switching chord, only the menu-bar and Control Centre item. A switched-out session fails every call with `screen_unavailable`. Windows and Linux have lists of their own (below).
- Every event the driver posts carries its marker in `kCGEventSourceUserData`. A physical event carries 0 there, so an event tap can classify each event with `is_synthetic_event`.

## Error codes

`DesktopError::code()` returns a stable code for each failure. The computer toolset maps it to the tool result. A code is never renamed or reused.

| Code | Meaning |
| --- | --- |
| `stale_ref` | The ref's snapshot is gone, or the element changed. Take a new snapshot |
| `secure_field_refused` | A write into a secure field, or any act while macOS secure input is on |
| `app_denied` | An application on the Windows or Linux platform deny list (terminals, password managers, system and security tools) |
| `chord_refused` | A denied key chord |
| `menu_item_refused` | A Quit, Log Out, Shut Down, Restart, Sleep, Lock Screen, Force Quit or Switch User menu item |
| `not_frontmost` | Input with no element target, and the named app is not the frontmost one |
| `own_window_refused` | The target is Elitea's own app or window, or Elitea is frontmost |
| `screen_unavailable` | The screen is locked, the screensaver is up, the display sleeps, or the session is not on the console |
| `app_not_found`, `window_not_found` | No such application or window |
| `permission_denied` | The Accessibility or Screen Recording grant is missing |
| `action_not_supported`, `action_failed` | The element cannot do the action, or it did not take effect |
| `timeout` | A wait or an OS read ran out of time |
| `invalid_args` | Bad arguments, such as text over 10,000 characters |
| `platform_not_supported` | The `Unsupported` driver of an OS other than macOS, Windows and Linux |
| `user_active_guard_unavailable` | The user-active guard's input watch stopped on its own (the display went away, a Windows hook could not be re-armed): every act is refused until a new watch runs. The host returns the same code when the watch cannot start |
| `internal` | Anything else |

## The macOS driver

The macOS driver wraps vendored copies of the `core` and `macos` crates of [agent-desktop](https://github.com/vercel-labs/agent-desktop) (Apache-2.0). They live in `libs/rust/vendor/agent-desktop/` with three recorded patches. `libs/rust/vendor/README.md` lists what was copied and every change. Capture runs `/usr/sbin/screencapture` through the vendor's own code. `screencapturekit-rs` was not used, because its build script runs `swift build`.

Actions are semantic first, through the accessibility API, with no pointer move and no change of focus. `ActionOutcome.delivery` says whether an action was delivered semantically or needed physical input.

## The Windows and Linux drivers

Both wrap vendored copies of agent-desktop's `windows` (UI Automation) and `linux` (AT-SPI) crates, at the same commit as macOS, behind one engine (`src/engine.rs`). Each crate, and the crates it needs (`uiautomation`, `windows` and `willhook` on Windows; `x11rb` and `zbus` on Linux), is compiled only on its own OS. Their `unsafe` stays in the vendored crates; `elitea-desktop-control` has none. `.github/workflows/ci-desktop-control.yml` runs check, clippy and the tests on windows-latest and ubuntu-latest.

The pure rules live in `src/platform.rs`, and their tests run on every OS:

- **Denied chords.** Windows: Alt+F4, Ctrl+Alt+Delete and Ctrl+Alt+End, Ctrl+Shift+Esc, Win+L, Win+X, Win+R, Win+S, Win+I, Win+E, Win+D, the Windows key alone, Alt+Tab and Win+Tab, and the power and sleep keys. Linux: Alt+F4, Ctrl+Alt+Delete, End, Backspace, Escape, L and T, Ctrl+Alt+F1 to F12 (virtual terminals), Super+L, Alt+F2, Alt+Space, the Super key alone, Super+A, Super+D, Super+Space, Alt+Tab and Super+Tab, and the power, sleep and suspend keys. The vendor's own blocked combos are refused too. As on macOS, an added modifier does not get a denied chord through.
- **Denied menu items.** The macOS list also covers Exit, Sign out, Log off, Shut down, Power off, Suspend, Hibernate and Reboot, with Windows mnemonics (`E&xit`) ignored.
- **Denied apps.** Opening, snapshotting or acting on a denied application fails with `app_denied`: Elitea itself, password managers, terminals and shells (`cmd.exe`, `powershell.exe`, `wt.exe`, GNOME Terminal, Konsole and others), the registry and management consoles (`regedit.exe`, `mmc.exe`), the Control Panel hosts (`rundll32.exe`, `control.exe`), Task Manager, the sign-in, UAC and lock-screen processes (`consent.exe`, `credentialuibroker.exe`), Windows Settings and Windows Security (`systemsettings.exe`, `sechealthui.exe`), the Linux settings apps whole (`org.gnome.Settings`, `gnome-control-center`, `org.kde.systemsettings`, `systemsettings`: their privacy and account pages are not apps of their own), polkit and pinentry prompts, screensavers and greeters. `open_app` takes only a plain application id (no path, no `..`; on Windows a `.exe` image).
- **Windows windows the owner does not name** (`windows_window_verdict`, vendor patch `elitea_ext::window_facts`). A packaged app's window (Settings, Windows Security, Calculator) is owned by `applicationframehost.exe` whatever it hosts, so it is judged by the hosted app's image (the frame's `Windows.UI.Core.CoreWindow` child) and refused when that cannot be read, as with a suspended app. `explorer.exe` owns the Run box, the Control Panel, Credential Manager and User Accounts as well as File Explorer: only a `CabinetWClass` folder window whose shell location is a `file:` path passes; every other Explorer window is refused (`app_denied`). The rule runs on every window the driver resolves, lists, finds frontmost or holds a ref into.
- **File Explorer is never typed into** (`text_entry_refusal`). Its address bar runs what is typed into it: `powershell -c ...` and Return starts a shell. The address band cannot be told reliably from the folder view (the focus moves into it on a keystroke), so in every `explorer.exe` window `type_text` (with or without a ref), `set_value` and a key chord that inserts text (`chord_inserts_text`: a character, Space, paste, Win+. / Win+; / Win+V) are refused with `app_denied`. Clicks, navigation keys (arrows, Return, Backspace, F5, Ctrl+C) and reads still pass.
- **Text-inserting chords need a known focus.** The focused element is searched 30 levels below the frontmost window. When none is found, a chord that may insert text (a character, Space, Ctrl+V or Cmd+V, Shift+Insert, AltGr, Win+. and Win+; (the emoji and symbol panel) and Win+V (the clipboard history), any key name the rule does not know) fails with `action_failed` (it could land in a deeper password field); navigation, editing and function keys and other Ctrl shortcuts pass (`chord_inserts_text`).
- **Secure fields.** An element is secure when the vendor marks it `secure` (UI Automation `IsPassword`, AT-SPI `PASSWORD_TEXT`). There is no OS-wide secure-input state as on macOS, so `secure_input()` is always false there; the focused element is read before `type_text` with no ref and before `key`.

The screen gate (`screen_unavailable`):

- **Windows** (vendor patch `windows/src/elitea_ext.rs`): this process's session is not the connected console session, the input desktop is not `Default` (the lock or sign-in screen, or a UAC or credential prompt's secure desktop), or the screensaver runs.
- **Linux** (`linux_screen_status`): no display, the logind session (the one `XDG_SESSION_ID` names, else the user's display session, else the pid's) is not active or has `LockedHint` set, a screensaver service (`org.freedesktop.ScreenSaver`, GNOME's, Cinnamon's or MATE's) says it is active, or the X server's own MIT-SCREEN-SAVER is on. It fails closed: only a screensaver service that answers can show the screen is unlocked. Without one (i3lock, slock and xsecurelock run no D-Bus service and set no `LockedHint`) the lock state is unknown and every call fails with `screen_unavailable`. There is no override.

The user-active guard:

- **Windows**: low-level keyboard and mouse hooks through `willhook` (listen only). Windows flags every injected event, and an injected event is read as the driver's own. So another program's injected input does not pause the agent either.
- **Linux on X11**: XInput2 raw events on the root window (listen only). An event from the server's XTEST devices is read as the driver's own, so another program's XTEST input (`xdotool`, a remote-control tool) does not pause the agent either; the active window's `_NET_WM_PID` tells input aimed at Elitea.
- **Linux on Wayland or XWayland: fails closed** (`linux_guard_unavailable`). Wayland gives no application a global view of the keyboard and pointer, and an X11 watch through XWayland sees only X clients. A session is taken as Wayland on any one sign: `WAYLAND_DISPLAY` or `XDG_SESSION_TYPE`; logind's `Session.Type` of any session the process could be in (the one `XDG_SESSION_ID` names, the user's display session, `/org/freedesktop/login1/user/self` `Display`, and the pid's own session, which an app started in a systemd `app-*.scope` does not have); or an X server that is Xwayland, by its `XWAYLAND` extension (Xwayland 23.1 and later) or its RandR output names (`XWAYLAND0`, `XWAYLAND1`, ... on every Xwayland). So a stripped environment does not get past it. The X vendor string is not read: Xwayland's is "The X.Org Foundation", the same as Xorg's. With no sign at all the session is taken as X11, so a plain Xorg started without logind or `XDG_SESSION_TYPE` still acts; the residual gap is an X server that hides both Xwayland tells, which no shipped Xwayland does. The watch cannot start, and every act is refused with `user_active_guard_unavailable` (`user_active_unavailable: a Wayland session ... (why)`). Reads still work, and the settings page shows computer use as read-only with the reason (`read_only_reason`). Sign in to an X11 session to let the agent act.
- **A watch that dies** (its thread ended: an X error, a Windows hook that cannot be re-armed) clears `InputWatch::alive()`. The driver then refuses every act with `user_active_guard_unavailable`, and the host treats the session's watch as refused, starting a new one next session.
- **Windows cannot detect a silently removed hook.** Windows removes a low-level hook without notice when its callback overruns `LowLevelHooksTimeout`, and the hook then delivers nothing. `willhook`'s event channel is a process-wide static that never disconnects and exposes no hook handle, so without `unsafe` code no call tells a removed hook from a person who is not typing. The watch bounds the exposure instead: every 30 seconds (`REARM_PERIOD`) it drops its hooks and installs new ones, and a re-arm that fails ends the watch (dead, as above). So a silently removed hook leaves the person's input unseen for at most 30 seconds, plus the few milliseconds of each re-arm.

The stop shortcut is Control+Alt+Escape on both (Option is Alt). The settings page's System Settings buttons are macOS's own; on Windows and Linux there is no grant to open.

## Run the live test

The unit tests run everywhere. The live test drives TextEdit and needs a logged-in macOS session. Windows and Linux have no live test yet: CI proves they build and that their pure rules and input readings hold.

<Steps>
<Step title="Grant access">
In System Settings > Privacy & Security, add the terminal that runs `cargo` to **Accessibility**. Add it to **Screen Recording** too, for the capture check. Then restart the terminal, because TCC reads the grant at launch.
</Step>
<Step title="Run it">
From `libs/rust`:

```bash
cargo test -p elitea-desktop-control --test macos_live -- --ignored --nocapture --test-threads=1
```

Keep your hands off the keyboard and the mouse while it runs. It opens an untitled TextEdit document and types into it. Close that document afterwards without saving.
</Step>
</Steps>
