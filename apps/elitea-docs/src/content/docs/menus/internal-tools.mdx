title: "Internal tools"
description: "Built-in chat and agent capabilities — image creation, data analysis, the code sandbox, attachments, planner, swarm mode, and smart tools selection."
---

Internal tools are capabilities you turn on from **Modules** in chat or an agent's Tools section, without configuring an external toolkit. They come from a fixed platform catalogue (`features/agents/lib/internalTools.ts`) and are turned on per conversation or saved as an agent's default.

<Note title="Which worker runs which module">
**Planner**, **Attachments**, **Data analysis**, **Smart tools selection**, **Python sandbox** and **Image creation** run on the platform's agent worker (Image creation needs an image model, and Python sandbox needs the deployment's code sandbox, see below). **Elitea MCP tools** and **Swarm mode** are not run by the platform's worker: they show disabled with a "Not available on the Rust worker" note (agent Tools section) so you can see the gap before turning one on, and a run that still hits one gets a visible in-conversation notice rather than the capability silently doing nothing (tracked in #866).
</Note>

## Turn a module on

<Tabs>
  <Tab title="In chat">
    Select **+** in the chat toolbar → **Modules**, then toggle the tool on. The setting lasts for the conversation.
  </Tab>
  <Tab title="On an agent">
    Open the agent, find **Modules** under **Tools** (select **Show all** if it is collapsed), toggle the tool, and **Save**. New conversations with that agent turn it on by default.
  </Tab>
</Tabs>

## Image creation

Lets the assistant generate images from a text prompt and shows them inline in the chat. Ask for an image in plain words, for example "draw a red fox in watercolor, 1536x1024". The images are saved automatically to the conversation's `attachments` bucket, where you can also download or delete them later from [Artifacts](/menus/artifacts).

The assistant can set these parameters:

| Parameter | Values |
| --- | --- |
| `prompt` | The text that describes the image (required). |
| `size` | Depends on the model. `gpt-image-*`: `1024x1024`, `1536x1024`, `1024x1536` or `auto`. `dall-e-3`: `1024x1024`, `1792x1024` or `1024x1792`. `dall-e-2`: `256x256`, `512x512` or `1024x1024`. Other models: `auto`. |
| `n` | How many images. 1 to 4 (`dall-e-3`: 1 only). The default is 1. |
| `quality` | `gpt-image-*`: `low`, `medium`, `high` or `auto`. `dall-e-3`: `standard` or `hd`. `dall-e-2`: none. A value the model does not take is refused before any image is billed. |

<Warning title="Each image is billed">
Image generation is billed per image by the LLM gateway, to the project, like every other model call. A budget limit refuses the call, and the assistant tells you so.
</Warning>

**Enabling it.** The toggle is on when the deployment has an image model. An administrator sets `global.imageGenerationModel` in the Helm values to the registry name of an image model the gateway serves. When it is empty, the toggle shows disabled with the note "No image model is configured for this deployment". The model is chosen for the whole deployment, and it must be a global shared model: a model that only one project owns is not available in other projects, and the assistant says so. Choosing it per project is not supported yet.

<Note title="Desktop">
The cloud agent worker runs this tool. The desktop app's local agent loop does not offer it yet.
</Note>

<Tip>
This toggle is a chat-conversation setting. To let an agent or pipeline generate or edit images as a step in its own logic — not just inline in chat — attach the [ImageGen toolkit](/integrations/toolkits/imagegen_toolkit) instead.
</Tip>

## Data analysis

Runs pandas-style analysis over a file you upload to the conversation — summaries, filtering, aggregation, and chart generation — driven entirely by natural-language requests. Upload the file first, then ask for the analysis; generated charts and exported files are saved back to the conversation.

<Tip>
For datasets larger than about 100 MB, or analysis needing custom code, use a Python-based toolkit or a pipeline Code node instead.
</Tip>

## Python sandbox (code execution)

Lets the agent write a short program and run it in the platform's isolated code sandbox, with the `run_code` tool. The switch keeps the name **Python sandbox**, but the tool runs every language the deployment's sandbox serves: Python, JavaScript, TypeScript and Rust. The tool's `language` argument offers exactly those languages, so an agent never asks for one the sandbox cannot run.

This is the same sandbox that runs a pipeline **Code** node and the code of Data analysis, with the same limits on time, memory and output, the same lack of network and files, and the same package preparation. It is not a second sandbox.

- **Python** returns what the program printed (`stdout`), what it wrote to `stderr`, the value of its last expression (`result`) and the traceback if it raised. Standard-library modules and the packages the sandbox provides can be imported.
- **JavaScript and TypeScript** are a module whose default export (or the result of a default-exported function of the state) is the result. What the program prints with `console.log` comes back as `output`.
- **Rust** defines `pub fn run(state: serde_json::Value) -> Result<serde_json::Value, Box<dyn std::error::Error>>`, and its value is the result. What it prints comes back as `output`.
- The agent can pass a JSON object in `input`. The program reads it as `elitea_state['data']` (`elitea_state.data` in JavaScript and TypeScript, `state["data"]` in Rust). Python returns `stdout` and `stderr` separately; the sandbox merges the printed output of JavaScript, TypeScript and Rust into one `output`.
- Each of `stdout`, `stderr`, `output` and the traceback is cut at 20,000 characters and a result at 40,000 bytes, and the answer carries a note when it was cut. What a program prints is data for the model to read, not an instruction.

**Enabling it.** The toggle is on when the deployment's code sandbox serves at least one language. An administrator configures the sandbox with `worker.runtime.sandboxRuntimes` in the Helm values (see [Configuration](/deployment/configuration#code-sandbox)). Without one, the toggle shows disabled with the note "No code sandbox is configured for this deployment". An agent that already has the module saved still runs: it just has no `run_code` tool, and the conversation says the module is not available.

<Note title="Approval">
`run_code` is a `code_execution` tool, so the deployment's approval rules for code execution apply to it, as they do to `execute_sql`. The data analysis tool `run_analysis_code` runs code in the same sandbox and is `code_execution` as well.
</Note>

<Note title="Desktop">
The desktop app's local agent has no platform sandbox, so the module is not offered there.
</Note>

## Attachments

Lets the agent list, read and search the files attached to the conversation — including ones attached in earlier messages — with `list_attachments`, `read_attachment` and `search_attachment`. A file small enough to fit is already shown to the model with your message; the tools reach the rest of a long document and the files from earlier turns. Each file is read from storage the first time the agent asks for it. Turn it on from the agent's **Tools** section (it is not in the chat toolbar).

## Planner

Lets an agent write a plan for a multi-step task and tick it off as it works: a title and numbered steps that move from pending to in progress to completed (`update_plan`, `start_step`, `complete_step`, `get_plan_status`, `delete_plan`). The plan belongs to the conversation: it is kept between messages and survives long conversations being summarised, and deleting the conversation removes it. The agent is also given short planning guidance in its instructions while the module is on.

## Swarm mode

Turns a set of agents into peers that can hand off control to one another mid-conversation, all sharing the same conversation history. The agent the user addresses is simply the default entry point; any peer can transfer to any other with a `transfer_to_<agent_name>` tool, and each hand-off's task argument must be fully self-contained — the receiving agent gets no other context. Swarm-enabled agents cannot themselves be added as a child of another swarm agent.

## Smart tools selection

Reduces token usage when an agent has many toolkits configured by binding only two meta-tools (`get_tool_schema`, `invoke_tool`) instead of every individual tool definition, loading real tool schemas on demand, and adding a compact index of the available toolkits and tools to the agent's instructions. Turn it on once a conversation or agent uses five or more toolkits — the more toolkits, the larger the savings. With fewer than 20 tools the module switches itself off for that message, since the meta-tools would cost more than they save.

<Note>
A tool that needs your confirmation (a sensitive action) or a sign-in to the service stays directly available to the agent instead of going through `invoke_tool`, so approvals keep working exactly as without the module. The Planner, Attachments and this module apply to the agent you chat with; agents it calls as tools, and pipeline steps, do not get them.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="A module toggle has no effect">Check the worker note under [Internal tools](/menus/internal-tools): Elitea MCP tools and Swarm mode are not run by the platform's worker — the conversation shows a visible notice rather than running them.</Accordion>
  <Accordion title="Image creation is disabled">No image model is configured for this deployment. Ask an administrator to set `global.imageGenerationModel` (see above).</Accordion>
  <Accordion title="Modules are missing from the chat toolbar entirely">No module is available for the project at all — ask your administrator to configure at least one provider or toolkit.</Accordion>
</AccordionGroup>
