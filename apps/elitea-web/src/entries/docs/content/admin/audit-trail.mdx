Audit Trail is a read-only view over what happened on the deployment — there is nothing to edit or configure here. Use it to answer "who did this, and when," whether you are investigating an incident, confirming a change actually landed, or checking whether a scheduled job ran.

## Review activity

<Steps>
  <Step title="Choose User or System events">
    User events are actions a person took; System events are platform-generated (for example a scheduled job firing). Each has its own tab.
  </Step>
  <Step title="Filter">
    Narrow by date range (with quick presets like 30 minutes, today, yesterday, 7 days, or 30 days, plus an explicit From/To), event type, project, user, or errors-only.
  </Step>
  <Step title="Use the heatmap">
    A calendar-style heatmap shows activity density over time, so a spike is visible before you drill into individual events.
  </Step>
</Steps>

## Traces and spans

A second view mode, alongside events, shows execution traces and their individual spans — each row names the action and, when there is one, the tool or model that ran it. Spans can be filtered by duration band (under 10 ms, up to over 10 seconds), which is the fastest way to find what is running slowly across the deployment rather than one conversation at a time.

## Investigate one person

From the Users page's row menu, the activity drawer filters this same audit data to one account — useful when investigating a specific person's actions rather than browsing the whole trail. See [Users and roles](/admin/users-and-roles).

## Export to your SIEM

Audit Trail is the place to look; it is not where evidence should be kept. The hash chain on security audit events makes tampering detectable, but immutability and long retention belong to your SIEM or WORM store. Elitea sends two streams there, in one versioned envelope, [`elitea.audit.v1`](/reference/audit-event-schema):

- **Security audit events** from the governed security audit outbox (credential decisions, grant, binding, mandate and delegation changes). These exist when enterprise credential governance is on. Each carries its position in the tamper-evident chain.
- **The audit trail on this page** (`centry.audit_events`): one event per completed request, scheduled job or admin task.

Two transports are built in, and you can use either or both:

| Transport | Use it when | Set |
|---|---|---|
| **OTLP logs** | Your collector or SIEM speaks OpenTelemetry | `ELITEA_AUDIT_EXPORT_OTLP_ENDPOINT` |
| **Signed webhook** | You run your own receiver, or a SIEM with an HTTP intake | `ELITEA_AUDIT_EXPORT_WEBHOOK_URL` and `ELITEA_AUDIT_EXPORT_WEBHOOK_KEYS_FILE` |

With neither set, export is off, no relay starts and nothing dials out. The full list of settings is in [Post-install configuration](/deployment/configuration#export-audit-evidence-to-a-siem), and the field-by-field schema, a sample event, signature verification and a collector configuration are in the [audit event schema reference](/reference/audit-event-schema).

### What the export guarantees

- **At least once.** A row is marked exported, or the audit trail cursor advances, only after the receiver accepted the batch. If your receiver is down, nothing is lost: events wait and are sent in order when it returns. Deduplicate on `event_id`.
- **Asynchronous.** Export runs in background relays. It never slows or fails the request or run that produced the event.
- **Outages do not drop evidence.** A batch is dead-lettered only when the receiver permanently refuses it as malformed (HTTP 400, 413 or 422) five times in a row. A receiver that is down, rate limiting, or rejecting your credentials (401, 403, 404, 429, 5xx) is never dead-lettered; the lag alert fires instead. A dead-lettered event is still in its source table and is also listed in `elitea_runtime.audit_export_dead_letters`.
- **Egress is guarded.** A webhook receiver on a private or loopback address is refused unless `ELITEA_AUDIT_EXPORT_EGRESS_ALLOWLIST` names it. Redirects are never followed.

### What it does not do

- It does not make the stored events immutable, and it does not retain them for you. Keeping them is your SIEM's job; the shared-responsibility split is in the enterprise controls section.
- Existing audit trail history is not replayed by default. Export starts at the newest row when you turn it on. Set `ELITEA_AUDIT_EXPORT_AUDIT_EVENTS_FROM` to `beginning` before the first start to send the whole table.
- Audit trail rows are not chained yet, so the `chain` object is present only on security audit events.

### Watch it

elitea-main serves Prometheus metrics for the export on port 9464 (`ELITEA_AUDIT_EXPORT_METRICS_ADDR`): `elitea_audit_export_lag_seconds`, `elitea_audit_export_backlog`, and the `delivered`, `failed` and `dead_lettered` counters. The chart ships a PodMonitor and three alerts, `EliteaAuditExportLag`, `EliteaAuditExportBacklog` and `EliteaAuditExportDeadLettered`, wherever the Prometheus Operator API is served.
