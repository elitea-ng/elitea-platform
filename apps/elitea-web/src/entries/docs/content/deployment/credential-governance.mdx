Enterprise credential governance is an operator switch for deployments that must prove which agent used which credential, on whose authority. With it on, every new run is pinned to a governed profile and an immutable policy revision. Later releases enforce that pin at each credential use. The design is ADR-0039 in the architecture records.

<Warning>
This release **records** the governed profile; it does not enforce it yet. No credential path reads the pin until the credential broker lands, so a governed run uses toolkit credentials exactly as a legacy run does. Turn the flag on now only to stage policy revisions, bindings and mandates.
</Warning>

## Off by default

`main.env.ELITEA_ENTERPRISE_CREDENTIAL_GOVERNANCE_ENABLED` is `"false"` by default. With it off:

- Admissions, routes and wire bytes are unchanged. The governed admin routes return 404.
- No new dependency is built or dialled: no Vault/OpenBao client, no audit relay.
- The new tables (migrations 0180–0187) are created on upgrade and stay empty.

The value must be exactly `"true"` or `"false"`. Anything else, such as `"1"` or `"TRUE"`, refuses boot rather than picking a profile.

## Turn it on

1. **Write a policy document.** It holds parameters only, never a secret:

   ```json
   {
     "schema": "elitea.credential-policy.v1",
     "allowed_identity_modes": ["dedicated_agent"],
     "vault_required_credential_classes": [],
     "max_mandate_ttl_seconds": 86400,
     "audit_backlog_alert_threshold": 1000
   }
   ```

   `allowed_identity_modes` takes `dedicated_agent`, `runtime_domain_binding` and `elitea_native`. A revision that allows none is refused, because then no agent could ever use a governed credential. Unknown fields are refused too.

2. **Store it as a revision.** Revisions are immutable: a change is a new id.

   ```bash
   elitea-main credential-policy put --id 2026-10-r1 --file policy.json --operator "$USER"
   elitea-main credential-policy show --id 2026-10-r1
   ```

   `put` runs the same checks boot runs (see below), so a revision that could not boot is refused when you publish it.

3. **Point the deployment at it** and set the flag:

   ```yaml
   main:
     env:
       ELITEA_ENTERPRISE_CREDENTIAL_GOVERNANCE_ENABLED: "true"
       ELITEA_CREDENTIAL_GOVERNANCE_POLICY_REVISION: "2026-10-r1"
   ```

Boot refuses to start when the revision is missing, its stored bytes no longer match its digest, it allows no identity mode, the security audit outbox is missing, or it lists a `vault_required_credential_classes` entry while no Vault/OpenBao store is configured.

## What a run records

Every new run is pinned to `elitea.credential-profile.governed.v1` and the active revision, in the same transaction that admits it. A pin never changes. A resumed run (a human-in-the-loop answer, a continued agent turn) keeps the pin it started under, even if the flag or the revision changed since. A run with no pin is legacy.

The same transaction stores the run's **execution security context**: the policy revision and digest, the tenant project, the subject and actor chain, the calling application, and the agent version's active identity binding. It holds references, epochs and digests only, never a credential. It is immutable. Every worker command of the run carries the context's digest inside the signed command, so a worker can prove it holds the context Main admitted.

A binding is recorded only when exactly one binding of the agent version is active. With none, or more than one, the context names no binding, and every governed credential use of the run is denied.

## Governed workers

A governed run's commands go out on their own NATS subjects, `elitea.rt.v1.<route>.g.*`, and only the governed durables `elitea-configuration-worker-governed-v1`, `elitea-agent-worker-governed-v1` and `elitea-index-worker-governed-v1` read them. The NATS bootstrap Job creates them beside the legacy durables. A worker that does not verify the context never binds them, so a governed command never reaches it.

Set `ELITEA_WORKER_GOVERNED_CONTEXT: "true"` on the Rust worker to bind the governed durables. Such a worker fetches each run's context under its claim, checks the digest, and refuses a context it cannot decode exactly.

Main also checks every claim:

| Refusal | When |
| --- | --- |
| `GOVERNED_WORKER_REQUIRED` | A governed command is claimed by a worker that did not declare it verifies the context |
| `GOVERNED_CONTEXT_MISSING` | A command without a context is claimed for a run pinned governed |

Neither is retried. With the flag on, Main refuses to boot when a command stream lacks its governed subject or durable, so re-run the NATS bootstrap Job before turning the flag on.

<Warning>
Turn the flag on only when at least one governed worker runs. Governed commands wait in their stream for a governed worker, and a run whose deadline passes first fails.
</Warning>

## Agent identity bindings and mandates

With the flag on, two admin API groups are mounted:

| Route | Purpose |
| --- | --- |
| `/api/v2/admin/agent_identities` | List and propose bindings of an agent version to an identity |
| `/api/v2/admin/agent_identities/{id}:approve`, `:suspend`, `:revoke` | Binding lifecycle |
| `/api/v2/admin/mandates` | List and issue mandates (who authorised an unattended run, for which agent and operations, until when) |
| `/api/v2/admin/mandates/{id}:approve`, `:suspend`, `:revoke` | Mandate lifecycle |

Four permissions gate them, held by `super_admin` and `admin` only:

- `models.agent_identity.bindings.manage` (list, propose, suspend, revoke) and `models.agent_identity.bindings.approve` (list, approve)
- `models.agent_identity.mandates.manage` (list, issue, suspend, revoke) and `models.agent_identity.mandates.approve` (list, approve)

Approval is a two-person step: the approver can never be the proposer. A mandate cannot outlive the revision's `max_mandate_ttl_seconds`, and suspending or revoking a binding also stops its mandates. Every change writes a security audit event.

### External agent identities

A binding in `dedicated_agent` mode names an identity the agent holds at an external provider, such as an Entra agent identity. Those identities have their own admin routes:

| Route | Purpose |
| --- | --- |
| `/api/v2/admin/external_agent_identities` | List and create external identities |
| `/api/v2/admin/external_agent_identities/{id}:provision`, `:activate`, `:suspend`, `:resume`, `:retire` | Identity lifecycle |

`models.agent_identity.external.manage` gates every route; it is held by `super_admin` and `admin`. Activation also needs `models.agent_identity.bindings.approve`, and needs an approved binding: provisioning never activates an identity. All versions of an agent share one identity. A fork gets a new one. While its external identity is not active, a binding is treated as suspended. Retiring takes two steps: the identity is `retiring` until the provider confirms, then `retired`.

## Credential use grants

A grant lets one agent binding use one credential, through one toolkit, against one target. Grants live per project:

| Route | Permission |
| --- | --- |
| `GET /api/v2/projects/{project_id}/credential_grants` | `models.credentials.governed.manage` or `.approve` |
| `POST /api/v2/projects/{project_id}/credential_grants` (propose) | `models.credentials.governed.manage` |
| `POST …/credential_grants/{id}:approve` | `models.credentials.governed.approve` |
| `POST …/credential_grants/{id}:suspend`, `:revoke` | `models.credentials.governed.manage` |

The five `models.credentials.governed.*` permissions (`use`, `reveal`, `manage`, `probe`, `approve`) are granted to **no role** by default. Grant them to a role in **Settings → Roles**. Approval is two-person, as for bindings, and the database enforces it. A `use` grant never permits reveal, manage or probe, and a grant for one target never permits another.

Each credential use will be decided by eight gates that must all permit: authentication source, RBAC, entity access, binding, toolkit, grant, operation and delegation or mandate. Any gate's error is a deny. Nothing calls the decision in this release; the credential broker will.

## Entra delegation

With the flag on, an OIDC identity provider marked as Entra keeps the signed-in user's delegated middle-tier token, encrypted, so a governed run can act on the user's behalf through on-behalf-of exchange. Set it on the provider's stored settings:

| Setting | Value |
| --- | --- |
| `entra` | `true` |
| `entra_tenants` | The tenant ids (lower-case GUIDs) allowed to sign in. Required. |
| `entra_api_scope` | The middle-tier scope requested at sign-in. Default `api://<client_id>/.default`. |
| `entra_federated_token_file` | Path of a projected workload identity token for on-behalf-of exchange. Without it, classic OBO is off; client secrets are refused. |
| `entra_agent_blueprint_id` | The agent identity blueprint application id, for Agent ID OBO |

Sign-in then accepts only those tenants' v2 issuers and requires the `tid` and `oid` claims. Accounts still link by `sub`, so turning this on does not orphan existing users. Signing out revokes what that session created, in one transaction that wipes the stored ciphertext. A change to these settings takes effect at the next restart. The admin UI does not show these fields yet: set them through the identity provider API, and note that saving the provider from the UI may drop them.

When Entra asks for interaction or a claims challenge, a run can pause with **credential authorization required** and resume as the same run once the user consents again. The worker reports that pause once the credential broker lands.

## Vault / OpenBao secret store

Governed credentials live in the built-in encrypted PostgreSQL vault unless the revision lists their class under `vault_required_credential_classes`. Those classes need an external HashiCorp Vault or OpenBao KV v2 store, configured only by these variables (read only with the flag on):

| Variable | Value |
| --- | --- |
| `ELITEA_SECRETSTORE_VAULT_ADDR` | `https://host[:port]`. Plain `http` is refused. |
| `ELITEA_SECRETSTORE_VAULT_CA_FILE` | CA bundle that signs the server certificate |
| `ELITEA_SECRETSTORE_VAULT_AUTH_METHOD` | `jwt` or `kubernetes` |
| `ELITEA_SECRETSTORE_VAULT_AUTH_MOUNT` | The auth method's mount path |
| `ELITEA_SECRETSTORE_VAULT_ROLE_PREFIX` | Roles are `<prefix>-<workload scope>`, one per scope |
| `ELITEA_SECRETSTORE_VAULT_KV_MOUNT` | The KV v2 mount. It must have `cas_required` on. |
| `ELITEA_SECRETSTORE_VAULT_TOKEN_FILE` | The projected workload token, re-read at every login |
| `ELITEA_SECRETSTORE_VAULT_NAMESPACE` | Vault Enterprise namespace. Leave empty for OpenBao and Vault CE. |
| `ELITEA_SECRETSTORE_VAULT_READINESS_SCOPE` | The workload scope the boot check logs in as |

All empty means "not configured". Setting any one of them makes all of them required: a half configuration refuses boot. There are no defaults for anything that selects authority.

## Security audit chain

Governed events (revisions, bindings, mandates, and later every credential decision) are written to a per-tenant hash chain in the same transaction as the change, then relayed to durable storage. A relay or exporter failure leaves rows pending; none is dropped. A backlog above the revision's `audit_backlog_alert_threshold` raises an alert.

Check a chain at any time:

```bash
elitea-main security-audit verify --tenant 42             # one tenant project
elitea-main security-audit verify --tenant 0 --source outbox   # the platform partition, not yet relayed rows
```

The scheduler can delete relayed outbox rows older than a window. `SECURITY_AUDIT_OUTBOX_RETENTION_DAYS` is `"0"` by default, which deletes nothing. `SECURITY_AUDIT_OUTBOX_RETENTION_INTERVAL` (default `1h`), `..._BATCH_SIZE` and `..._MAX_BATCHES` bound each sweep.

## Turning it off

Turning the flag off stops new governed admissions. Runs already pinned stay governed, and their commands still need a governed worker. Once enforcement ships, such a run fails closed at its next credential use instead of falling back to legacy behaviour. To drain without failures, wait until no governed run is active before turning the flag off. Rollback to an earlier release needs no data migration: the new tables are additive and unread there.
