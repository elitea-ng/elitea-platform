This walks a Kubernetes install of the `elitea` chart end to end. It is one chart for everything: the platform, NATS JetStream with its stream bootstrap, the vector store and, where a cluster needs it, the sandbox-runtime installer. Read [Production deployment overview](/deployment/overview) first for the topology and what the chart does not provision. For a first install on an empty cluster, [Deploy from scratch](/deployment/from-scratch) has every Secret, certificate authority, database step and edge rule in one place, with a complete values file.

## Prerequisites

<CardGroup cols={2}>
  <Card title="Cluster access" icon="server">A Kubernetes cluster with `kubectl` and `helm` configured against it. Helm 4.3 or newer is recommended; Helm 3.8 or newer also renders the chart, which is what Argo CD uses. With Helm 4, `--atomic` is `--rollback-on-failure`.</Card>
  <Card title="PostgreSQL" icon="database">Reachable, with an administrator DSN available for the database-preparation Job (`CREATE DATABASE`). No extension is needed: vectors are kept in Qdrant through elitea-vector (`vector.enabled`), not in PostgreSQL.</Card>
  <Card title="NATS JetStream" icon="server">Bundled: the chart runs it (`nats.enabled`, on by default) and creates its streams with a hook Job (`natsBootstrap`). The platform needs no Redis: the runtime command bus, live updates and presence are on NATS, and the chart refuses values that still set `runtimeRedis`.</Card>
  <Card title="Object storage" icon="package">An S3-compatible bucket, created ahead of the first sync and named by `main.env.STORAGE_CONTAINER`.</Card>
  <Card title="cert-manager" icon="shield-check">Required. The bundled NATS CA, the NATS client identities and the LLM gateway's mTLS hop (on by default) are all cert-manager `Certificate`s. The gateway's issuer (`llmGateway.mtls.issuerRef`, default `ClusterIssuer elitea-internal-ca`) is yours to create.</Card>
</CardGroup>

## Secrets to create beforehand

Nothing secret goes in a values file — a Helm parameter renders into a ConfigMap, readable by anyone with `get` on the namespace. Create these Kubernetes Secrets first; the chart only ever takes their **names**.

<Accordion title="SECRETS_MASTER_KEY">
Wraps each project's vault key. Required by both elitea-main and the gateway, and it must be the same key: elitea-main reads the gateway's reference (`llmGateway.secrets.SECRETS_MASTER_KEY`, default Secret `elitea-llm-gateway-secrets`, key `secrets-master-key`) unless you override both. Generate: `python3 -c 'import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())'`
</Accordion>

<Accordion title="postgresql.existingSecret">
The database DSN, one Secret + key pair that every component reading the database (elitea-main, its migration Job, the scheduler, the LLM gateway, the workload-session Job) derives its `DATABASE_URL` from. Default names: Secret `elitea-main-db`, key `database-url`.
</Accordion>

<Accordion title="runtime.material.secretName (runtime plane only)">
Agent-execution signing keys and listener certificates (from `deploy/scripts/gen-runtime-certs.sh`). Required if `main.runtime.enabled: true`.
</Accordion>

<Accordion title="fileConfig.authConfig.material.secretName (production auth)">
Three files: the browser-attempt key, the PAT signing key and the Form users JSON. Required if using Form or mixed authentication. The auth document is `elitea.auth.form.v2`: it has no `redis` block, because the Form sign-in state is in PostgreSQL, and the attempt key is `credentials.attempt_key_file`. The Form users JSON is a sign-in path only when `main.env.ELITEA_FORM_LOGIN_ENABLED` is `"true"`; Form sign-in is off by default.
</Accordion>

<Accordion title="Gateway identity secret (GATEWAY_IDENTITY_SECRET)">
Required on both main and gateway; must be identical. HMAC key for signing/verifying identity headers.
</Accordion>

## Two settings with no chart default

The chart **refuses to render** while either of these is empty — there is no safe guess for either, and a guessed value would look armed while guarding nothing:

| Setting | What it is |
|---|---|
| `llmGateway.env.GATEWAY_SELF_LLM_ORIGINS` | Every origin that reaches this deployment's `/llm` surface, public and in-cluster, comma-separated — e.g. `https://elitea.example.com/llm/v1,http://elitea-main:8080/llm/v1`. |
| `llmGateway.egressPosture` | `"allowlist"` (only hosts in `GATEWAY_EGRESS_ALLOWLIST` / governance rows) or `"public-unrestricted"` (any public host, until the first governance row narrows it). Private-network reachability follows only from an entry that explicitly names a private address or block — never from the posture alone. |

Also required: `platform.aiProjectId`, the id of the platform's public/shared project — it must name a project schema (`p_<id>`) that already exists. It fills `main.env.ELITEA_AI_PROJECT_ID`, `llmGateway.env.ELITEA_AI_PROJECT_ID` and `web.env.VITE_PUBLIC_PROJECT_ID` at once; `helm template` refuses a values file where the three copies disagree.

## Choose a values file

<Tabs>
<Tab title="values.yaml (base)">
The chart's own defaults: a **default install has no production authentication**, so `ELITEA_CONFIGURATIONS_ENABLED`, `ELITEA_PROJECT_INFO_ENABLED`, `ELITEA_INDEX_TYPES_ENABLED` and `ELITEA_APPLICATION_SKILLS_ENABLED` all render off, and `main.runtime.enabled` is off — no chat. Start here only if you are layering capabilities on by hand.
</Tab>
<Tab title="values-standalone.yaml">
The full capability set, matching `docker-compose.standalone-full.yml` — every capability flag on, the runtime plane on (agent execution, index ingest), sized for `postgresql.maxConnections: 200` across up to `main.autoscaling.maxReplicas: 4`. Needs both the runtime material Secret and the auth material Secret. This is the reference production shape.
</Tab>
<Tab title="values-auth-minimal.yaml">
The cheapest install that can seed an AI provider credential through the product's own API instead of hand-written SQL: production (Form) authentication plus `ELITEA_CONFIGURATIONS_ENABLED`, **no runtime plane** — no agent execution, no chat. Needs the auth material Secret, but no Redis, no runtime material Secret and no worker: the Form sign-in state is in PostgreSQL.
</Tab>
<Tab title="values-gke.yaml">
Google Kubernetes Engine with no static cloud credential: Cloud SQL with `sslmode=require` and a hand-prepared database, keyless GCS through Workload Identity, the GKE Ingress with its BackendConfig and FrontendConfig, Google's load-balancer ranges in the NetworkPolicy, and every Secret from Secret Manager through `externalSecrets`. Sized for about 4 vCPU and 10 GiB of requests. See [Deploy on GKE with Argo CD](/deployment/gke-argocd).
</Tab>
<Tab title="values-staging.yaml">
A minimal single-replica shape (image tag `shadow-v0.1`, `DATABASE_URL` inlined for a throwaway environment, autoscaling and the pod disruption budget both off). Use it for a disposable smoke/shadow environment, not as a production starting point.
</Tab>
</Tabs>

## Install: one chart, one namespace

One release installs everything, in one namespace. NATS requires TLS and a client certificate from every client (mTLS, no anonymous or password access), and those certificates come from the chart's own NATS CA, a *namespaced* cert-manager `Issuer`, so NATS, its bootstrap and the platform share the release's namespace by construction. **cert-manager must be installed first.**

From a clone, build the chart's dependencies first. The upstream NATS chart and the sandbox-runtime installer are pinned in the committed `Chart.lock`, and `charts/` is never committed:

```bash
deploy/helm/elitea/build-deps.sh   # helm dependency build, from Chart.lock
helm install elitea deploy/helm/elitea \
  -f deploy/helm/elitea/values-standalone.yaml \
  --set postgresql.existingSecret=elitea-main-db \
  --set-string llmGateway.env.GATEWAY_SELF_LLM_ORIGINS=https://elitea.example.com/llm/v1 \
  --set-string llmGateway.egressPosture=public-unrestricted \
  --set-string platform.aiProjectId=1 \
  -n elitea --create-namespace
```

The published chart is the recommended source: `oci://ghcr.io/elitea-ng/charts/elitea --version <version>` in place of the path. Its package carries the same values files (`helm pull --untar` to read them) and both dependencies, so it needs no `helm dependency build`. In an air-gapped network, mirror that OCI chart; do not build from a clone.

The chart issues each NATS client (elitea-main, the LLM gateway, the scheduler, the worker) its own certificate and renders `tls://elitea-nats.elitea.svc.cluster.local:4222` for it — no NATS credential goes in any value. The stream and KV bootstrap is a `post-install,post-upgrade` hook Job; until it has run, the workloads restart, then settle.

<Warning title="No --wait on a first install">
`helm install --wait` waits for workloads that wait for the streams the bootstrap hook creates, and that hook runs only after the wait. Leave `--wait` off the first install; later upgrades may use it.
</Warning>

For three NATS nodes, add `-f values-nats-ha.yaml` (it raises the bootstrap's replica count too). To use a NATS you run yourself, set `nats.enabled=false` and point `natsClient.*` at it. Under ArgoCD the same chart orders itself with sync waves — see [GitOps with ArgoCD](/deployment/argocd).

<Check title="Prove it renders first">
`helm template` catches missing prerequisites before any kubectl apply:
```bash
helm template deploy/helm/elitea -f deploy/helm/elitea/values-standalone.yaml \
  --set postgresql.existingSecret=elitea-main-db \
  --set-string llmGateway.env.GATEWAY_SELF_LLM_ORIGINS=https://elitea.example.com/llm/v1
```
</Check>

## The migration job and DB bootstrap

`elitea-migrate` runs as a pre-install hook; the database may start empty. The `dbInit` Job (hook weight -20) handles `CREATE DATABASE` for the agent-state database before migrations run. It creates no extension.

## First-admin bootstrap

A fresh database seeds exactly one administrator, `dev@elitea.ai`, with no password on a single-sign-on deployment — name your own account instead through `identity.initial_global_admins` (a YAML list, wins when the authentication document has one) or `main.env.ELITEA_INITIAL_GLOBAL_ADMINS` (comma-separated, the usual path for a single-sign-on-only install with no document). With Form sign-in off (the default), the first OIDC or SAML sign-in that matches an entry — `oidc:<sub>`, `saml:<nameid>`, or `email:<address>` for an OIDC login with a verified address — is your first administrator. Write Form logins there only if you enable Form sign-in.

An entry is `oidc:<sub>`, `saml:<nameid>`, or `email:<verified address>` (matches only when the id_token asserts `email_verified: true`). The grant is one-shot: an account that already holds any administration role is left as is; one with none receives the grant on its next sign-in.

For OIDC with a verified e-mail address, use `email:<your address>`. You know this value before the first sign-in, so you can set it at install time.

For other cases, sign in once and open **Settings › Profile**. Each **Sign-in reference** row shows one exact value that the list accepts, for example `oidc:<sub>` or `saml:<nameid>`. Click a row to copy it. Add the value to the list, upgrade the release, and sign in again. You do not need to query the database. See [Install Elitea](/getting-started/install#first-login-and-setup) for the browser-side walkthrough of this same step.

## Capability flags this install serves

<Accordion title="How to read this table">
`cmd/elitea-main` gates whole route groups on these variables. `values.yaml` sets every one; `values-standalone.yaml` is the reference production set. `ELITEA_CONFIGURATIONS_ENABLED` ships **empty** in the base chart — `_helpers.tpl` derives `"true"` automatically once any authentication is configured and `ELITEA_AI_PROJECT_ID` is set; a stated value always overrides the derivation.
</Accordion>

| Flag | Default install | `values-standalone.yaml` | Needs |
|---|---|---|---|
| `ELITEA_ARTIFACTS_ENABLED` | on | on | object storage configured |
| `ELITEA_CONFIGURATIONS_ENABLED` | derived | on | any authentication **and** `ELITEA_AI_PROJECT_ID` |
| `ELITEA_PROJECT_INFO_ENABLED` | off | on | production authentication |
| `ELITEA_CONFIGURATIONS_MUTATION_ENABLED` | off | off | `ELITEA_CONFIGURATIONS_ENABLED` **and** `runtime.enabled` |
| `ELITEA_INDEX_TYPES_ENABLED` | off | on | production authentication |
| `ELITEA_APPLICATION_SKILLS_ENABLED` | off | on | production authentication |
| `ELITEA_RUNTIME_ENABLED` (`main.runtime.enabled`) | off | on | production authentication **and** runtime material |

<Warning>
`ELITEA_CONFIGURATIONS_MUTATION_ENABLED` stays off in every shipped values file. It composes a second, asynchronous write route that would win the path from the compatibility route every install currently serves — and the compatibility route already writes `status_ok` inline from the same admission decision, which is what makes a saved credential usable. Turning it on is a separate cutover with its own client-side work, not a fix for an invisible credential.
</Warning>

## Post-install checks

<Steps>
<Step title="Liveness through the edge">
```bash
curl -si https://elitea.example.com/healthz   # 200 {"status":"ok"} with "vary: Origin"
```
`/readyz` and `/startupz` are deliberately not routed by the edge: their bodies name each dependency's state. The chart's probes reach them on the pod directly.
</Step>
<Step title="Admin console">
`/admin/app` — sign in as the account you named above.
</Step>
<Step title="Docs and API reference">
`/docs/` (this site) and `/api/docs` (the OpenAPI UI) should both resolve once `main.ingress` (or a route of your own to elitea-main) publishes the platform: elitea-main relays `/app` and `/docs` to elitea-web itself.
</Step>
</Steps>

See [Troubleshooting](/support/troubleshooting#operator-checks) for what each endpoint answers and the application-level Health tab it complements.

## What a Kubernetes install does NOT give you

<AccordionGroup>
<Accordion title="No PostgreSQL">
The chart provisions no database. The migration hook fails against a cluster where PostgreSQL does not already exist or where the Secret/host settings have not been pointed at it. NATS, by contrast, is part of the release: elitea-main's live updates — the project SSE stream and canvas presence — need it with JetStream (`ELITEA_EVENTS_NATS_URL`, derived from the `natsClient` block), and so does the runtime plane: its command bus is JetStream in the RUNTIME account (`ELITEA_RUNTIME_NATS_URL`, as the `elitea-main-runtime` identity), consumed by the workers from their own WORKER account. The chart refuses `main.runtime.enabled` with no NATS to publish to.
</Accordion>
<Accordion title="No edge by default">
No Ingress or HTTPRoute renders until `main.ingress.enabled: true`. Then it is one `/` rule to elitea-main, which is the whole edge: elitea-main redirects `/` to `/app/`, relays `/app` and `/docs` to elitea-web, and serves its MCP endpoint under `/app` itself. On GKE, `main.ingress.gke` adds the BackendConfig and FrontendConfig the Google load balancer needs.
</Accordion>
<Accordion title="Bring your own NATS">
The bundled server lives in the release's namespace, signed by the chart's namespaced `elitea-nats-ca` Issuer. To use a NATS you run elsewhere, set `nats.enabled: false`, back a cert-manager `ClusterIssuer` with a CA used for NATS only, and point `natsClient.service`, `natsClient.namespace` and `natsClient.tls.issuerRef` at it; the bootstrap's identities follow `natsClient` (`natsBootstrap.tls.certificate.issuerRef`). The bootstrap Job still runs against your server unless `natsBootstrap.enabled: false`. Your server must run JetStream and map the same client identities, or elitea-main refuses to start. `deploy/helm/elitea/NATS.md` has the contract.
</Accordion>
<Accordion title="Who can mint a NATS identity">
Anyone who may create a cert-manager `Certificate` in the NATS namespace, or read its Secrets (the CA key is one), can obtain any NATS client identity. Restrict both with RBAC; the optional approver-policy (`nats.security.approverPolicy`) limits what the NATS issuers sign. See `deploy/helm/elitea/NATS.md`.
</Accordion>
<Accordion title="No secrets">
Every sensitive value is a Kubernetes Secret — see "Secrets to create beforehand" above. In production, turn on `externalSecrets` and the chart renders an ExternalSecret for each one from your secret manager's store; [Deploy on GKE with Argo CD](/deployment/gke-argocd) shows it with Google Secret Manager.
</Accordion>
</AccordionGroup>
