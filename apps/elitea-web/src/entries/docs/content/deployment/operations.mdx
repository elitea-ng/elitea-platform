Running the platform after install: upgrading it safely, changing its master key, scaling its four independently-scaled components, and where to look when something breaks.

## Upgrades

<Steps>
<Step title="Bump the chart version">
Point your ArgoCD `Application` (or `helm upgrade`) at the new published chart version — see [GitOps with ArgoCD](/deployment/argocd#image-tag-promotion). The published chart's `image.tag` already tracks that version.
</Step>
<Step title="Let the migration hook run first">
`elitea-migrate` is a `pre-install,pre-upgrade` Helm hook. Helm applies and awaits every such hook — including the migration Job — before it touches any of the release's other resources, so new pods never roll against an un-migrated schema. A failed migration **aborts the release**, and the previously running pods keep serving; nothing is torn down until the new version proves it can start.
</Step>
<Step title="helm upgrade">
```bash
helm upgrade elitea deploy/helm/elitea \
  -f deploy/helm/elitea/values-standalone.yaml \
  --reuse-values \
  --set image.tag=<new-tag>
```
Or, under ArgoCD, let `selfHeal: true` reconcile the bumped `targetRevision`/parameter automatically.
</Step>
<Step title="Roll back on failure">
`helm rollback elitea <revision>` (or the ArgoCD equivalent, `argocd app rollback elitea <history-id>`) returns to the previous release's values and image tags. The migration hook runs again on the way there — a rollback that also needs a schema rollback is a database operation this mechanism does not perform for you.
</Step>
</Steps>

## Changing SECRETS_MASTER_KEY

The key has three states, and moving between them is not symmetric:

| State | Effect |
|---|---|
| Set, valid | Every project's vault key is wrapped with it; rows are Fernet tokens. |
| Not set | The service still starts, with a **log warning** — every project key is stored **in the clear**. Anyone who can read the database can open every project secret. |
| Set, malformed | The service **refuses to start**, naming the variable. |

Rows written under one key (or under no key) do not become readable when the key changes — there is no in-place re-encryption. To rotate the key: run `scripts/rewrap-centry-vault.py` against a **copy** of the database first. It rewraps the project key and never rewrites the secret values themselves, so a rotation that fails partway leaves the plaintext secrets untouched.

<Warning>
Both `elitea-main` and `elitea-llm-gateway` read the same `centry.secrets_key` table. Give the same value to every service that reads it — two services with two answers would put two row formats in one table, and neither could read what the other wrote.
</Warning>

## Scaling

Three components carry a native `HorizontalPodAutoscaler`; the fourth uses a different mechanism on purpose:

<CardGroup cols={2}>
  <Card title="elitea-main" icon="server">CPU/memory HPA, `minReplicas: 2` / `maxReplicas: 10` by default. Scaling this past what `postgresql.maxConnections` was sized for is refused at render time — see [Production deployment overview](/deployment/overview#sizing-the-postgresql-connection-budget).</Card>
  <Card title="elitea-web" icon="layout"> CPU/memory HPA. Stateless; a rollout is safe at any time.</Card>
  <Card title="llm-gateway" icon="waypoints">An HPA on a custom `/llm` SSE-connection metric — CPU/memory is a poor signal for I/O-bound streaming. **Off by default**: it needs the Prometheus Adapter installed and configured to surface that gauge metric, or it reports `FailedGetPodsMetric` and silently pins at `minReplicas`.</Card>
  <Card title="agent worker" icon="cpu">**No native HPA.** An agent execution spends most of its life waiting on a model, so CPU/memory never reflects backlog. Queue-depth autoscaling through **KEDA** is available (`worker.autoscaling`, off by default) — it scales on the Redis consumer group's pending-entry depth. The chart refuses to install a KEDA `ScaledObject` unless KEDA is actually present, rather than creating an object nothing reads.</Card>
</CardGroup>

<Warning>
KEDA's scaler must be able to verify the runtime Redis's private CA — install the KEDA operator with that CA mounted first. A scaler that cannot connect reports no depth, which scales the fleet **down** while the backlog grows; the chart cannot detect this for you.
</Warning>

<Note>
The agent worker's own replica count stays correct at `>1` — the database enforces one active claim per execution regardless (`execution_claims_active_idx` is unique on `(execution_id, generation)` while a claim is live) — but scaling out is not free capacity by default. Measure the Redis consumer group's read rate before raising it or turning KEDA on; a long `cooldownSeconds` (300s default) is deliberate, because an in-flight agent execution can run for minutes and a short cooldown turns every quiet moment into a round of terminations.
</Note>

## Backups

<AccordionGroup>
<Accordion title="PostgreSQL">
Not provisioned or backed up by any chart here — bring your own PostgreSQL operator/managed service and its backup mechanism. The connection budget reserves headroom (`reservedConnections: 25`) explicitly for backup tooling and interactive `psql` alongside the application's own pools, so a backup job does not compete with the application for its last connection slot.
</Accordion>
<Accordion title="Object storage">
Also brought by you — the chart only creates the bucket (optionally, via `objectInit`) and sets its retention lifecycle. Use your object store's own versioning/replication for backup.
</Accordion>
<Accordion title="NATS JetStream">
The `nats` and `nats-bootstrap` charts are commodity infrastructure this platform points at; back up the JetStream KV buckets and stream through NATS's own tooling if their loss matters to you. Losing the JetStream store resets budget-enforcement counters to zero, but does not lose spend history: the Usage page's accumulators are written independently by elitea-scheduler's write-back consumer from the gateway's billing deltas, not read out of the counter itself.
</Accordion>
<Accordion title="Restoring from a backup that predates a worker's session row">
`runtime-session-init` (or the Helm workload-session Job) is what authorizes the agent worker's certificate identity in `elitea_runtime.workload_sessions`; a database restored from a backup that predates it has no such row. Re-run `standalone-stack.sh seed-runtime` (compose) or re-trigger the workload-session hook Job (Helm) to recover, rather than assuming a restore alone brings chat back.
</Accordion>
</AccordionGroup>

## CI/CD: what publishes, and how it's checked

`.github/workflows/publish.yml` runs on pushes to `main`/`next`: `semantic-release` decides the version, then every first-party image is built, **scanned twice** (once against the artefact this release actually pushes, in addition to a same-day CI scan of a rebuild), and **cosign-signed keylessly** before the charts (`elitea`, `nats`, `nats-bootstrap`) are packaged, stamped with that version, pushed to `oci://ghcr.io/elitea-ng/charts/<chart>`, and signed the same way. The chart job runs strictly after the images it references are pushed, so a chart never reaches the registry pointing at a tag that does not exist yet. If any stage fails, a rollback job deletes everything that stage's run had already pushed — charts and images alike.

```bash
cosign verify ghcr.io/elitea-ng/elitea-main:<tag> \
  --certificate-identity-regexp '^https://github.com/elitea-ng/elitea-platform/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Separately, `.github/workflows/helm-install-smoke.yml` installs the chart into a real `kind` cluster (not just `helm template`) on every PR touching `deploy/helm/**`, and asserts every pod reaches Ready, the DeepWiki/Inventory provider pod's two containers run the runners the chart set, the facade's provider registration is healthy over its mTLS hop, and a fixture generation completes end to end — the runtime plane, workers and LLM gateway stay off in that smoke run, so it proves the chart installs cleanly, not the full product.

## Security posture

<CardGroup cols={2}>
  <Card title="Image scanning" icon="shield-check">Every published image is scanned by Trivy against the exact digest this release pushes (not a same-day rebuild), gated by `scripts/ci/image-scan-gate.sh`; an exempted finding must be recorded in `.github/image-scan-exempt.txt` rather than silently passing.</Card>
  <Card title="mTLS runtime material" icon="lock">The agent-execution plane's three listeners (control, output, content) all require and verify a client certificate; there is no cleartext mode. The runtime and auth material both arrive as Kubernetes Secrets, copied by an init container into an owner-only `emptyDir` because a plain Secret volume cannot satisfy the permission profile the code enforces.</Card>
  <Card title="Forward-auth header stripping" icon="shield-alert">The edge (Ingress/HTTPRoute) must strip caller-supplied `X-Auth-*` and `X-Elitea-*` identity headers before they reach elitea-main — the pod network typically sits inside `trusted_proxy_cidrs`, so anything reaching the Service with these headers set by the caller is an impersonation. `main.ingress.stripIdentityHeaders` lists the exact set for the HTTPRoute path; a plain `networking.k8s.io/v1` Ingress has no portable header-removal field and must strip them on the ingress controller itself.</Card>
  <Card title="GATEWAY_IDENTITY_SECRET" icon="key">Required, not optional, on both elitea-main and the gateway, and the two must agree — see [Install with Helm](/deployment/helm-install#secrets-to-create-beforehand).</Card>
</CardGroup>
