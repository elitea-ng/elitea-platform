The Memory toolkit gives an agent, pipeline or conversation a small key-value store it can write to and search across turns — separate from the conversation's own chat history. It's listed under the **other** category in the toolkit type picker.

<Note>
This is a different feature from [Settings › Memory](/menus/settings/memory)'s **Long-term Memory** section, which recalls facts about you automatically, before a turn starts, across every conversation — with no tool call involved. The Memory toolkit here is a real, attachable tool the model calls itself, mid-turn, against its own key-value store.
</Note>

## Prerequisites

- On the Python worker, a `pgvector` credential: the memories are rows in that database.
- On a deployment that runs the Rust worker with the Rust indexing runtime, no credential: the form does not ask for one, and memories are kept in the platform's vector store. An administrator must have set the memory embedding model (`worker.runtime.memoryEmbeddingModel`); without it the Memory type is hidden from the picker with that reason.
- No vendor account is needed — the store lives inside your project.

## Connect the toolkit

<Steps>
<Step title="Open the toolkit type picker">
In the left navigation, open **Toolkits**, then select **New**. Filter the type picker by the **other** category, or search for "Memory".
</Step>
<Step title="Set the store credential (Python worker only)">
Choose a **pgvector** credential to back the store. The Rust worker's form has no such field.
</Step>
<Step title="Save">
Name the toolkit and select **Create**. Attach it to an agent, pipeline or conversation the same way as any other toolkit.
</Step>
</Steps>

## Common issues

<Note>
Memory works on both workers, with one difference in where the data lives. On the Python worker memories are rows in the pgvector database you picked. On the Rust worker (Rust indexing runtime) they are stored in the platform's vector store, scoped to your project and the toolkit's **Namespace**, and `search_memory` ranks them by how close they are to the query. Memories saved under the Python worker are not carried over when a deployment moves to the Rust worker.
</Note>

<Note>
On the Rust worker a memory holds up to 16 KiB of content and 8 KiB of metadata, a key is at most 256 bytes, and a namespace holds up to 10,000 memories and versions; `search_memory` returns at most 50 results.
</Note>

<Note>
**Memory scope** (Rust worker). *Personal* (the default): each person has a private memory, and nobody else can read, search or delete it. *Project*: one memory shared by everyone in the project. *Both*: the agent chooses per memory, personal unless it says project. Anything saved to *project* memory is read back by every later conversation in the project as a fact, so in *Both* mode the agent is told to save there only when the person asked and never to copy personal memories or text that came from a web page, a document or a tool. If an agent reads untrusted content, prefer *Personal* only. A scheduled run acts as the person who owns the schedule and uses that person's personal memory. A conversation with more than one person has no personal memory (the agent says so); project memory still works there. Memories are kept per project, and the platform, not the agent, keeps one person's personal memory from another: it is enforced where the memories are stored.
</Note>

<Note>
On the Rust worker, saving to an existing key keeps the old value as history instead of overwriting it. `get_memory` and `search_memory` return the current value; they also accept `as_of` (an RFC 3339 timestamp, to see what was true then) and `include_history`. `delete_memory` removes every version. A key keeps at most 20 versions. Deleting the toolkit deletes its memories, including every person's personal ones in its namespace; a person who leaves the project has their personal memories there deleted.
</Note>

<Note>
The store is scoped to whatever key you give it — an agent must be instructed (or coded, in a pipeline) to use consistent keys, or writes and reads won't line up. There is no automatic per-user or per-conversation partitioning.
</Note>
